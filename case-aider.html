Aider：repo map 与编辑格式

Aider 是最早一批被广泛使用的终端编码助手。它几乎不靠"让模型自己调工具去找代码"，而是由代码在每一轮把仓库的结构摘要按 token 预算装进上下文，让模型用文本写出修改，再由代码确定性地应用、提交、跑 lint 和测试。读它，是学"不靠 agent 自主也能把上下文工程做到极致"的最好教材。

约 40 分钟前置：第 3、5 章研读版本：5dc9490（2026-05-22）
学完你能
  • 讲清 repo map 怎样用 tree-sitter 抽取定义与引用、用 PageRank 排序、再用二分法装进 token 预算
  • 说出"让模型输出文本补丁、由代码确定性应用"的编辑格式思路，以及 Aider 为什么宁可失败也不做模糊匹配
  • 理解 git 自动提交、/undo 的安全检查、lint/测试回灌与反思上限如何构成一个可逆、有上限的闭环
  • 能在自己的系统里复用"按预算装填上下文""稳定内容在前""弱模型做杂活"这几条做法

2 · 为什么读它

很多人一提编码 agent，就想到"模型自己 grep、自己读文件、自己决定下一步"。Aider 走的是另一条路：上下文由代码决定，动作由代码执行，模型只负责"想清楚要改什么、写出来"。这让它在几个方面成了教科书：

  • 上下文工程（第 5 章）：repo map 是"按 token 预算挑选最相关信息"的一个完整、可读的实现，有排序、有预算、有缓存。
  • 结构化输出的另一种答案（第 3 章）：它不用 JSON，而是让模型输出它最熟悉的文本格式（SEARCH/REPLACE 块、unified diff 等），再由代码严格解析。
  • 可逆与闭环（第 10 章）：每次修改都是一个 git 提交，lint 和测试的错误回灌给模型，回灌次数有上限。
  • 模型分工（第 1、14 章）：architect 模式用一个模型想方案、另一个模型改代码；提交说明、历史摘要交给便宜的弱模型（weak model）。

它也有明显的边界：没有通用的工具调用循环，很多步骤要用户在终端里确认。正因为简单，每个设计决定都看得很清楚。

5 · 关键设计一：repo map

问题：仓库有几百个文件，上下文装不下；只给模型聊天里的那一两个文件，它又不知道别处有什么函数可用、谁在调用它要改的函数。Aider 的回答是给其余文件做一份"地图"：只列出最相关的类和函数签名，并严格控制在 token 预算里。

5.1 抽取：tree-sitter 标签

get_tags_raw（repomap.py#L279）用 tree-sitter 解析文件，再用每种语言的查询文件（如 aider/queries/tree-sitter-language-pack/python-tags.scm）抓出两类节点：name.definition.*（定义）和 name.reference.*（引用），得到 Tag(rel_fname, fname, line, name, kind)。有的语言的查询只给定义不给引用，就用 Pygments 的词法分析补上引用。

解析结果按文件的修改时间（mtime）缓存在仓库下的 .aider.tags.cache.v* 目录里（diskcache，底层是 SQLite），文件没变就不重新解析（get_tags #L233）。

5.2 排序：带个性化的 PageRank

get_ranked_tags（#L365）把文件当节点：文件 A 引用了 B 定义的标识符，就连一条 A→B 的边。边的权重是一组经验系数：


mul = 1.0
if ident in mentioned_idents:
    mul *= 10
if (is_snake or is_kebab or is_camel) and len(ident) >= 8:
    mul *= 10
if ident.startswith("_"):
    mul *= 0.1
if len(defines[ident]) > 5:
    mul *= 0.1
for referencer, num_refs in Counter(references[ident]).items():
    for definer in definers:
        use_mul = mul
        if referencer in chat_rel_fnames:
            use_mul *= 50
        num_refs = math.sqrt(num_refs)
        G.add_edge(referencer, definer, weight=use_mul * num_refs, ident=ident)

每条规则背后都是一个朴素的判断：你在对话里提到的名字更重要（×10）；又长又带下划线或驼峰的名字更可能是有意义的业务函数，而不是 get、run 这类泛用词（×10）；私有的、到处都有定义的名字不重要（×0.1）；聊天里的文件引用的东西最重要（×50）；引用次数开平方，免得高频的琐碎名字压过一切。

然后用 networkx 的 PageRank 算每个文件的分数，聊天文件和你提到的文件得到"个性化"权重（personalization），相当于随机游走总是从它们出发。最后把每个文件的分数按出边权重分给它引用的那些定义，得到"（文件，标识符）"的排名。聊天里的文件本身不进地图，因为它们的全文已经在上下文里了。

5.3 装填：二分法逼近 token 预算

排好序之后，还要决定取前多少个。get_ranked_tags_map_uncached（#L629）用二分法试不同的数量，每次把候选渲染成树状文本（用 grep-ast 的 TreeContext 只显示定义所在行和必要的上层结构），数一下 token；落在预算 15% 误差以内就停。数 token 时，长文本只按行抽样约 1/100 再按比例放大（token_count #L89），在"准"和"快"之间取了平衡。

预算从哪来：get_repo_map_tokens（models.py#L782）默认取模型最大输入的 1/8，再夹在 1024 到 4096 之间；用户也可以用 --map-tokens 指定。聊天里还没有任何文件时，预算放大 8 倍（map_mul_no_files=8），但不超过"窗口减 4096"，因为这时模型最需要全局视野。

repo map 是"上下文预算"思想的一个完整实现：先定预算，再按相关性排序，最后按预算截断，而且预算、排序、截断三件事都在代码里，可测、可调。只按"最近 N 条""最多 N 个"截断的系统，做不到"长的少放、短的多放"。

6 · 关键设计二：编辑格式

让模型改代码，最直接的办法是让它输出整个新文件（whole 格式）：简单，但文件一大就既慢又贵，还容易在不相关的地方"顺手"改错。Aider 设计了一组编辑格式（edit format），每种对应一个 Coder 子类（aider/coders/），由模型配置表决定默认用哪种：

格式Coder 类模型写什么
diffEditBlockCoderSEARCH/REPLACE 块：先原样抄出要替换的几行，再写替换后的内容
diff-fencedEditBlockFencedCoder同上，但文件名写在代码围栏里面，适配部分模型的习惯
udiffUnifiedDiffCoder类似 diff -U0 的统一差异格式
wholeWholeFileCoder整个文件的新内容
patchPatchCoder一种带上下文的补丁格式
architectArchitectCoder只写方案，再交给编辑器模型用 editor-diff 等格式落地

在研读版本的模型配置表 aider/resources/model-settings.yml 里，显式写了 edit_format 的 333 项中，diff 占 289 项，diff-fenced 35 项，whole 和 udiff 各 4 项，architect 1 项。SEARCH/REPLACE 是事实上的主力格式。

6.1 宁可失败，也不错改

SEARCH/REPLACE 的风险在于模型抄的"原文"可能和文件有出入。replace_most_similar_chunk（editblock_coder.py#L157）按从严到宽的顺序尝试：完全匹配、只差前导空白、去掉多余的首行空行、处理模型用 ... 省略的部分。值得注意的是函数最后一段：


    return
    # Try fuzzy matching
    res = replace_closest_edit_distance(whole_lines, part, part_lines, replace_lines)
    if res:
        return res

按编辑距离做模糊匹配的代码还在，但被一行 return 挡在了前面，实际不会执行。这是一个很有代表性的取舍：匹配不上就明确失败，把失败原因清楚地告诉模型，比"猜一个最像的地方改掉"安全得多。

失败时 apply_edits（#L41）构造的错误信息是第 3 章"可执行的错误信息"的范例：哪个块没匹配上；文件里最相似的几行（"Did you mean to match some of these actual lines"）；如果替换内容其实已经在文件里了，提醒"你确定还需要这个块吗"；其余成功的块已经应用，"不要重发，只重写失败的那几个"。这段文字原样成为反思消息，模型下一轮只需修正失败的部分。

6.2 architect：把"想"和"写"拆开

ArchitectCoder.reply_completed（architect_coder.py#L11）在主模型写完方案后，经用户确认，新建一个编辑器 Coder：用 editor_model 和 editor_edit_format，关掉 repo map（map_tokens=0），清空历史，只把方案文本作为输入。这就是第 1 章的提示链（prompt chaining）加模型路由：擅长推理的模型负责规划，擅长按格式输出的模型负责落地，两个阶段的上下文互不污染。

7 · 关键设计三：git 作为安全网

让 AI 直接改你的工作区，最大的顾虑是"改坏了怎么办"。Aider 的答案是把每次修改都变成一个独立的 git 提交：

  • 先提交你的脏改动：要编辑的文件如果有你未提交的修改，dirty_commit（#L2411）会先单独提交，保证 AI 的修改和你的修改分在不同提交里。
  • 自动提交、可识别：--auto-commits 默认开启；提交说明由 commit_message_models() 返回的模型列表依次尝试，弱模型排在第一位（models.py#L622）；作者名默认标"(aider)"（repo.py#L131 的说明列出了几种署名组合）。
  • /undo 有三道检查（commands.py#L560）：最后一个提交必须是本次会话里 Aider 自己做的（记在 aider_commit_hashes 里），否则拒绝；已经推送到 origin 的不撤；涉及的文件有未提交改动的不撤。

这是第 10 章"可逆"和第 8 章"撤回"在单机工具上的落地：撤销只作用于自己确定做过的事，碰到已经对外生效（已推送）或会丢别人工作（有脏改动）的情况，宁可拒绝。

8 · 关键设计四：反馈回路与上下文维护

8.1 lint 与测试回灌

Linter.lint（linter.py#L82）按语言选检查方式：用户配置了 lint 命令就用它；Python 默认组合编译检查和 flake8 的一小组致命错误（E9,F821,F823,…，只抓语法错误和未定义名字这类"肯定是错"的问题）；其他语言用 tree-sitter 找语法错误。错误输出后面会附上出错行周围的代码结构（tree_context），让模型知道错在哪个函数里。

这里的设计要点是：回灌的信号是客观的、确定性的。模型说"改好了"不算数，编译器和测试说了才算。这正是第 12 章"不信 agent 自述，读客观进度"的同一思想。

8.2 历史摘要

ChatSummary（history.py#L7）在历史超过预算时触发。预算是模型最大输入的 1/16，夹在 1024 到 8192 之间（models.py#L358）。做法：保留最近约一半预算的消息原文（尾部），把更早的部分交给模型摘要（先试弱模型，失败再用主模型），切分点保证落在 assistant 消息之后；摘要加尾部还超预算就递归，最多 3 层。摘要在后台线程里做，不阻塞用户。

8.3 为提示缓存排好顺序

回头看 ChatChunks.all_messages 的顺序：系统提示和示例在最前，只读文件和 repo map 其次，然后才是会增长的历史、会被编辑的聊天文件、本轮消息。add_cache_control_headers（#L28）在示例（或系统提示）、repo map（或只读文件）、聊天文件这三处末尾打上缓存断点。开启缓存预热时，warm_cache（#L1340）会每隔约 5 分钟（5 * 60 - 5 秒）发一次 max_tokens=1 的请求，让缓存在用户思考时不过期。这是第 2 章"稳定在前、易变在后"的标准做法。

Aider 的 SEARCH/REPLACE 块匹配不上文件时，最终会怎么做？

  1. 用编辑距离找最相似的段落替换掉
  2. 改用 whole 格式重写整个文件
  3. 不修改这一块，把"哪块没匹配上、文件里最像的几行、成功的块不要重发"写成错误信息回灌给模型
  4. 直接放弃整轮修改并回滚所有文件
模糊匹配的代码虽然还在，但被一行 return 挡住了。失败的块不改，已经成功的块照常应用，错误信息成为下一轮的反思消息，并受 max_reflections = 3 的上限约束。这是"精确失败 + 可执行的错误信息"胜过"猜测性修复"的典型例子。

9 · 值得借鉴 / 不宜照搬

值得借鉴不宜照搬
按 token 预算装填上下文：排序与截断分离，用二分法逼近预算，抽样估算 token 数。权重是经验常数：×10、×50、×0.1 是为代码仓库调出来的，换到消息、文档等其他领域要用自己的评测重新校准。
稳定在前的分块顺序加缓存断点，必要时用预热保住缓存。依赖终端里的人工确认：加文件、修 lint、执行 shell 命令都在问用户。无人值守的系统要把这些确认换成策略和权限（第 8 章）。
文本补丁由代码确定性应用：模型写它熟悉的格式，解析严格、失败精确、错误可执行。没有通用的工具循环：开放任务（先查日志再决定改哪里）不适合这种"上下文由人指定"的模式。
每次修改都可逆：先隔离用户的脏改动，撤销只作用于自己做过且未推送的提交。自动提交到当前分支：团队仓库里通常要配合 worktree 或独立分支（第 12 章），否则提交历史会很杂。
弱模型做杂活：提交说明、历史摘要都先用便宜模型，失败再升级。反思靠人确认才触发：lint/测试失败要问"要不要修"，交互式场景合理，批处理场景要改成有上限的自动重试。

10 · 对照复盘

真实项目复盘
  • N12 · niuma 的上下文只按条数截断、没有 token 预算。Aider 的 repo map 和 ChatSummary 都是"先定预算、再排序、按预算截断"，预算还按模型窗口自动推算。
  • N3 · niuma 一次分析调用要同时输出十几个判断。architect 模式把"想方案"和"按格式写修改"拆给两次调用、两种格式，每一步都更容易做对。
  • N11 · 缓存和超时都是出了事才补。Aider 从分块顺序、缓存断点到预热，都把缓存当作设计的一部分。
  • D5 · devtask 的"完成"由模型用自由文本宣布。Aider 的闭环信号来自 lint 和测试命令的退出结果。

11 · 读码练习

练习 1：聊天里还没有任何文件时，repo map 的预算怎么变？为什么这样设计？

看 repomap.py#L120–132：预算乘以 map_mul_no_files（默认 8），但不超过"窗口减 4096"。没有聊天文件时，模型还不知道该改哪里，最需要全局视野，而且此时上下文里没有大文件占空间。

练习 2：同一个标识符被同一个文件引用了 9 次，边的权重会放大几倍？为什么不直接乘 9？

看 #L511–514：num_refs = math.sqrt(num_refs)，所以是 3 倍。注释写着"scale down so high freq (low value) mentions don't dominate"：高频引用往往是 log、get 这类琐碎调用，开平方压制它们的影响。

练习 3：如果一次回复里有 3 个 SEARCH/REPLACE 块，其中 1 个匹配失败，文件最终是什么状态？下一轮模型会看到什么？

看 editblock_coder.py#L41–124：成功的 2 块已写盘，失败的 1 块未改；随后抛出 ValueError，apply_updates 把它记为反思消息。模型会看到失败块的原文、文件里最相似的行，以及"其余 2 块已应用，不要重发"。

练习 4：/undo 为什么要检查"最后一个提交是不是本会话里 Aider 做的"？去掉这个检查会出什么事？

看 commands.py#L560 起的 raw_cmd_undo。没有这个检查，用户自己刚提交的工作也可能被当成 AI 的修改撤掉。撤回只应作用于"确定是自己做的"动作，这和第 8 章撤回自动代发的道理相同。

练习 5：把 ChatChunks 的顺序改成"历史放在 repo map 前面"，会对成本有什么影响？

看 chat_chunks.py#L16–40。历史每轮都在增长，放在前面会让后面的 repo map 和只读文件每轮都落在缓存前缀之外，缓存命中率大幅下降。前缀缓存的规则是：从第一个变化的位置起，后面全部失效（第 2 章）。

repo map 的排序里，"聊天中的文件引用了某个定义"对应的边权重要乘 50。最能说明这个设计意图的是？

  1. 让聊天中的文件本身排在地图最前面
  2. 你正在改的文件所依赖的函数和类，最需要让模型看到签名
  3. 减少 PageRank 的迭代次数
  4. 保证地图里一定包含测试文件
聊天中的文件本身不会出现在地图里（它们的全文已经在上下文中）。×50 让"被聊天文件引用的定义"大幅上升，模型改代码时最需要知道的，正是这些被调用者的签名。再配合个性化 PageRank，从聊天文件出发的"相关性"会沿着引用关系向外扩散。
本章要点
  • repo map = tree-sitter 抽取定义与引用 + 带个性化的 PageRank 排序 + 二分法装填 token 预算，排序、预算、截断都在代码里。
  • 编辑格式让模型输出熟悉的文本补丁，由代码严格解析与应用；匹配不上就精确失败、把可执行的错误信息回灌，而不是模糊地猜。
  • git 自动提交加上有检查的 /undo，把每次修改变得可逆；lint 和测试提供客观信号，反思最多 3 次。
  • 分块顺序、缓存断点、预热，以及弱模型处理杂活，是成本工程的具体做法。
  • 它的局限也同样清楚：经验权重需要校准，大量交互式确认不适合无人值守的场景。
