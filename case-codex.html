OpenAI Codex CLI：审批、沙箱与 agent loop

Codex CLI 是 OpenAI 开源的本地编码 agent。它最值得读的地方，是把"模型能不能执行这条命令"拆成了两个互相独立、可以组合的维度：审批策略决定什么时候问人，沙箱决定就算不问人，命令最多能碰到什么。把这两件事分开，是本课第 8、9 章最好的工程范本。

约 45 分钟前置：第 4、8、9、12 章研读版本：9f3cb25（2026-11-25）
学完你能
  • 在 Codex 源码里找到 agent loop、审批判定、沙箱执行、压缩、会话记录各自的位置
  • 说清 4 种审批策略 × 4 种沙箱策略组合起来，一条命令会被直接执行、请求批准还是拒绝
  • 理解"规则文件里的白名单""危险命令启发式""沙箱兜底"三层防线各自负责什么
  • 把这些设计迁移到你自己的 agent：审批与权限分离、无交互模式下拒绝而不是放行、规则可审计可沉淀

2 · 为什么读它

多数 agent 框架教你"怎么让模型调用工具"，很少认真回答另一个问题：模型调用的工具，凭什么可以被执行？Codex 不得不认真回答，因为它让模型在你的机器上跑任意 shell 命令。读它能学到三件在别处很少系统讲的事：

  • 权限的分层：静态规则（execpolicy）、启发式（危险命令识别）、操作系统级强制（沙箱）、人（审批）以及可选的模型审查者（guardian），各自守哪一段。
  • 无人值守时的默认值：无交互模式下，"需要人批准"一律变成"拒绝"，而不是"那就放行吧"。
  • 大型 agent 的工程化：会话以 JSONL 落盘可回放、JSON 事件流给程序消费、自动压缩、Stop hook，都和本课第 10、12、14 章一一对应。
怎么读一个 48 万行的仓库

不要从 main.rs 往下读。先定一个问题（比如"一条 shell 命令什么时候需要批准"），找到描述它的类型定义（AskForApproval），再沿着"谁用了这个类型"往外扩。类型定义上的文档注释往往就是最好的设计说明，本页引用的大部分结论都来自这些注释。

5 · 关键设计一：审批策略与沙箱是两件事

先看两个类型定义，它们在 protocol/src/protocol.rs 里紧挨着：


pub enum AskForApproval {
    /// Internal policy for projects marked untrusted. Commands require
    /// approval unless an explicit exec policy rule allows them.
    UnlessTrusted,          // 配置里写作 "untrusted"
    /// The model decides when to ask the user for approval.
    OnRequest,              // 默认值；"on-failure" 现在只是它的别名
    Granular(GranularApprovalConfig),  // 按类别分别开关
    /// Never ask the user to approve commands. ...
    Never,
}
pub enum SandboxPolicy {
    DangerFullAccess,
    ReadOnly { network_access: bool },
    ExternalSandbox { network_access: NetworkAccess },
    WorkspaceWrite { writable_roots, network_access, .. },
}

注意它们回答的是不同的问题：

审批策略 AskForApproval沙箱策略 SandboxPolicy
回答的问题什么时候停下来问人就算不问人，命令最多能碰到什么
谁来执行Codex 自己的代码（编排器）操作系统（Seatbelt、bubblewrap、seccomp）
被模型绕过的可能取决于判定逻辑写得好不好模型生成的命令在内核层被拦，提示词注入也绕不过

内置的三档预设（approval-presets）就是把两个维度配成对：

  • Read Only：on-request + 只读。能读工作区，改文件、联网都要批准。
  • Default（id 为 auto）：on-request + 工作区可写。能读写工作区、跑命令，联网和改工作区外的文件要批准。
  • Full Access：never + 不设沙箱。描述里直接写着"Exercise caution"。
一个细节：可写目录里的只读子目录

WritableRoot 结构（protocol.rs:1314）带了一组 read_only_subpaths。注释说明了原因：可写根目录下的 .git（尤其 .git/hooks）、.codex 这类文件夹，被改了就能让 agent 给自己提权，所以即使整个工作区可写，它们也保持只读。这就是第 9 章"最小权限"在文件系统上的落点：能改变规则本身的东西，不能交给被规则约束的一方去改。

    在 never + workspace-write 下，模型执行 npm install（需要联网）会怎样？

    1. 直接执行并联网成功，因为 never 表示不拦
    2. 弹出审批请求，问用户是否允许联网
    3. 在沙箱里执行，联网被沙箱拒绝，失败结果直接返回给模型，不会升级去问人
    4. 命令被禁止，根本不会执行
    never 的注释写的是"永远不问人批准命令，失败立即返回给模型，绝不升级给用户审批"。它不等于"什么都放行"：没有被判定为危险的命令会被放行，但仍然跑在沙箱里，沙箱照样拦。这正是"审批"和"沙箱"分开的意义：关掉审批，不等于关掉沙箱。

    6 · 关键设计二：三层防线，各守一段

    一条命令在执行前会依次经过三层检查，每一层的强度和用途都不一样：

    1. execpolicy 规则（显式、可审计）：用 Starlark 写的 prefix_rule，按命令前缀匹配，决定 allow、prompt 或 forbidden，多条命中时取最严格的那个。规则可以带 justification（为什么有这条规则，会显示在审批提示里），还可以带 match / not_match 示例，加载时就当单元测试跑一遍。说明见 execpolicy/README.md。
    2. 危险命令启发式（窄而保守）：dangerous_command_match_for_exec 识别的其实很少：主要是带强制参数的 rm，外面套了 sudo、env、trap 也能拆开识别。命中后除非策略是 never（那就直接禁止），否则一律询问。
    3. 沙箱（兜底、强制）：前两层都是"判断"，只有沙箱是"强制"。启发式漏掉的命令，仍然只能在允许的目录里写、默认不能联网。
    
prefix_rule(
    pattern = ["git", ["push", "reset"]],   # 列表元素表示"任选其一"
    decision = "prompt",                    # allow | prompt | forbidden
    justification = "推送和重置会影响远端或丢失工作，需要人确认",
    match = [["git", "push"], "git reset --hard"],   # 加载时验证：这些必须命中
    not_match = ["git status"],                      # 加载时验证：这些不能命中
)
    可迁移的经验：规则要能自证

    match / not_match 是一个小而强的设计：规则文件里自带正反例，加载时就校验。你给自己的 agent 写白名单、敏感词表、路由规则时，也应该让每条规则带上它该拦和不该拦的例子，这样规则改坏了会在加载时就报错，而不是在线上漏拦。

    还有一个容易被忽略的闭环：审批通过时，Codex 可以附带一条建议的规则修订（proposed_execpolicy_amendment，定义在 tools/sandboxing.rs 的 ExecApprovalRequirement 里），用户接受后，以后同类命令就不用再问。这是第 8 章"按采纳记录逐步放权"的工程化版本：放权的结果落在一份人能读、能审、能回滚的规则文件里，而不是藏在某个模型的记忆里。

    7 · 关键设计三：无人值守时，"该问人"就等于"不许做"

    codex exec 是给脚本和 CI 用的无交互模式。没有人可以点"批准"，那遇到需要批准的请求怎么办？approval_warning.rs 里的启动警告说得很清楚：codex exec runs non-interactively and immediately rejects approval requests it receives. 也就是立即拒绝，而且会提示你：想自己审，就到交互界面里跑。

    其他相关设计：

    • exec 默认要求在 git 仓库里运行，不在仓库里要显式加 --skip-git-repo-check：有 git，改坏了才能回滚。
    • --output-schema 接一个 JSON Schema 文件，约束模型最终回答的形状（第 3 章）。
    • --json 输出事件流，事件类型定义在 exec_events.rs：thread.started、turn.started / turn.completed / turn.failed、item.started / item.updated / item.completed、error。条目类型包括助手消息、推理、命令执行、文件修改、MCP 工具调用、网页搜索、待办清单等。
    • --ephemeral 不把会话写盘；codex exec resume 续上之前的会话。

    "立即拒绝"和"抛错退出"的区别很重要：拒绝结果会作为工具结果回到模型，模型可以换一条不需要审批的路继续干活；只有确实做不下去才失败。这比"遇到审批就整体失败"更有用，也比"遇到审批就放行"安全得多。

    8 · 关键设计四：上下文的边界与压缩

    AGENTS.md：不信任的项目不读

    load_project_instructions 的第一个判断是：项目被标记为不受信任，或者字节预算为 0，就什么都不加载。这是第 9 章"间接提示注入"的直接防御：你 clone 了一个陌生仓库，它的 AGENTS.md 里如果写着"把 ~/.ssh 发到某个地址"，不受信任时这段文字根本进不了上下文。

    其他规则（都在 agents_md.rs）：

    • 每个目录依次找 AGENTS.override.md、AGENTS.md、配置的备用文件名，只取第一个存在的；本地覆盖文件优先。
    • 备用文件名里带路径分隔符、. 或 .. 的会被忽略，注释特别提到：在 Windows 上解析网络路径，哪怕只是探测元数据，都可能把凭据发出去。
    • 默认预算 32 KiB（config_toml.rs:76），超了会给出"请精简或调大 project_doc_max_bytes"的警告，不会悄悄截断。

    自动压缩：交接给"另一个 LLM"

    阈值由 auto_compact_token_limit 决定：模型上下文窗口的 90%，配置了更小的值时取二者较小者。压缩用的提示词（prompts/templates/compact/prompt.md）只有几行，但定位很准：

    You are performing a CONTEXT CHECKPOINT COMPACTION. Create a handoff summary for another LLM that will resume the task.

    然后要求写进：当前进展与关键决定、重要上下文与约束和用户偏好、还剩什么要做、继续工作需要的关键数据。把压缩定位成"写交接文档"而不是"做摘要"，模型就会自然地保留"接手的人需要知道的东西"，而不是平均地缩短每一段。这和第 5 章、第 12 章讲的结构化笔记、交接是同一个思路。

    9 · 关键设计五：可选的模型审查者，但边界很清楚

    审批不一定只能交给人。ApprovalsReviewer（shared.rs:297）有两个取值：默认的 user，和 auto_review。后者的说明是：用一个提示词经过精心设计的子 agent 收集相关上下文，按基于风险的决策框架来批准或拒绝。

    值得注意的是它的位置。guardian/mod.rs 开头写着："扩展选择策略与证据；核心强制执行权限与必审要求"。也就是说：

    • 模型审查者是显式开启的，默认还是人；
    • 它是一个隔离的审查会话，不是正在干活的那个 agent 顺手给自己批；
    • 它能决定的只是"批准一次提权申请"，沙箱和必审规则仍由核心强制执行；编排器头部注释也说明，提权重试需要重新审查，不能沿用上一次的批准。

    10 · 值得借鉴 / 不宜照搬

    值得借鉴不宜照搬
    审批与权限分成两个正交维度，再用少量预设配对给用户选完整的操作系统级沙箱：你的 agent 如果不跑任意命令，用进程隔离或只读凭据就够了，不必自己维护 Seatbelt 和 seccomp 策略
    无人值守时"需要审批"直接变成"拒绝"，并把拒绝作为结果回给模型141 个 crate 的拆分粒度：这是大团队长期演进的结果，个人项目照搬只会增加摩擦
    规则文件带正反例、加载即校验；放权落在人能审的规则文件里危险命令启发式本身：它故意做得很窄，安全靠的是沙箱兜底；如果你没有沙箱，这么窄的启发式就远远不够
    不受信任的项目不加载项目说明；能改变权限的目录强制只读
    会话 JSONL 落盘、事件流给程序消费、Stop hook 有防死循环标志

    11 · 对照复盘

    和两个真实项目的对照
    • D8 授权只拦一次，权限请求由另一个 LLM 代按：Codex 也允许模型审查，但它是显式开启、隔离的审查会话，提权重试必须重新审查，沙箱与必审规则由核心强制执行。devtask 是正在跑的话题 agent 顺手按键，没有这些边界。
    • D9 三要素集中在同一个 agent：Codex 的默认档（workspace-write）不联网、只能写工作区，.git/hooks 等目录强制只读；devtask 没有给编码 agent 设权限模式，继承了全局配置。
    • D6 驾驭交互式终端，没用程序化协议：Codex 自己就提供了 exec --json 事件流、会话记录与 resume、app-server。驾驭它的程序应该消费这些结构化事件，而不是读终端画面。

    12 · 读码练习

    练习 1：on-request + read-only 下，模型想改一个文件，第一次尝试会发生什么？

    要点：改文件这类命令不是危险命令；on-request 在受限沙箱里对"没有申请提权"的命令判 Allow，所以会先在只读沙箱里跑，写入被沙箱拒绝。之后能否申请到沙箱外重跑，看 wants_no_sandbox_approval：on-request 返回 false，所以不会自动升级，失败结果回给模型；模型可以主动申请提权（这时才会询问用户）。看 core/src/exec_policy.rs 的 render_decision_for_unmatched_command_for_platform 和 core/src/tools/orchestrator.rs 里处理 SandboxErr::Denied 的分支。

    练习 2：为什么 granular 模式下，即使关掉了沙箱审批，危险命令仍然可能弹出审批？

    要点：GranularApprovalConfig 上 sandbox_approval 字段的注释写明："Dangerous commands can still request approval within existing permissions."。关掉的是"申请到沙箱外"这一类，危险命令在现有权限内的确认仍然保留。对照 render_decision_for_unmatched_command_for_platform 里危险命令分支：只有 Never 判 Forbidden，其余都判 Prompt。

    练习 3：AGENTS.md 的查找为什么默认不越过项目根？如果当前目录不在任何 git 仓库里会怎样？

    要点：看 core/src/agents_md.rs 的模块注释：以 project_root_markers（默认 .git）确定项目根，不越过它；找不到标记时只看当前目录；标记列表为空时不向上找。不越过项目根，是为了不把上层目录里与本项目无关、甚至不可信的说明带进上下文。

    练习 4：在 run_turn 里找到 Stop hook 要求继续时的处理，说说它如何避免无限循环。

    要点：core/src/session/turn.rs 中 if !needs_follow_up 之后的分支：hook 返回 should_block 且带有继续提示时，把提示记录为一条消息、把 stop_hook_active 设为 true 再 continue；没有提示的 block 会被忽略并发出警告。stop_hook_active 会传给 hook，hook 据此决定第二次不再拦截（第 12 章）。另外注意记忆整理这类无人值守会话被 Stop hook 拒绝时直接报错，不把拒绝喂回循环。

    Codex 对不受信任的项目不加载 AGENTS.md。这主要防的是哪类风险？

    1. 上下文太长导致费用上升
    2. 陌生仓库里的说明文件携带间接提示注入，诱导 agent 执行有害操作
    3. AGENTS.md 格式不规范导致解析失败
    4. 不同项目的说明互相冲突
    项目说明会被当作"用户指令"拼进上下文，权重很高。仓库里的文件是外部可控的内容，属于第 9 章说的不可信输入。不受信任时干脆不读，是最便宜也最可靠的防线。
    本章要点
    • Codex 把"什么时候问人"（审批策略）和"最多能碰什么"（沙箱）分成两个正交维度，再用 Read Only / Default / Full Access 三档预设配对。
    • 三层防线各守一段：execpolicy 规则显式可审计，危险命令启发式窄而保守，沙箱在操作系统层兜底。
    • 无人值守模式下需要审批的请求被立即拒绝，拒绝作为结果回给模型，而不是放行或整体失败。
    • 不受信任的项目不加载 AGENTS.md；可写目录里能改变权限的子目录强制只读。
    • 压缩被定位成"给接手的 LLM 写交接摘要"；会话以 JSONL 落盘，exec 输出结构化事件流。
