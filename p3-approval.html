P3 · 提案与审批：不批准就不发，批准两次也只发一条

代表你对外说话的 agent，第一条铁律是"一切对外动作皆提案"：模型只能提议，发不发由人（或人明确授权的规则）决定。这个项目把 P2 的回复草稿变成提案，并解决随之而来的所有工程问题：状态怎么流转、批准两次怎么办、发到一半进程崩了怎么办。

约 150 分钟前置：P2、第 8 章、第 10 章产出：SQLite 库 + 命令行审批工具 + 10 个测试
做完你能
  • 用"带条件的 UPDATE + 影响行数"实现并发安全的状态机
  • 用事务性发件箱（transactional outbox）保证"状态改了"和"要发的消息记下了"同时成立
  • 用幂等键让重试、重复批准、崩溃恢复都不会重复发送
  • 写一个策略层：默认人工审批，只有显式开启且全部护栏通过时才自动批准

1 · 成品是什么

一个命令行工具。分诊结果里需要回复的工单变成待审批的提案；你可以列出、查看、改写后批准、拒绝（并写理由）；批准后的消息经发件箱发出。下面是一次实际运行：

第 1 步：迁移 src/store/migrations.ts

建表语句写在你这个项目自己的迁移清单里，按顺序执行，执行到第几个记在 SQLite 的 user_version。规则只有一条：只追加，不修改已经发布的迁移。P4 会在末尾追加第 2 个。下面是加完 P4 之后的完整文件，现在只需要写第 1 个：

为什么状态用 CHECK 约束

状态拼错一个字母（'aproved'）是很难发现的 bug：那条记录从此不在任何查询里出现。数据库层的 CHECK 让它在写入时就报错。

第 2 步：打开数据库 src/store/db.ts

WAL 模式让命令行和后台进程可以同时读写；busy_timeout 让写冲突时等一会儿而不是立刻失败；每个迁移在一个事务里执行，失败就整个回滚。


import { Database } from 'bun:sqlite';
import { migrations } from './migrations';

// WAL：CLI 和后台进程可以同时读写同一个库；busy_timeout：写冲突时等一会儿而不是立刻报错。
export function openDb(path = 'agent-lab.db'): Database {
  const db = new Database(path, { create: true, strict: true });
  db.run('PRAGMA journal_mode = WAL');
  db.run('PRAGMA busy_timeout = 5000');
  db.run('PRAGMA foreign_keys = ON');
  migrate(db);
  return db;
}

function migrate(db: Database): void {
  const { user_version: current } = db.query('PRAGMA user_version').get() as { user_version: number };
  for (let v = current; v < migrations.length; v++) {
    db.transaction(() => {
      db.run(migrations[v]!);
      db.run(`PRAGMA user_version = ${v + 1}`);
    })();
  }
}

第 3 步：提案与状态机 src/proposals.ts

整个项目最重要的三个函数：

  • transition()：状态迁移的唯一入口。它不是"先读状态、判断、再写"，而是一条 UPDATE … WHERE id = ? AND status IN (允许的起点)，用影响的行数判断成没成。两个进程同时批准同一条，数据库保证只有一个能成功。
  • approve()：在一个事务里改状态并写发件箱。幂等键是"提案 id + 正文"的哈希：改写后的正文是另一条消息，得到另一个键；原文重发得到同一个键。
  • recoverInterrupted()：启动时把卡在 executing 的提案退回 pending。

import type { Database } from 'bun:sqlite';
import { createHash, randomUUID } from 'node:crypto';

export type Status = 'pending' | 'approved' | 'rejected' | 'expired' | 'executing' | 'done' | 'failed';
export type Proposal = {
  id: string;
  kind: string;
  target: string;
  body: string;
  final_body: string | null;
  status: Status;
  confidence: number;
  source_ref: string;
  auto_approved: number;
  reason: string | null;
  error: string | null;
  created_at: number;
  updated_at: number;
  expires_at: number;
};

export class ConflictError extends Error {}

const DAY = 24 * 3600 * 1000;

export function createProposal(
  db: Database,
  p: { kind: string; target: string; body: string; confidence: number; sourceRef: string; ttlMs?: number },
  now = Date.now(),
): Proposal {
  const id = randomUUID().slice(0, 8);
  db.query(
    `INSERT INTO proposals (id, kind, target, body, status, confidence, source_ref, created_at, updated_at, expires_at)
     VALUES (?, ?, ?, ?, 'pending', ?, ?, ?, ?, ?)`,
  ).run(id, p.kind, p.target, p.body, p.confidence, p.sourceRef, now, now, now + (p.ttlMs ?? DAY));
  logEvent(db, id, 'created', null, now);
  return getProposal(db, id)!;
}

export const getProposal = (db: Database, id: string) =>
  db.query('SELECT * FROM proposals WHERE id = ?').get(id) as Proposal | null;

export const listProposals = (db: Database, status?: Status) =>
  (status
    ? db.query('SELECT * FROM proposals WHERE status = ? ORDER BY created_at').all(status)
    : db.query('SELECT * FROM proposals ORDER BY created_at').all()) as Proposal[];

export const logEvent = (db: Database, proposalId: string, type: string, detail: string | null, now = Date.now()) =>
  db.query('INSERT INTO events (proposal_id, type, detail, at) VALUES (?, ?, ?, ?)').run(proposalId, type, detail, now);

// 状态迁移只走这一个函数：UPDATE … WHERE status IN (允许的起点)，靠影响行数判断成没成。
// 两个进程同时批准同一条，只有一个能把 pending 改掉，另一个拿到 ConflictError。
export function transition(
  db: Database,
  id: string,
  from: Status[],
  to: Status,
  fields: { final_body?: string; reason?: string | null; error?: string | null; auto_approved?: number } = {},
  now = Date.now(),
): void {
  const sets = ['status = ?', 'updated_at = ?'];
  const args: (string | number | null)[] = [to, now];
  for (const [k, v] of Object.entries(fields)) {
    sets.push(`${k} = ?`);
    args.push(v as string | number | null);
  }
  const placeholders = from.map(() => '?').join(', ');
  const res = db.query(`UPDATE proposals SET ${sets.join(', ')} WHERE id = ? AND status IN (${placeholders})`).run(...args, id, ...from);
  if (res.changes !== 1) {
    const current = getProposal(db, id);
    throw new ConflictError(current ? `提案 ${id} 当前是 ${current.status}，不能改成 ${to}` : `没有提案 ${id}`);
  }
  logEvent(db, id, to, fields.reason ?? fields.error ?? null, now);
}

export const idempotencyKey = (proposalId: string, body: string) =>
  createHash('sha256').update(`${proposalId}\n${body}`).digest('hex').slice(0, 32);

// 批准：改状态 + 写发件箱放在同一个事务里（transactional outbox）。要么都成，要么都没发生。
export function approve(db: Database, id: string, opts: { editedBody?: string; auto?: boolean } = {}, now = Date.now()): void {
  db.transaction(() => {
    const p = getProposal(db, id);
    if (!p) throw new ConflictError(`没有提案 ${id}`);
    const body = opts.editedBody ?? p.body;
    // failed 的可以再批准一次：同样的正文得到同样的幂等键，对方服务会去重
    transition(db, id, ['pending', 'failed'], 'approved', { final_body: body, auto_approved: opts.auto ? 1 : 0, error: null }, now);
    if (p.kind !== 'reply') return; // 非对外发送的提案（如 P4 的档案修改）由各自的执行器处理
    const key = idempotencyKey(id, body);
    const existing = db.query('SELECT status FROM outbox WHERE idempotency_key = ?').get(key) as { status: string } | null;
    if (existing?.status === 'sent') {
      transition(db, id, ['approved'], 'done', { reason: '这段内容之前已经发出过' }, now);
      return;
    }
    db.query(
      `INSERT INTO outbox (idempotency_key, proposal_id, target, body, status, created_at) VALUES (?, ?, ?, ?, 'queued', ?)
       ON CONFLICT(idempotency_key) DO UPDATE SET status = 'queued', last_error = NULL WHERE outbox.status = 'failed'`,
    ).run(key, id, p.target, body, now);
  })();
}

export const reject = (db: Database, id: string, reason: string, now = Date.now()) =>
  transition(db, id, ['pending', 'failed'], 'rejected', { reason }, now);

// 过期：待审批太久的草稿多半已经不合时宜，宁可作废也不要晚发。
export function expireStale(db: Database, now = Date.now()): number {
  const stale = db.query("SELECT id FROM proposals WHERE status = 'pending' AND expires_at < ?").all(now) as { id: string }[];
  for (const { id } of stale) transition(db, id, ['pending'], 'expired', { reason: '超过有效期未处理' }, now);
  return stale.length;
}

// 启动恢复：上次进程在"发送中"退出，不知道到底发没发出去。不自动重发，退回待审批让人决定；
// 再批准时用的是同一个幂等键，对方若已收到会去重，不会发两遍。
export function recoverInterrupted(db: Database, now = Date.now()): number {
  const stuck = db.query("SELECT id FROM proposals WHERE status = 'executing'").all() as { id: string }[];
  db.transaction(() => {
    for (const { id } of stuck) {
      transition(db, id, ['executing'], 'pending', { error: '上次发送时进程中断，不确定是否已发出；可直接重新批准，不会重复发送' }, now);
      db.query("UPDATE outbox SET status = 'failed', last_error = '进程中断' WHERE proposal_id = ? AND status = 'queued'").run(id);
    }
  })();
  return stuck.length;
}

第 4 步：发件箱与发送器 src/outbox.ts

发送器只做一件事：把排队的消息送出去，处理重试。注意每次成功都在一个事务里同时更新发件箱和提案状态。


import type { Database } from 'bun:sqlite';
import { transition } from './proposals';

// 外部发送接口的抽象。真实实现可以是邮件、IM、工单系统；要求它支持幂等键（或自己按幂等键去重）。
export interface Sender {
  send(msg: { idempotencyKey: string; target: string; body: string }): Promise<{ remoteId: string }>;
}

type Row = { idempotency_key: string; proposal_id: string; target: string; body: string; attempts: number };

// 把发件箱里排队的消息发出去。每条：approved → executing → done；失败重试，超过次数标 failed 交还给人。
export async function drainOutbox(db: Database, sender: Sender, opts: { maxAttempts?: number; now?: () => number } = {}) {
  const maxAttempts = opts.maxAttempts ?? 3;
  const now = opts.now ?? Date.now;
  const rows = db.query("SELECT * FROM outbox WHERE status = 'queued' ORDER BY created_at").all() as Row[];
  const report = { sent: 0, failed: 0 };
  for (const row of rows) {
    transition(db, row.proposal_id, ['approved'], 'executing', {}, now());
    for (let attempt = row.attempts + 1; ; attempt++) {
      try {
        const { remoteId } = await sender.send({ idempotencyKey: row.idempotency_key, target: row.target, body: row.body });
        db.transaction(() => {
          db.query("UPDATE outbox SET status = 'sent', attempts = ?, remote_id = ?, sent_at = ? WHERE idempotency_key = ?").run(
            attempt,
            remoteId,
            now(),
            row.idempotency_key,
          );
          transition(db, row.proposal_id, ['executing'], 'done', {}, now());
        })();
        report.sent++;
        break;
      } catch (err) {
        const message = err instanceof Error ? err.message : String(err);
        db.query('UPDATE outbox SET attempts = ?, last_error = ? WHERE idempotency_key = ?').run(attempt, message, row.idempotency_key);
        if (attempt >= maxAttempts) {
          db.transaction(() => {
            db.query("UPDATE outbox SET status = 'failed' WHERE idempotency_key = ?").run(row.idempotency_key);
            transition(db, row.proposal_id, ['executing'], 'failed', { error: `发送失败 ${attempt} 次：${message}` }, now());
          })();
          report.failed++;
          break;
        }
        await Bun.sleep(200 * 2 ** (attempt - 1)); // 指数退避
      }
    }
  }
  return report;
}

第 5 步：模拟外部服务与真实发送器

测试用的 FakeMessageApi 实现了"按幂等键去重"，还能模拟两种最难缠的故障：前几次直接失败；以及"其实发出去了，但响应在路上丢了"。后者是分布式系统里最经典的陷阱：你以为失败了，重试一次，对方就收到两条。


import type { Sender } from './outbox';

// 模拟一个支持幂等键的外部消息服务：同一个键只投递一次，重复请求返回第一次的结果。
// 还能模拟两种故障：前 N 次直接失败；"其实发出去了，但响应在路上丢了"。
export class FakeMessageApi implements Sender {
  readonly delivered: { target: string; body: string; remoteId: string }[] = [];
  private readonly byKey = new Map<string, string>();
  failNext = 0;
  loseResponseNext = 0;

  async send(msg: { idempotencyKey: string; target: string; body: string }) {
    if (this.failNext > 0) {
      this.failNext--;
      throw new Error('503 Service Unavailable');
    }
    let remoteId = this.byKey.get(msg.idempotencyKey);
    if (!remoteId) {
      remoteId = `m${this.delivered.length + 1}`;
      this.byKey.set(msg.idempotencyKey, remoteId);
      this.delivered.push({ target: msg.target, body: msg.body, remoteId });
    }
    if (this.loseResponseNext > 0) {
      this.loseResponseNext--;
      throw new Error('连接超时（对方其实已经收到）');
    }
    return { remoteId };
  }
}

命令行默认用 JsonlSender 把消息写进本地文件；设置了 SEND_WEBHOOK_URL 就改用 WebhookSender，幂等键放在 Idempotency-Key 请求头里——这是支付等行业通行的做法，接收方按这个头去重。


import { appendFileSync, existsSync, readFileSync } from 'node:fs';
import type { Sender } from './outbox';

// 本地演示用：把"发出去的消息"追加到一个 JSONL 文件，按幂等键去重。
export class JsonlSender implements Sender {
  constructor(private readonly path = 'sent.jsonl') {}

  async send(msg: { idempotencyKey: string; target: string; body: string }) {
    const lines = existsSync(this.path) ? readFileSync(this.path, 'utf8').split('\n').filter(Boolean) : [];
    const found = lines.map((l) => JSON.parse(l) as { key: string; remoteId: string }).find((r) => r.key === msg.idempotencyKey);
    if (found) return { remoteId: found.remoteId };
    const remoteId = `local-${lines.length + 1}`;
    appendFileSync(this.path, `${JSON.stringify({ key: msg.idempotencyKey, remoteId, target: msg.target, body: msg.body, at: new Date().toISOString() })}\n`);
    return { remoteId };
  }
}

// 接真实服务：POST 到一个 webhook（自动化平台、内部网关等），幂等键放在 Idempotency-Key 头里。
export class WebhookSender implements Sender {
  constructor(private readonly url: string) {}

  async send(msg: { idempotencyKey: string; target: string; body: string }) {
    const res = await fetch(this.url, {
      method: 'POST',
      headers: { 'content-type': 'application/json', 'idempotency-key': msg.idempotencyKey },
      body: JSON.stringify({ target: msg.target, text: msg.body }),
      signal: AbortSignal.timeout(15_000),
    });
    if (!res.ok) throw new Error(`webhook 返回 ${res.status}`);
    const data = (await res.json().catch(() => ({}))) as { id?: string };
    return { remoteId: data.id ?? msg.idempotencyKey };
  }
}

第 6 步：策略层 src/policy.ts

策略决定一条新提案是"等人批准"还是"可以自动批准"。默认值是最保守的：所有对象都要审批。自动批准必须按对象显式开启，并且每条护栏都要通过；任何一条不过，就退回人工审批，同时把原因写下来。


import type { Database } from 'bun:sqlite';

// 策略层：决定一条新提案是等人批准（suggest），还是可以自动批准（auto）。
// 默认一切 suggest；auto 必须按对象显式开启，而且每条护栏都要通过。
export type Mode = 'off' | 'suggest' | 'auto';
export type Policy = {
  modes: Record<string, Mode>; // 按发送对象设置；没设置的用 defaultMode
  defaultMode: Mode;
  minConfidence: number;
  maxAutoPerHour: number;
  denyKeywords: string[];
  quietHours: { start: number; end: number } | null; // 本地小时，支持跨午夜，如 { start: 22, end: 8 }
};

export const defaultPolicy: Policy = {
  modes: {},
  defaultMode: 'suggest',
  minConfidence: 0.85,
  maxAutoPerHour: 3,
  denyKeywords: ['合同', '报价', '付款', '薪资', '密码', '离职', '法务'],
  quietHours: { start: 22, end: 8 },
};

export type Decision = { action: 'drop' | 'pending' | 'auto'; reasons: string[] };

export function decide(
  db: Database,
  policy: Policy,
  p: { target: string; body: string; confidence: number; sourceText: string },
  now = new Date(),
): Decision {
  const mode = policy.modes[p.target] ?? policy.defaultMode;
  if (mode === 'off') return { action: 'drop', reasons: ['该对象已关闭'] };
  if (mode === 'suggest') return { action: 'pending', reasons: ['该对象需要人工审批'] };

  const reasons: string[] = [];
  if (p.confidence < policy.minConfidence) reasons.push(`置信度 ${p.confidence} 低于 ${policy.minConfidence}`);
  const hit = policy.denyKeywords.find((k) => p.body.includes(k) || p.sourceText.includes(k));
  if (hit) reasons.push(`命中敏感词「${hit}」`);
  const { n } = db
    .query('SELECT COUNT(*) AS n FROM proposals WHERE target = ? AND auto_approved = 1 AND created_at > ?')
    .get(p.target, now.getTime() - 3600_000) as { n: number };
  if (n >= policy.maxAutoPerHour) reasons.push(`近 1 小时已自动发送 ${n} 条`);
  if (policy.quietHours && inQuietHours(now.getHours(), policy.quietHours)) reasons.push('静默时段');
  return reasons.length ? { action: 'pending', reasons } : { action: 'auto', reasons: ['全部护栏通过'] };
}

const inQuietHours = (h: number, q: { start: number; end: number }) => (q.start <= q.end ? h >= q.start && h < q.end : h >= q.start || h < q.end);
护栏不是安全边界

敏感词、置信度、频率上限能挡住"明显不该自动发"的情况，但挡不住精心构造的提示注入。真正的边界是：自动批准只对低风险的对象和动作开放，并且发出后能撤回、能追责（第 8、9 章）。

第 7 步：命令行 src/cli.ts

triage 命令把 P2 的结果接进来：需要追问的生成追问提案，需要回复的生成回复提案，交给策略层决定是否自动批准。每次启动先做崩溃恢复。


import { parseArgs } from 'node:util';
import { OpenAICompatibleModel } from './models/openai-compatible';
import { drainOutbox } from './outbox';
import { decide, defaultPolicy } from './policy';
import { approve, ConflictError, createProposal, expireStale, getProposal, listProposals, recoverInterrupted, reject, type Status } from './proposals';
import { JsonlSender, WebhookSender } from './senders';
import { openDb } from './store/db';
import type { Ticket } from './triage/schema';
import { triageBatch } from './triage/pipeline';

const HELP = `用法：bun run src/cli.ts <命令>
  triage <tickets.json>          分诊工单，需要回复的生成提案（按策略决定是否自动批准）
  list [--status pending]        列出提案
  show <id>                      查看一条提案
  approve <id> [--edit 新正文]    批准（可改写后批准）
  reject <id> --reason 理由       拒绝
  send                           把发件箱里排队的消息发出去
  expire                         作废过期的待审批提案`;

const { positionals, values } = parseArgs({
  allowPositionals: true,
  options: { status: { type: 'string' }, edit: { type: 'string' }, reason: { type: 'string' } },
});
const [command, arg] = positionals;
const db = openDb(process.env.AGENT_LAB_DB ?? 'agent-lab.db');
const recovered = recoverInterrupted(db);
if (recovered) console.log(`⚠ 有 ${recovered} 条提案在上次发送时中断，已退回待审批`);
const sender = process.env.SEND_WEBHOOK_URL ? new WebhookSender(process.env.SEND_WEBHOOK_URL) : new JsonlSender();

try {
  switch (command) {
    case 'triage': {
      if (!arg) throw new Error('缺少 tickets.json');
      const tickets = (await Bun.file(arg).json()) as Ticket[];
      for (const r of await triageBatch(OpenAICompatibleModel.fromEnv(), tickets)) {
        if (!r.ok) {
          console.log(`✗ ${r.ticket.id} 分析失败：${r.error}`);
          continue;
        }
        const body = r.route.action === 'clarify' ? r.analysis.missing_info.join('\n') : r.analysis.reply_draft;
        if (!body || r.route.action === 'archive') continue;
        const d = decide(db, defaultPolicy, { target: r.ticket.from, body, confidence: r.analysis.confidence, sourceText: r.ticket.body });
        if (d.action === 'drop') continue;
        const p = createProposal(db, { kind: 'reply', target: r.ticket.from, body, confidence: r.analysis.confidence, sourceRef: r.ticket.id });
        if (d.action === 'auto') approve(db, p.id, { auto: true });
        console.log(`${d.action === 'auto' ? '⚡ 自动批准' : '• 待审批'} ${p.id} → ${p.target}（${d.reasons.join('；')}）`);
      }
      break;
    }
    case 'list':
      for (const p of listProposals(db, values.status as Status | undefined)) {
        console.log(`${p.id}  ${p.status.padEnd(9)} ${p.target}  ${(p.final_body ?? p.body).slice(0, 40).replace(/\n/g, ' ')}`);
      }
      break;
    case 'show':
      console.log(getProposal(db, arg ?? '') ?? '没有这条提案');
      break;
    case 'approve':
      approve(db, arg ?? '', { editedBody: values.edit });
      console.log(`已批准 ${arg}，执行 send 发出`);
      break;
    case 'reject':
      if (!values.reason) throw new Error('拒绝时请写 --reason，它是改进提示词最好的材料');
      reject(db, arg ?? '', values.reason);
      console.log(`已拒绝 ${arg}`);
      break;
    case 'send':
      console.log(await drainOutbox(db, sender));
      break;
    case 'expire':
      console.log(`作废 ${expireStale(db)} 条`);
      break;
    default:
      console.log(HELP);
  }
} catch (err) {
  console.error(err instanceof ConflictError ? `✗ ${err.message}` : err);
  process.exitCode = 1;
} finally {
  db.close();
}

测试拦的是
批准两次只发一条状态检查缺失或幂等键随机生成，导致重复发送
改写后批准发出去的是模型的原稿，而不是人改过的版本
偶发失败会重试一次网络抖动就让提案失败
响应丢失后重试"其实已送达"的消息因为重试被发了两遍
重试用尽后可再批准失败的提案卡死，人无法重新处理
崩溃恢复重启后自动重发"可能已经发过"的消息，或者提案永远卡在 executing
拒绝后不能批准状态机允许了不该有的箭头
默认需要审批 / 敏感词 / 频率上限策略在没有显式授权时自动放行；护栏被绕过

为什么"改状态为 approved"和"写入发件箱"必须放在同一个数据库事务里？

  1. 为了让代码更短
  2. 否则进程可能在两步之间崩溃：状态显示已批准，但要发的消息没有记下来（或者反过来），系统进入不一致的状态
  3. 因为 SQLite 不支持多条语句
  4. 为了让发送更快
这就是事务性发件箱模式要解决的问题：业务状态的变化和"要通知外部"这件事必须原子地一起成立。发件箱之后的投递是"至少一次"，所以接收方需要按幂等键去重——两半合起来，才得到"效果上恰好一次"。

8 · 进阶挑战

  1. 撤回：给已发出的消息加一个 24 小时内可撤回的动作（需要发送接口支持按 remote_id 撤回），撤回本身也是一条要记录的事件。
  2. 后台发送器：写一个常驻进程，每隔几秒 drain 一次发件箱，并处理 SIGTERM——退出前等正在发的那条完成。
  3. 放权建议：统计某个对象最近 30 条提案的"原样批准率"，超过阈值时生成一条"要不要对他开启自动批准"的设置提案——它本身也要审批。
  4. 草稿被取代：同一张工单有了新消息、生成新草稿时，旧的 pending 提案自动作废。
  5. 审批卡片：把审批入口从命令行换成一个本地网页或你常用的聊天工具的交互卡片，后端仍然只调用 approve()、reject()。

9 · 常见坑

  • 先 SELECT 判断、再 UPDATE：两个请求同时读到 pending，都"批准"成功。状态判断必须写在 UPDATE 的 WHERE 里。
  • 在事务里调用外部接口：网络请求可能很慢，会长时间锁住数据库。事务里只做本地读写，外部调用放在事务之外。
  • 幂等键用随机 UUID：每次重试都是新键，对方无法去重。键必须由"这条消息是什么"决定。
  • 崩溃后自动重发：只有当你确定对方支持幂等键时才安全。不确定时，交给人决定。
  • 拒绝不写理由：拒绝理由是 P4 反思、P6 评测最宝贵的数据，CLI 里强制要求填写。
本项目要点
  • 一切对外动作皆提案；"自动"只是提案被策略自动批准，走的是同一条路径。
  • 状态迁移只用一个函数，判断写在 UPDATE 的 WHERE 里，靠影响行数判断成败。
  • 事务性发件箱 + 幂等键 = 效果上恰好一次。
  • 结果未知（发送中崩溃）时不自动重发，交给人；同一个幂等键保证人再批准也不会重复。
  • 默认人工审批；自动批准要显式开启、通过全部护栏，并记下判断理由。
