人在回路与自主度

一个替你处理邮件、日程和工单的 agent，最先遇到的不是"它够不够聪明"，而是"我敢不敢让它替我发出去"。这一章讲怎么把"人"设计进系统：哪些动作必须经你批准，审批界面怎样才不会沦为走过场，以及怎样随着信任积累一格一格地放权。

约 40 分钟前置：第 1、4 章含 1 个分步动画、2 个交互、3 道小测
学完你能
  • 用"提案模式"设计 agent 的对外动作，保证系统里不存在"直接发"的代码路径
  • 设计一张不会被"无脑批准"的审批卡，并把用户的改写与拒绝变成学习信号
  • 用"动作 × 对象"的信任矩阵按风险分级放权，并写出升级与降级规则
  • 为自动模式配齐护栏，并用期望成本判断"这件事值不值得打扰用户"
  • 在 OpenAI Agents SDK、LangGraph 这类框架里正确实现中断与恢复

1 · 为什么"人"必须是架构的一部分

对外动作和普通工具调用有三点本质差异，决定了它们不能像"查一下日历"那样随手执行：

  • 不可撤回或撤回有代价。邮件发出去就被读了，日程改了别人就收到通知了。即使系统支持撤回，对方也可能已经看见。
  • 它代表的是你。agent 发出的每句话，在收件人眼里都是你说的。语气不对、承诺了做不到的时间，损失的是你的信用。
  • 错误代价不对称。少回一封"收到"几乎没有成本；对客户错报一个价格可能很贵。同一个准确率，放在不同动作上意义完全不同。

所以"要不要人工审批"不是一个产品开关，而是一个按动作风险分配控制权的架构问题。第 1 章介绍的五级自主度（Feng、McDonald、Zhang，《Levels of Autonomy for AI Agents》，v2 2025-07-28）给了我们描述它的语言：

等级用户角色用户能做什么典型动作
L1操作者 Operator主导每一步，agent 按指令执行高风险场景，如转账、签约
L2协作者 Collaborator共同规划，随时可以接管结对写文档、写代码
L3顾问 Consultantagent 主导，用户只能给反馈agent 写方案，你提意见
L4审批者 Approver预设审批条件，只批有后果的动作回复邮件、建工单、改日程
L5旁观者 Observer只看日志，必要时紧急停止自动回"收到"、整理归档

论文强调了一个容易被忽略的观点：自主度是设计选择，与模型能力无关。一个能力很强的模型也完全可以运行在 L4。同时作者把 L4 的一个核心难题列为开放问题：如何避免审批变成走过场。这正是本章大部分篇幅要解决的。

OWASP ASI09：人对 agent 的过度信任

OWASP 在 2025-12-09 发布的 Top 10 for Agentic Applications 里，把 "Human-Agent Trust Exploitation" 列为第 9 项：agent 给出一段头头是道的解释，审批人看着有理就点了"批准"。攻击者（或者只是模型自己的幻觉）可以利用这一点，让危险动作带着"合理的理由"通过审批。审批界面的设计本身就是安全边界。

2 · 提案模式：系统里不存在"直接发"

最重要的一条架构约束只有一句话：一切对外动作皆提案（Proposal）。模型永远不直接调用"发送邮件"；它只产出一个"建议发送这封邮件"的提案对象，落库，等待策略或用户做决定。执行器只读取状态为 approved 的提案。

这样做的好处是全局性的：

  • 审批、自动执行、撤回走同一条路。所谓"自动模式"只是"提案被策略自动批准"，而不是另一条绕过审批的代码路径。代码审查时只要盯住执行器一个入口。
  • 天然可审计。每个对外动作都有提案记录：依据哪条消息、模型给了几个选项、谁批的、改了什么、执行结果如何。
  • 天然可学习。"原样批准 / 改写后批准 / 拒绝 / 我自己回了"本身就是最高质量的反馈数据（第 13 章评测会用到）。

落到代码，提案是一个普通的领域对象，状态机由代码维护（状态迁移的完整细节见第 10 章）：


export type ProposalKind = 'reply' | 'create_task' | 'update_event' | 'send_external_email';
export type ProposalStatus = 'pending' | 'approved' | 'executing' | 'done' | 'failed' | 'rejected' | 'expired';

export interface Proposal {
  id: string;
  kind: ProposalKind;
  target: { personId: string | null; conversationId: string };
  options: string[];            // 模型给出的候选（如两个不同语气的草稿）
  evidence: string[];           // 依据的消息 ID，审批卡上可跳转原文
  confidence: number;           // 模型自评，只作为护栏之一，不作为唯一依据
  status: ProposalStatus;
  autoApproved: boolean;
  chosen: { index: number; text: string | null; reason: string | null } | null; // 用户改写与理由
}

// 执行器只有一个入口，只接受 approved；没有"直接发"的函数
export async function executeApproved(p: Proposal, deps: Deps): Promise<void> {
  if (p.status !== 'approved') throw new Error(`提案 ${p.id} 状态为 ${p.status}，拒绝执行`);
  const text = p.chosen?.text ?? p.options[p.chosen?.index ?? 0];
  await deps.store.transition(p.id, 'approved', 'executing');
  try {
    await deps.sender.send({ to: p.target, text, idempotencyKey: `proposal:${p.id}` });
    await deps.store.transition(p.id, 'executing', 'done');
  } catch (err) {
    await deps.store.fail(p.id, String(err)); // 回到可重试状态，由人决定，见第 10 章
  }
}

在代码库里搜索所有"发送类"API 的调用点（发邮件、发消息、改日程、建工单），每一个都必须只出现在执行器里。任何在分析、工具循环或回调里直接调用的地方，都是绕过审批的后门。

3 · 审批界面：让"批准"是一次真正的判断

如果审批卡只显示一段草稿和一个"发送"按钮，用户在第三十张卡时一定会开始无脑点批准。走过场的审批比没有审批更危险——它给了系统"有人把关"的错觉。好的审批卡要让判断又快又真：

要素为什么反模式
原文摘录 + 跳转链接用户要判断的是"这样回对不对"，必须看到对方原话，而不是模型的转述只给模型写的摘要——摘要本身可能就是错的
依据与不确定点模型应列出它拿不准的地方（"不确定报价是否含税"）一段自信流畅的解释（ASI09 的温床）
多个候选两个不同语气的草稿让用户做"选择题"，比判断一段文本对不对更快只有一个草稿，不对就只能拒绝
改写后发送大多数时候草稿"差一点"，改一个词就能发只能批准或拒绝，导致用户为了省事批准不完美的草稿
风险标记命中敏感词、对象是外部、首次联系，用醒目的标记提醒放慢所有卡长得一样，高风险卡淹没在日常卡里
可选的拒绝理由"太正式了""这个不用回"是可以直接写进规则的反馈拒绝就是拒绝，没有信息量
失效机制用户已经亲自回复了，卡片应自动作废，避免重复发送旧卡一直挂着，几小时后被误点批准
把改写当作最好的训练数据

用户对提案的四种处理，信息量从低到高：原样批准（模型做对了）＜ 拒绝（不该这样做）＜ 改写后批准（差在哪里一目了然）＜ 用户绕过卡片自己回复（最真实的"标准答案"）。即时用法是把最近的改写对（改前 / 改后）作为起草示例直接放进上下文；定期用法是让模型从一批信号中归纳"稳定的偏好"，生成一条同样需要审批的"修改偏好"提案。注意：被新提案取代而作废的、和原样批准的，都不应当作负面信号。

你的审批卡上线一个月后，数据显示 98% 的卡被原样批准，平均停留时间 1.2 秒。最合理的解读是？

  1. 模型已经足够好，可以把所有动作都改成自动执行
  2. 用户很满意，不需要任何改动
  3. 审批很可能已经流于形式：应该按动作与对象拆开看数据，把真正低风险的格子放权，让剩下的卡更少、更值得认真看
  4. 应该增加更多确认弹窗，强迫用户认真阅读
1.2 秒连原文都看不完。整体放权会把高风险动作一起放出去；加弹窗只会让用户更快地连点。正确做法是按格子（动作 × 对象）分析：给"对同事回'收到'"这类格子放权，减少卡片总量，让剩下的卡片（对外部、带金额、首次联系）重新获得注意力。

4 · 信任矩阵：按"动作 × 对象"一格一格放权

"这个会话开自动回复"是一个太粗的开关：同一个会话里，"收到"和"报价是 X 元"风险完全不同；同一个动作，对同事和对外部客户也不同。更好的建模是一个二维矩阵：

  • 行是动作：简短应答（"收到""好的"）、实质性回复、创建任务、修改日程、发外部邮件……
  • 列是对象：上级、同事、外部联系人、没有档案的陌生人……（对象由人物档案判断，见第 6 章）
  • 每格一个等级：
等级含义对应自主度
L0 不碰连提案都不生成—
L1 出卡生成提案，等你批准（所有格子的默认值）审批者
L2 做了记账自动执行，进日报"替你做了什么"，一段时间内可撤回旁观者（有通知）
L3 静默做自动执行，不单独通知，日报里只计数旁观者

升级与降级规则

放权应该由数据驱动、由人确认，而不是让 agent 自己给自己升级：

  • 升级建议：某格在观察窗口内（例如 30 天）有足够多已有结论的卡（例如 ≥ 10 张），原样批准率达到阈值（例如 ≥ 90%），且没有撤回记录 → 生成一张"这类事以后直接做？"的设置卡。批准这张卡才真正改格子；被拒绝的格子在一个窗口内不再提。
  • 降级：用户撤回了一条自动执行的动作 → 那一格立即降一级，不需要询问，并在撤回回执里说明。收紧权限可以单方面做，放宽权限必须经同意。
为什么收和放不对称

错误放权的代价（对外说错话）远高于错误收权的代价（多看几张卡）。不对称规则让系统在出错后迅速回到安全状态，同时把每一次放权都变成一次显式的、可追溯的人类决定。

动手：信任矩阵模拟器

点格子在 L0–L3 之间切换，调整护栏，然后看下方事件流的处理结果。自动执行的事件可以点"撤回"，观察对应格子被降级。

信任矩阵 + 护栏模拟器
点击格子循环切换：L0 不碰L1 出卡L2 做了记账L3 静默做

在模拟器里，你把"简短应答 × 同事"设为 L3，但事件"同事在群里说'大家周会改到周四'"仍然被出卡了。最可能的原因是？

  1. L3 只对私聊生效
  2. 群聊消息没有点名你，触发了"群聊须点名我"的护栏，自动执行被降级为出卡
  3. 置信度永远达不到阈值
  4. 模拟器坏了
矩阵决定"最高能放到哪一级"，护栏决定"这一次能不能真的自动"。任何一条护栏不通过，自动执行都要降级为出卡而不是直接丢弃——提案仍然存在，只是需要你看一眼。

5 · 自动模式的护栏

即使某一格已经放权，每一次自动执行之前仍要逐条检查护栏。护栏是确定性代码，不是提示词里的一句"请谨慎"：

护栏防的是什么
全局暂停开关出事时一键止血，所有自动执行立即回到出卡
会话 / 发件人白名单放权只在明确选定的范围生效，新会话默认不自动
群聊须被点名群里大多数消息不是对你说的，自动插话很尴尬
置信度阈值模型自己拿不准时交给人；但置信度只能作为之一，模型对错误也可能很自信
频率上限防止失控循环刷屏（例如每会话每小时最多 N 条）
静默时段深夜自动回复既不像本人，也容易在无人监督时出错
敏感词钱、合同、审批、人事、密码类话题一律交给人，同时检查入站消息和草稿两侧
疑似机器人对话对方也是自动回复时，两个 agent 会互相回复形成乒乓，必须检测并停止
特殊来源永远审批例如"告诉需求方任务已完成"这类交付通知，内容事关承诺，不进自动化

type Level = 0 | 1 | 2 | 3;
type Decision =
  | { kind: 'drop' }
  | { kind: 'card'; failed: string[] }       // 出卡等审批，记录未通过的护栏
  | { kind: 'auto'; notify: boolean };       // L2 通知记账，L3 静默

export function decide(p: Proposal, ctx: PolicyContext): Decision {
  const level: Level = ctx.matrix.get(actionOf(p), objectOf(p, ctx.people)) ?? 1;
  if (level === 0) return { kind: 'drop' };
  if (level === 1) return { kind: 'card', failed: [] };

  const failed: string[] = [];
  if (ctx.paused) failed.push('全局暂停');
  if (!ctx.allowConversations.has(p.target.conversationId)) failed.push('会话不在白名单');
  if (ctx.isGroup && !ctx.mentionedMe) failed.push('群聊未点名');
  if (p.confidence < ctx.minConfidence) failed.push(`置信度 ${p.confidence} 低于阈值`);
  if (ctx.autoCountLastHour(p.target.conversationId) >= ctx.maxPerHour) failed.push('超过每小时上限');
  if (ctx.inQuietHours(ctx.now)) failed.push('静默时段');
  if (hitsKeywords([...ctx.inboundTexts, ...p.options], ctx.denyKeywords)) failed.push('命中敏感词');
  if (ctx.botPingPongSuspected) failed.push('疑似机器人对话');

  return failed.length ? { kind: 'card', failed } : { kind: 'auto', notify: level === 2 };
}

两个细节：护栏失败时把原因写进日志和卡片（"本可自动，但命中敏感词"），用户才能理解系统的行为；自动执行的只取第一个候选，多选一本来就是人的工作。

6 · 什么时候值得打扰用户

人在回路还有另一面：agent 主动找你（推送提醒、请求确认、追问）也是在消耗你的注意力。打扰太多，用户会关掉通知；打扰太少，重要的事被漏掉。这是一个有几十年研究积累的问题。

  • Horvitz 的混合主动原则（CHI 1999）：自动动作应该按期望效用来权衡——收益乘以"用户真的需要"的概率，减去打扰的成本；拿不准时，发起一次简短的澄清，而不是猜。
  • Amershi 等《Guidelines for Human-AI Interaction》（CHI 2019）的 18 条准则里，与此直接相关的有：G3 根据情境把握服务时机；G15 鼓励细粒度反馈；G18 系统行为变化时通知用户（比如"我从今天起会自动回复这类消息"）。
  • 主动式 agent 的评测：ProactiveBench（ICLR 2025）以"用户是否接受"作为主动提示是否成功的标准；ChatGPT Pulse（2025-09-25）采用夜间异步研究、次日推送卡片、用 👍/👎 调整的形式。

2026 年的 PRISM 工作把这件事形式化成一个清晰的阈值规则：估计两个概率——用户需要帮助的概率 pneed、用户接受这次打扰的概率 paccept——再结合误报成本 CFA（打扰了但没必要）和漏报成本 CFN（该提醒没提醒）：

打扰 ⇔ paccept ≥ τ = CFA / (CFA + pneed · CFN)

直觉：漏报越贵、越可能被需要，门槛越低；误报越贵，门槛越高。论文报告这种做法把误报率从 50.22% 降到 22.94%。拖动下面的滑块感受一下：

落到工程上的几条做法
  • 分级推送：紧急的立刻推送，普通的攒进早晚两次简报，纯通知类只进日报。
  • 用户不在时换策略：休假或开会期间只推送高紧急度的卡；对私聊里在等你答复的人，可以发一条开启时由你确认过正文的占位回复（每人一次），其余攒着；回来时一张交接简报告诉你发生了什么。
  • 把打扰也记成数据：被直接忽略、被立刻关闭的推送，是在告诉你阈值设低了。

7 · 框架里的中断与恢复

审批意味着 agent 的执行会停下来等人，可能是几秒，也可能是几天。这对实现提出了两个要求：状态能持久化；恢复时不会把已经做过的副作用再做一遍。主流框架的做法：

在工具上声明 needsApproval（布尔值或异步函数），运行到这个工具时不执行，而是出现在 result.interruptions 里；人做决定后调用 state.approve() / state.reject()，再把状态交回 run 继续。


import { Agent, run, tool, RunState } from '@openai/agents';
import { z } from 'zod';

const sendEmail = tool({
  name: 'send_email',
  description: '给指定收件人发邮件',
  parameters: z.object({ to: z.string(), body: z.string() }),
  needsApproval: async (_ctx, { to }) => !to.endsWith('@example.com'), // 外部收件人才需审批
  execute: async ({ to, body }) => mailer.send(to, body),
});

const agent = new Agent({ name: '办公助理', instructions: '…', tools: [sendEmail] });
let result = await run(agent, '把月报发给客户');

if (result.interruptions.length) {
  // 等待可能很久：把状态序列化后存到服务端（快照本身不带鉴权，不能交给客户端）
  await db.saveRun(runId, result.state.toString());
}

// ……用户在界面上点了批准之后：
const state = await RunState.fromString(agent, await db.takeRun(runId)); // 原子地取出并删除，防止重放
for (const item of state.getInterruptions()) state.approve(item);
result = await run(agent, state);

官方文档特别提醒：序列化的快照没有鉴权，应保存在服务端，并且原子地消费，防止同一次批准被重放两次。审批人的身份要从你自己的登录会话里取，不能相信请求体里自报的身份。还要注意：原子消费只防止"同一个快照恢复两次"，并不保证工具的副作用恰好执行一次——发邮件这类工具自己仍要带幂等键（第 10 章）。

在节点里调用 interrupt() 暂停，需要配置 checkpointer 和 thread_id；恢复时传入 new Command({ resume: 值 })。


import { interrupt, Command } from '@langchain/langgraph';

async function approveAndSend(state: State) {
  // ⚠️ 恢复时整个节点会从头重跑：interrupt 之前的代码会再执行一遍
  const decision = interrupt({ draft: state.draft, to: state.to }); // 第一次运行到这里暂停
  if (decision.action !== 'approve') return { status: 'rejected' };
  await mailer.send(state.to, decision.text ?? state.draft, { idempotencyKey: state.proposalId });
  return { status: 'sent' };
}

// 恢复：
await graph.invoke(new Command({ resume: { action: 'approve', text: null } }), {
  configurable: { thread_id: threadId },
});

三个必须知道的坑：

  • 恢复时整个节点从头重跑。所以 interrupt() 之前不要放副作用；非放不可的必须幂等，或者挪到单独的节点里。
  • 不要用 try/catch 包住 interrupt()。它靠抛出特殊异常实现暂停，被吞掉就不会暂停。
  • 同一节点多次 interrupt 的顺序必须稳定。恢复值是按调用顺序的下标匹配的，条件分支里时有时无的 interrupt 会导致答案对错位置。

如果你的系统本身就是"提案落库 + 执行器轮询"的结构（第 2 节），审批天然就是异步的：agent 的那一轮在生成提案后就结束了，不需要"挂起的执行"。用户批准只是一次数据库状态更新，执行器下一拍拾取。

这种结构最简单、最可靠——没有需要序列化的调用栈，也没有"恢复时重跑"的问题。代价是 agent 不能在同一次推理里等到审批结果再继续推理；需要"批准后继续做后续步骤"时，把后续步骤建模成由"提案完成"事件触发的新一轮。

12-Factor Agents 里的两条原则说的正是这件事：Contact humans with tool calls（联系人类也是一次结构化输出）与 Launch/Pause/Resume with simple APIs。

在 LangGraph 的一个节点里，你先调用了 createTicket() 建工单，再调用 interrupt() 等用户确认是否通知客户。用户确认后会发生什么？

  1. 从 interrupt 那一行继续，一切正常
  2. 图会报错，因为节点里不能有副作用
  3. createTicket 被跳过，因为框架记得它执行过
  4. 整个节点从头重跑，createTicket 被再调用一次——如果它不幂等，就会多出一张重复工单
恢复的语义是"重跑整个节点，在 interrupt 处返回恢复值"。解决办法：把建工单挪到前一个节点，或者给它一个幂等键（例如由线程 ID 派生），保证重跑时服务端识别为同一次请求。

8 · 反模式清单

  • "自动模式"是另一条代码路径：审批路径和自动路径各写一套，迟早有一边漏了检查。应该只有一个执行器。
  • 让 agent 决定自己的权限：模型输出"这条可以自动发"并被直接采纳。放权建议只能生成待审批的设置卡。
  • 护栏写在提示词里："不要在深夜自动回复"应该是一行时间判断，而不是一句请求。
  • 把置信度当唯一依据：模型的自评置信度不可靠，只能和其他确定性护栏一起用。
  • 按会话一刀切：给整个会话开自动，等于把这个会话里所有动作的风险一起放出去了。
  • 撤回不影响权限：撤回是最强的负面信号，不降级就等于告诉系统"错了也没关系"。
  • 审批卡永不过期：情况已经变化（对方追问、你亲自回复了）的卡还能被批准，会造成重复或过时的回复。
真实项目复盘

本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

  • N6 · niuma 7 天推 238 张卡，真正点过的只有一成
  • D7 · devtask 的授权卡上看不到将要执行的指令
  • D8 · devtask 授权后，话题里任何人都能经模型驱动编码 agent
本章要点
  • 对外动作按风险分配控制权；自主度是设计选择，与模型能力无关。
  • 一切对外动作皆提案：模型只产出提案，执行器只读 approved，自动执行是"被策略批准"，不是另一条路径。
  • 审批卡要展示原文、依据与不确定点，支持多选与改写，防止 ASI09 式的过度信任；改写与拒绝是最好的学习信号。
  • 信任矩阵按"动作 × 对象"分级（L0–L3），默认全 L1；升级由数据建议、人来批准，撤回立即降级。
  • 护栏是确定性代码，任一不通过就降级为出卡；打扰用户要按期望成本决策。
  • 框架中断恢复时要特别注意副作用的幂等与状态的安全保存。
