LangGraph：检查点、中断与持久执行

"人在回路"喊起来容易，难的是：agent 跑到一半停下来等人，等了三天，进程早就重启过好几次，人点了"同意"之后它要从哪里接着跑、哪些事不能再做一遍？LangGraph 把这个问题做成了运行时的核心。读它的源码，是理解持久执行（durable execution）最直接的路径。

2 · 为什么读它

第 10 章讲过持久执行的几个基本要素：状态外置、步骤可重放、副作用幂等、可以暂停等待外部事件。大多数团队是在业务代码里零散地实现这些要素的。LangGraph 把它们收拢成一个运行时，并且在源码里把每一个边界情况都写清楚了：

  • 状态怎么存：不是存"变量"，而是存每个 channel 的值和版本号，外加"每个节点看过哪个版本"。
  • 停在哪里：只在超步之间落检查点；一个超步里已经完成的节点，它的写入会作为待定写入（pending writes）单独保存。
  • 恢复时做什么：已经有写入的任务不再执行，没有写入的任务（比如被中断的那个）从头再跑。

理解了这三点，你就能回答第 8 章留下的问题：等人审批这几天里，什么会被重做、什么不会。

5 · 关键设计逐个拆

5.1 超步：写入只在步与步之间生效

它怎么做：主循环非常短，源码里有一段注释说清了规则——第 N 步的 channel 更新只在第 N+1 步可见，一个超步内 channel 是不可变的。


# Channel updates from step N are only visible in step N+1
# channels are guaranteed to be immutable for the duration of the step,
# with channel updates applied only at the transition between steps.
while loop.tick():
    for task in loop.match_cached_writes():
        loop.put_writes(task.id, task.writes, cached=True)
    for _ in runner.tick(
        [t for t in loop.tasks.values() if not t.writes],
        timeout=self.step_timeout,
        get_waiter=get_waiter,
        schedule_task=loop.accept_push,
    ):
        ...
    loop.after_tick()

为什么这样设计：这是 Pregel 的批量同步并行（BSP）模型。好处有三个：并行节点之间不会出现读写竞态；每个超步边界都是一个天然的、一致的检查点位置；同一个超步里谁先跑完都不影响结果，执行是确定的。代价是：并行节点想基于彼此的结果做事，必须等到下一个超步。

对应课程：第 10 章"确定性外壳"——把不确定的模型调用关进节点里，节点之间的推进完全由运行时确定。

5.2 channel 与 reducer：并发写入的规则写在类型上

它怎么做：StateGraph 把状态类型的每个字段变成一个 channel（state.py#L1855）。普通字段是 LastValue，一个超步里收到两个值会直接报错：


def update(self, values: Sequence[Value]) -> bool:
    if len(values) == 0:
        return False
    if len(values) != 1:
        msg = create_error_message(
            message=f"At key '{self.key}': Can receive only one value per step. Use an Annotated key to handle multiple values.",
            error_code=ErrorCode.INVALID_CONCURRENT_GRAPH_UPDATE,
        )
        raise InvalidUpdateError(msg)
    self.value = values[-1]
    return True

写成 Annotated[list, operator.add] 的字段则被识别为 BinaryOperatorAggregate（state.py#L1909），多个并行节点的写入用这个操作符合并。想绕过 reducer 直接覆盖，要显式写 Overwrite(...)（types.py#L1132）。

为什么这样设计：并发写同一个字段时"谁赢"是个必须回答的问题。LangGraph 的选择是：默认不允许，要合并就在类型上声明怎么合并。错误在第一次并发写时就暴露出来，而不是变成一个偶发的"消息丢了一条"。

对应课程：第 10 章的状态机设计；第 3 章"把约束写进类型和 schema，而不是写进说明"。

5.3 检查点里存了什么

Checkpoint 是一个 TypedDict（checkpoint/base/__init__.py#L93），关键字段只有几个：

字段含义
id唯一且单调递增，可以直接用来排序
channel_values各 channel 的值
channel_versions各 channel 的版本号，单调递增
versions_seen每个节点看过每个 channel 的哪个版本——下一步该跑谁，就靠它和 channel_versions 比较
updated_channels这一步更新了哪些 channel

元数据 CheckpointMetadata（L39）里的 source 取值有四种：input（调用的输入）、loop（循环内部）、update（手动改状态）、fork（从别的检查点复制）。step 在第一个 input 检查点是 -1，第一个 loop 检查点是 0。

本仓库内置的 checkpointer 有：InMemorySaver（libs/checkpoint）、SqliteSaver / AsyncSqliteSaver（libs/checkpoint-sqlite）、PostgresSaver / AsyncPostgresSaver，以及只保留最新检查点的 ShallowPostgresSaver（libs/checkpoint-postgres）。接口只有五个方法，换存储不动业务代码。

时间旅行：get_state_history（main.py#L1529）列出一条线程的历史检查点；update_state（L2636）在某个检查点上手动改状态，会生成 source 为 update 或 fork 的新检查点。这让"从第 3 步换个答复重来一次"成为一等操作，评测和调试都用得上（第 13 章的回放）。

5.4 interrupt：为什么恢复时整个节点重跑

它怎么做：interrupt() 本身不保存"执行到哪一行"。Python 没法把一个函数执行到一半的栈帧可靠地持久化下来，所以 LangGraph 选择了另一种做法：给每次 interrupt() 调用编号，答复按编号存下来；恢复时重新执行整个节点，执行到第 N 次 interrupt() 时直接返回第 N 个答复。


scratchpad = conf[CONFIG_KEY_SCRATCHPAD]
idx = scratchpad.interrupt_counter()
# find previous resume values
if scratchpad.resume:
    if idx < len(scratchpad.resume):
        v = scratchpad.resume[idx]
        ...
        return validated
# find current resume value
v = scratchpad.get_null_resume(True)
if v is not None:
    ...
    return validated
# no resume value found
raise GraphInterrupt((Interrupt(value=value, id=..., response_schema=...),))

函数的文档字符串也写得很明确：恢复后"从节点开头执行，重新执行所有逻辑"；一个节点里有多个 interrupt 时，按它们在节点里的顺序匹配答复；而且必须配 checkpointer 才能用。

由此推出三条工程规则：

  1. 中断之前的副作用会被重做。在 interrupt() 之前发邮件、扣款、建工单，恢复时都会再来一次。
  2. interrupt() 的调用顺序必须稳定。不要把它放在依赖外部可变数据的条件分支里，否则答复会对不上号。
  3. 不要用宽泛的 try/except 吞掉 GraphInterrupt，否则中断不会发生。

最稳妥的做法是把副作用放进独立的节点：审批节点只负责 interrupt()，发送节点在下一个超步执行。已经完成的超步落进了检查点，恢复时不会再执行；即便发送节点本身失败重试，也只需在这一个节点里用幂等键防重（第 10 章）。下面的模拟器让你亲手看到区别。

5.5 durability：什么时候真正写盘

它怎么做：Durability = Literal["sync", "async", "exit"]（types.py#L101），调用时用 durability= 参数指定，默认是 "async"（main.py#L2715）。

模式源码里的行为适合
sync每个超步结束后，主循环等检查点写完才进下一步（main.py#L3106）步骤之间有昂贵或不可逆的副作用，崩溃后绝不能丢一步
async（默认）检查点在下一步执行的同时异步写入；任务写入照常即时保存大多数场景：几乎不损失性能，崩溃时最多丢正在写的那个检查点
exit只在图退出时保存；循环内不保存任务写入（_loop.py#L535 的条件）短小、可整体重跑的图；追求吞吐

没有 checkpointer 却传了 durability，会收到"不起作用"的警告（main.py#L2930 附近）。

对应课程：第 10 章"持久化的粒度是一种取舍"；第 14 章的延迟与成本。

一个容易记错的默认值

研读版本里，默认的递归上限（超步数上限）DEFAULT_RECURSION_LIMIT 是 10007，可以用环境变量 LANGGRAPH_DEFAULT_RECURSION_LIMIT 改（_internal/_config.py#L42）。很多旧教程里写的是更小的数字。这类默认值以你用的版本的源码为准——这本身就是读源码的价值。

6 · 值得借鉴 / 不宜照搬

值得借鉴不宜照搬
只在明确的边界（超步之间）落检查点，边界内的部分结果作为待定写入单独存——恢复语义清晰如果你的流程只有三五个固定步骤，一张状态表加幂等键（第 10 章）就够了，不必引入图运行时
并发写入的合并规则写在类型上，冲突第一时间报错"整个节点重跑"对写节点的人要求很高，团队里每个人都得懂这条规则，否则副作用会被悄悄重做
checkpointer 接口只有五个方法，存储可替换它是运行时，不是 agent 框架；仓库自己也说写 agent 属于更上层的 harness
检查点带来时间旅行与分叉，调试和评测都能复用检查点会保存完整状态，包括消息原文；隐私数据要考虑存在哪、保留多久

7 · 对照复盘

两个真实项目里的对应问题
  • D12 · devtask 用轮询和内存状态感知变化，话题的"忙碌"只存在内存里，丢一个结束信号最长 1 小时才失效；启动前崩溃的任务没有对账。LangGraph 的做法正好相反：状态全部外置在检查点里，进程随时可以死，用同一个 thread_id 就能接着跑。
  • N15 · niuma 遇到对方拒收，一天重试了三千多次。LangGraph 的节点有 RetryPolicy，但"哪些错误该重试"仍需你自己定义——运行时给了重试的位置，没给重试的判断。

8 · 读码练习

练习 1：同一个超步里有两个并行节点 A、B，A 成功、B 调用了 interrupt。恢复时 A 会再执行吗？

不会。A 完成时写入已经通过 put_writes 存为待定写入；恢复后 tick() 把待定写入重新应用到成功的任务上（_loop.py 的 _reapply_writes_to_succeeded_nodes），主循环只执行 not t.writes 的任务，所以只有 B 重跑。看 _loop.py#L483、#L692，main.py#L3086。

练习 2：两个并行节点同时往一个普通字段 status: str 写值，会发生什么？怎么改？

报 InvalidUpdateError，错误码 INVALID_CONCURRENT_GRAPH_UPDATE（channels/last_value.py#L56）。要么让两个节点写不同字段，要么把字段标注成 Annotated[类型, reducer] 声明合并方式。

练习 3：为什么 interrupt() 必须配 checkpointer？

答复要按调用编号存起来，恢复时要读回中断前的状态和其他任务的待定写入，这些都存在 checkpointer 里。没有它，"恢复"就无处可读。看 types.py#L983 的文档字符串和 #L1099 之后的实现。

练习 4：把 durability 设成 exit，进程在第 5 个超步崩溃，重启后会从哪里继续？

exit 模式下循环内不保存检查点和任务写入（_loop.py#L535、#L1338 的条件），只在图退出时保存。崩溃前的进度都没落盘，只能从上一次正常退出时的检查点开始。这就是 exit 只适合"可整体重跑"的图的原因。

审批节点里先调用 send_email() 通知审批人，再调用 interrupt() 等批准。人批准恢复后，审批人会收到几封通知？

  1. 1 封，LangGraph 会记住已经发过
  2. 0 封，恢复时跳过中断前的代码
  3. 2 封，恢复时整个节点从头重跑，中断前的 send_email 又执行了一次
  4. 取决于 durability 模式
文档字符串原文："The graph resumes from the start of the node, re-executing all logic." 运行时不知道你的哪一行是副作用。把通知放进中断之前的独立节点，或者给 send_email 加幂等键。

下面哪件事是 durability="sync" 相比默认的 "async" 额外保证的？

  1. 节点不会被重试
  2. 进入下一个超步之前，上一个超步的检查点一定已经写完
  3. 副作用只会执行一次
  4. interrupt 不需要 checkpointer
sync 模式下主循环在 after_tick() 之后等待 _put_checkpoint_fut 完成（main.py#L3106）。它保证的是"检查点先于下一步"，不保证副作用幂等——那仍然是你的责任。
本章要点
  • LangGraph 是 Pregel 式运行时：节点在超步里并行执行，写入只在步与步之间生效，检查点落在超步边界。
  • 状态是一组带版本号的 channel；并发写入的合并规则写在类型上（LastValue 拒绝并发，reducer 声明合并）。
  • 任务一完成就存待定写入，恢复时已完成的任务不重跑；被中断的节点从头重跑，interrupt() 按调用顺序取回答复。
  • 副作用要放在独立节点或做成幂等；不要放在 interrupt() 之前，不要吞掉 GraphInterrupt。
  • durability 默认 async；sync 换更强的落盘保证，exit 换吞吐。
