读这类材料的规矩

闭源产品的分析很容易被当成事实传来传去。本章按来源性质分三档：官方 以官方文档和工程博客为准；社区·运行时 是抓包或运行时日志直接看到的提示词与请求，可信但会随版本变化；社区·推断 是对混淆代码命名、内部阈值的推断，或者只有一个来源的说法。与官方冲突时一律以官方为准，第 5 节专门列出了冲突。

4 · 精华逐条拆

4.1 单线程主循环：把复杂度放在 harness，不放在编排

它怎么做：只有一个主线程、一份扁平的消息历史。需要分解任务时，靠任务清单和子 agent，而不是多个 agent 互相传话。用户可以在 agent 工作时插话，消息会在当前这批工具调用结束后被读到（官方文档的"queue messages"）。

依据：官方 运行原理文档描述的就是这个循环。社区·运行时 MinusX 抓包后的第一条结论就是"Keep Things Simple"：一个主循环、最多一个分支、一份消息历史。社区·推断 PromptLayer 一文里流传很广的内部代号 "nO""h2A"，来自对混淆代码的逆向，不是官方命名，没有学习价值。

为什么有效：可调试。出问题时只有一条轨迹要读。这正是第 11 章 Cognition"写操作保持单线程"的观点。

对应：第 4 章 · 第 11 章

4.2 工具分层：常用操作做成专用工具，长尾交给 Bash

它怎么做：同时提供低层（Bash、Read、Write）、中层（Edit、Grep、Glob）和高层工具（子 agent、WebFetch、退出计划模式）。明明有 Bash，为什么还要单独的 Grep？MinusX 的解释是：使用越频繁的操作，越值得做成专用工具以提高准确率；罕见场景再让模型写 bash。

依据：社区·运行时 MinusX（2025-08，工具列表来自抓包）。官方 工具文档按文件、搜索、执行、Web、代码智能五类组织；《Writing effective tools for agents》（2025-09-11）讲的"少而精、语义化返回、可执行的错误信息"在这里都有体现。

细节：工具描述本身就是提示词，而且很长。抓包看到的工具定义写满了"什么时候用、什么时候别用"，还带正反例（比如"用绝对路径，别 cd"）。一篇社区分析社区·推断 统计，仅 Bash 工具的说明就约 6,500 token，大部分是一份反模式清单。

提示词不是一个字符串：Piebald-AI/claude-code-system-promptsGitHub 仓库 · 从公开 npm 包提取 在每个版本发布后用脚本从编译产物里提取提示词。它的结论是：系统提示由大量按环境和配置条件拼接的片段组成；内置工具各有自己的描述，Explore、Plan 等内置子 agent 各有自己的系统提示；压缩、生成 CLAUDE.md、生成会话标题等辅助功能也各有提示词。合计 500 多段文本，而且几乎每个版本都在变（它维护的变更记录覆盖 v2.0.14 以来的 343 个版本）。启示：提示词是需要版本化、逐版本 diff 的工程资产（第 13、14 章）。本课程不转载这些提示词原文。

编辑策略：一个基于公开源码的分析仓库（how-claude-code-works，见第 5 节）泄露源码 · 单一来源 总结了编辑工具的设计：用"查找并替换"而不是整文件重写，要求被替换的片段在文件里唯一，并且要求编辑前先读过该文件。唯一性约束和先读后改，都是在防模型凭记忆"幻觉式"地改错位置。

对应：第 3 章

4.3 任务清单外置并反复复述

它怎么做：模型用一个工具维护自己的任务清单，UI 把它显示成勾选列表。之后每次调用工具，清单的当前状态都会以 system reminder 的形式回灌进上下文。

依据：社区·运行时 claude-code-reverse 的运行时日志显示，早期版本把清单写成 ~/.claude/todos/ 下的 JSON，并经"system reminder"回灌；MinusX 也看到了这类提醒。官方 2026 年的 hooks 文档里已经有 TaskCreated / TaskCompleted 事件，说明任务清单已经演进为正式的任务工具。具体形态随版本变化，但"外置 + 复述"这个思路没变。

为什么有效：这正是 Manus 说的"复述 todo 对抗目标漂移"（第 5 章）。和让另一个模型做计划、再交给执行者相比，模型自己维护的清单可以中途增删，不会出现交接时信息丢失的问题。

对应：第 5 章 · 第 12 章

4.4 上下文管理是一条管线，而不是一个动作

它怎么做（官方）：

  • 少装：MCP 工具定义默认延迟加载，只有工具名和服务说明占上下文，用到时再经工具搜索取回；Skills 只装描述，正文在调用时才展开。
  • 按需取：代码搜索用 Grep/Glob 这类"像人一样搜"的方式，而不是向量检索（MinusX：LLM search >>> RAG）。
  • 可观察：/context 命令能看到上下文都被什么占着。
  • 压缩：接近上限时自动压缩，可以用 Compact Instructions 指定保留什么；压缩反复失败时停下报错，不无限重试。

社区·推断 那篇基于公开源码的分析还提到两点：系统提示由十几个片段拼成，中间有一个"缓存边界"，之前的内容跨轮稳定、可以命中提示缓存，之后才放会话相关的动态内容；上下文管理分为预算、局部压缩、全量压缩三层。这两点和第 2 章"静态在前、易变在后"的原则一致。how-claude-code-works 仓库（同样基于公开源码）把压缩描述成"4 级渐进式压缩"，Dibia 说是 3 层：两者切分口径不同，结论一致，即先用便宜的手段，最后才动用模型做全量摘要。

对应：第 2 章 · 第 5 章 · 第 7 章

4.5 子 agent：用来隔离上下文，而不是分角色

它怎么做（官方）：每个子 agent 有自己的上下文窗口、系统提示、工具权限和独立的权限设置；默认从零开始，fork 则带着当前对话的副本出发；fork 不能再 fork；不给它子 agent 工具，它就不能继续派生。官方最佳实践也直说了代价：每个子 agent 都单独发请求，token 照算；从零开始的子 agent 还得重新收集主对话已有的上下文，有时反而更慢。

依据：社区·运行时 claude-trace 早期抓到的子 agent 工具描述写着"每次调用无状态""只能回一条最终报告""所以你的任务描述要非常详细，并说清要它返回什么"，而且当时只给它只读工具。这几条至今仍是写子 agent 提示词的好规范。

为什么有效：搜索过程中读过、又被排除的文件，会产生大量和最终结论无关的"脏上下文"。子 agent 把这些隔离在自己的窗口里，主上下文只收下结论。

对应：第 5 章 · 第 11 章

4.6 权限：规则、模式、分类器、沙箱四层叠加

它怎么做（官方）：权限模式定基线，规则叠在上面——deny 规则在包括 bypassPermissions 在内的所有模式下都生效；ask 规则在任何模式下都不会被自动批准；关键路径的 rm 等少数操作永远要问。沙箱则从环境层面兜底：文件隔离加网络隔离，两者缺一不可。官方原话：没有网络隔离，被攻破的 agent 能把 SSH 密钥传出去；没有文件隔离，它能逃出沙箱拿到网络。

两份基于公开源码的分析（Dibia 文章、how-claude-code-works 仓库）泄露源码 都提到，权限与命令安全是代码量最集中的地方之一：Bash 工具的绝大部分代码是安全校验（解析命令结构、识别注入与混淆、判断哪些命令是只读的），仓库把它归纳为"7 层纵深防御"。具体层数和实现属于内部细节，可学的是方向：越接近攻击面的工具，越要把校验做成确定性代码。

4.7 auto mode：用一个"看不见说辞"的分类器替代人工审批

这是 2026 年最值得精读的一篇 agent 安全工程文章（官方，How we built Claude Code auto mode，2026-03-25）。要点：

  • 动机是审批疲劳：用户实际上会批准约 93% 的权限提示，批得越多看得越不仔细。这个数字在《How we contain Claude》（2026-05-25）里再次出现。
  • 两层防御：输入层，一个服务端的提示注入探针扫描工具输出，可疑时在上下文里加警告；输出层，一个对话记录分类器在每个动作执行前审查。
  • 三级过滤：一级是内置的只读工具白名单和用户的 allow 规则（进入 auto 模式时会丢掉"放行任意代码执行"的宽泛规则，比如放行所有 python）；二级是项目目录内的文件编辑，直接放行，因为有版本控制兜底；只有剩下真正有风险的动作才进入三级，交给分类器。
  • 分类器看不到说辞：它只看用户消息和工具调用本身，去掉了 agent 自己的文字和工具结果。去掉文字，是为了不让 agent 用"用户之前默许了"之类的理由说服它；去掉工具结果，是主要的防注入手段。代价是分不清某个参数是查来的还是编的。
  • 两阶段：先用一个快速的单 token 判断，倾向拦截；被拦下的再用带推理的第二阶段复核。真实流量上误拦率从 8.5% 降到 0.4%，代价是在 52 个真实"越权"样本上漏放了 17%。文章把它称为"诚实的数字"，并明确说它不能替代对高风险基础设施的人工审查。

为什么值得学：它示范了一个安全组件该怎么带着评测上线——三个数据集、两项指标、按阶段拆开报告、直说漏放率。这正是第 13 章要求的做法。

对应：第 8 章 · 第 9 章 · 第 13 章

4.8 Hooks：给概率系统装上确定性的扳机

它怎么做（官方）：几十个生命周期事件，分为每会话、每轮、每次工具调用三种节奏。退出码 0 表示放行，并应用输出的 JSON；退出码 2 表示阻断，stderr 作为理由；其他退出码只是非阻断错误，动作照常进行。所以"出错就 exit 1"拦不住任何东西，这是最常见的坑。Stop hook 能阻止 agent 停下，PreToolUse hook 能拒绝或改写工具调用。


#!/bin/bash
# PreToolUse 钩子：输入是 stdin 上的 JSON，Read 的 file_path 已被展开为绝对路径
FILE=$(jq -r '.tool_input.file_path // empty')
case "$FILE" in
  */.env|*/.env.*)
    echo "禁止读取环境变量文件：$FILE" >&2
    exit 2   # 2 才会阻断；exit 1 只是"非阻断错误"，读取照样发生
    ;;
esac
exit 0

注意这个钩子只挂在 Read 工具上，模型照样可以用 cat .env 绕过去。这正是官方把 hooks、deny 规则和沙箱分成不同层的原因：hook 管"在哪个时刻做什么确定性动作"，真正的访问边界要靠规则和沙箱。

对应：第 12 章 · 第 10 章

4.9 CLAUDE.md 与 Skills：分层、按需的指令

它怎么做（官方）：CLAUDE.md 有组织策略、用户、项目、本地等多个层级，每次会话都会载入，适合放"从代码里推断不出来"的约定；它还能读 AGENTS.md。Skills 是带 SKILL.md 的文件夹，会话开始只载入描述，被调用时才展开正文和附带文件，也就是三级渐进披露。auto memory 是 agent 自己写的笔记，启动时只载入开头一部分。

依据：社区·运行时 MinusX 说有没有 claude.md 效果"天差地别"。官方 最佳实践的总前提是：上下文窗口填得很快，而且越满效果越差。所以常驻的指令要短，长的流程放进按需展开的 Skill。

对应：第 5 章 · 第 6 章 · 第 11 章

4.10 headless 与 SDK：同一个循环，换个外壳

它怎么做（官方）：claude -p 以无交互方式运行同一个 agentic loop；--output-format 支持 text、json（含结果、会话 ID 与元数据）和 stream-json（逐行 JSON 事件）；--json-schema 约束结构化输出；--allowedTools 预先批准工具；--bare 跳过 hooks、Skills、插件、MCP、记忆和 CLAUDE.md 的自动发现，让脚本运行可复现。Agent SDK 则是它的库形态。官方文档强调：终端、IDE、网页、CI 背后是同一个循环。

为什么重要：要编排编码 agent，应该走这条程序化的路，而不是去读终端画面。第 12 章和跟练项目 P7 用的就是它。

对应：第 12 章 · P7

社区说法与官方的冲突
  • 压缩时机："约 92% 触发"（PromptLayer）和"约 50% 触发"（Rungta）互相矛盾。官方只说"接近上限时"，并提供手动 /compact 和 Compact Instructions。以官方为准，阈值属于实现细节，会随版本变化。
  • 子 agent 并发：2025 年的分析说"最多一个分支"。官方现在支持后台运行的子 agent 和 fork，最佳实践还专门讨论了"子 agent 的成本"。
  • 提示词规模：MinusX（2025-08）抓到的系统提示约 2,800 token、工具定义约 9,400 token；2026-04 的分析给出的是系统提示约 1.9 万 token。这不是谁错了，而是同一个产品在 8 个月里的变化。Piebald 的变更记录显示提示词几乎每个版本都在变。引用这类数字时一定要带上日期和版本号。

6 · 值得借鉴 / 不宜照搬

  • 笨循环 + 厚 harness：主循环保持简单，工程投入放在工具安全、上下文预算、错误恢复和权限上。
  • 每条自动恢复路径都要有上限：官方的"压缩反复失败就停下报错"，和社区分析提到的那次事故，讲的是同一件事。
  • 安全靠环境，不只靠模型：《How we contain Claude》把防御分成环境、模型、外部内容三部分，并说明凭据从不进入沙箱。
  • 分类器只看动作，不看说辞：任何"让模型审另一个模型"的设计，都应该去掉被审方的自我辩护。
  • 任务清单外置 + 复述、子 agent 隔离脏上下文、常驻指令短、长流程按需展开。
  • 安全组件带着评测上线：报误拦率和漏放率，按阶段拆开，直说不足。
  • 长提示词和大量 IMPORTANT：Claude Code 的提示词很长，但它背后有海量遥测和评测在支撑每一条。小团队照搬这种写法，只会得到第 5 章说的"if-else 式提示词"。MinusX 自己也提醒：要写决策算法，别堆一锅"要/不要"。
  • "大部分动作可以放行"：编码 agent 的动作大多在本地，有快照和 git 可以回滚。替你对外发消息的 agent，发出去的东西撤不回来，审批基线必须更严（第 8 章）。
  • "不用向量检索"：代码结构化、术语稳定，grep 很好用。聊天记录、中文文档、同义表述多的语料，往往还是需要混合检索（第 7 章）。
  • "笨循环就够了"：这个前提是模型足够强。换成较弱的模型时，往往需要更多脚手架，比如显式的计划步骤和更严格的工具约束。

8 · 读文档练习

练习 1：为什么 deny 规则在 bypassPermissions 下仍然生效，而 allow 规则反而没有作用？

去读 Permission modes 页面"Available modes"表格下面的说明。要点：bypassPermissions 本来就放行一切，allow 规则自然多余；deny 规则代表"无论如何都不许"的硬边界，必须独立于模式存在。这是"放权"和"边界"两件事分开配置的范例，对照第 8 章的信任矩阵。

练习 2：auto mode 的分类器为什么要去掉 agent 自己的文字和工具结果？代价是什么？

读 auto mode 文章"Design decisions"一节。去掉文字，是为了防止 agent 说服分类器；去掉工具结果，是主要的防注入手段。代价是分不清某个参数（比如作业 ID）是查来的还是编的。文章还报告了对比实验：保留这些内容反而让"越权"测试集上的表现变差。

练习 3：用运行时工具观察一次压缩

用 claude-trace 记录一次会话：先让它读几个大文件，再执行 /compact，对比压缩前后发出的请求，看系统提示、消息列表和那段摘要。这是合规、可复现的研究方法：观察的是你自己的流量，不涉及任何泄露的源码。

练习 4：写一个 PreToolUse 钩子，并说出它挡不住什么

照 4.8 节的示意写一个钩子，然后试着用 Bash 的 cat 绕过它。答案：钩子只挂在 Read 上，挡不住 shell。要真正封住，需要 deny 规则加上沙箱的文件隔离。读 Hooks 页面的"Exit code output"表，确认 exit 1 只是非阻断错误。

练习 5：对比两篇相隔 8 个月的分析

MinusX（2025-08）和 Dibia（2026-04）给出的提示词规模差了好几倍。请解释为什么不能说其中一篇错了，并总结引用闭源产品分析时应该记录哪些元数据：日期、版本、方法、来源性质。

练习 6：用 clean-room 实现对照本章

克隆 learn-claude-code，依次读 s01（循环）、s06（子 agent）、s08（上下文压缩）、s03/s04（权限与 hooks），每读完一节回到本章对应的 4.1、4.5、4.4、4.6/4.8，写下"教学实现省略了什么、生产实现多了什么"。例如：教学版的压缩通常只有一级，生产版是从便宜手段到全量摘要的多级管线，还要给反复失败的压缩加上限。

你给 Claude Code 写了一个 PreToolUse hook，检测到危险命令时 exit 1。实际会发生什么？

  1. 命令被阻断，stderr 作为理由告诉模型
  2. 整个会话中止
  3. 记为非阻断错误，命令照常执行
  4. 转入询问用户
官方 hooks 文档的规定：只有退出码 2 才是阻断，其他非零退出码一律是非阻断错误，动作继续进行。要阻断，就用 exit 2，或者输出带 permissionDecision: "deny" 的 JSON。

auto mode 的对话记录分类器审查一个动作时，能看到哪些内容？

  1. 完整对话：用户消息、agent 的推理与说明、工具结果
  2. 用户消息和 agent 的工具调用本身，去掉了 agent 的文字和工具结果
  3. 只有工具调用本身
  4. 只有工具结果
只看工具调用会失去"用户想要什么"这个锚点，连用户明确要求的动作也会被拦；加上 agent 的文字，它又可能被说服；加上工具结果，又给了提示注入可乘之机。官方最终选了"用户消息 + 工具调用"，并给出了对比实验的结论。
本章要点
  • Claude Code 的核心是一个简单的单线程循环，工程量集中在 harness：工具安全、上下文管线、错误恢复、权限。
  • 上下文要"少装、按需取、可观察、会压缩"；子 agent 用来隔离脏上下文，不是用来分角色。
  • 安全分四层叠加：规则、模式、分类器、沙箱；hook 是确定性的扳机，不是访问边界。
  • auto mode 示范了"让模型审模型"的正确姿势：只看动作不看说辞，带着评测上线。
  • 引用闭源产品的分析时，要标出日期和来源性质；与官方冲突时以官方为准。
