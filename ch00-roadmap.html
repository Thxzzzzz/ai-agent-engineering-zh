导论：Agent 工程师的能力版图

在动手写第一行 agent 代码之前，先看清终点：一个能独立设计、交付并长期运维 agent 系统的工程师，到底需要掌握哪些东西，又最常在哪些地方栽跟头。

约 25 分钟前置：无含 1 个分步动画、1 个交互能力地图、2 道小测
学完你能
  • 说清"Agent 工程师"和传统后端工程师、机器学习工程师的分工差异
  • 用九个能力域给自己做一次画像，找到最该补的短板
  • 认出 agent 系统七种最常见的失败形态，并知道每一种在本课程哪里解决

1 · 这是一个什么样的岗位

2023 年以前，"用大模型做产品"基本等于"写一段提示词，调一次接口"。今天的 agent 系统则是一个完整的软件系统：它要常驻运行、读写真实业务数据、替用户做事、出错时能恢复、成本要可控、效果要能证明。这类系统的难点从"模型能不能做到"转移到了"怎么让一个不可靠的决策者在可靠的系统里干活"。

Chip Huyen 在《AI Engineering》（O'Reilly，2025）里把这个新角色称为 AI 工程师：他们不训练基础模型，而是在现成模型之上做应用——评估、提示与上下文、检索与 agent、推理优化、架构与用户反馈。Agent 工程师是其中最偏"系统"的一支：你的主要产出不是模型，而是围绕模型的控制流、工具、状态、护栏和度量。

好消息

Agent 工程的大部分能力是后端工程能力的延伸：状态机、幂等、重试、权限、可观测性都是老朋友。真正新的部分集中在三处：上下文怎么组织（模型只知道你给它看的东西）、不可靠的决策怎么约束（审批、护栏、权限隔离）、概率性的质量怎么度量（评测）。这三处正是本课程的重心。

3 · Agent 系统的七种典型失败

理解一个领域最快的方法，是先看它怎么坏掉。下面跟着一次 agent 运行的生命周期，逐一看失败发生在哪个环节、长什么样、在哪一章解决。

办公助理发送会议通知时接口超时，你的代码捕获异常后把"发送"动作重试了一次，结果参会人收到两封邮件。这属于哪类问题，主要靠什么解决？

  1. 跑偏，靠写更清楚的系统提示
  2. 绕圈，靠降低模型温度
  3. 重复执行副作用，靠幂等键与持久化的动作状态
  4. 成本失控，靠换便宜的模型
超时不等于失败——请求可能已经到达服务端。对有副作用的动作，重试必须带同一个幂等键，由服务端去重；同时把"已批准待发送 / 发送中 / 已发送"记进数据库，重启后不会盲目再发。这是纯工程问题，和模型无关。

4 · 贯穿全课的示例：办公助理 agent

为了让各章的知识落在同一个具体系统上，本课程用一个办公助理 agent作为贯穿示例。它替一位职场用户处理日常事务：

读汇总收件读邮件、工单和会议纪要，按紧急程度生成摘要，"40 封未读里只有 3 封需要你回"。
想提炼待办从"月报导出能不能加个按部门筛选？"里提炼出需求、验收点和需要追问的问题。
写起草回复按用户的语气起草回复和会议改期通知，但默认不自己发。
做审批后执行用户点"批准"后才发信、建任务、改日程；或把开发任务交给编码 agent。
记长期记忆记住同事的职责、用户的沟通习惯、答应过别人的事，并按期跟进。
量持续评测记录每次调用的 trace，用户改过的草稿就是下一批评测用例。

这个示例几乎覆盖了 agent 工程的全部难点：它读的是不可信内容（任何人都能给你发邮件），它能访问私有数据，它还能对外发送——这正是安全研究里说的"致命三要素"（第 9 章）；它是常驻进程，要扛住崩溃与重启（第 10 章）；它要记住人又不能记错（第 6 章）；它的质量是主观的，必须靠评测来度量（第 13 章）。

为什么不直接做一个"什么都能干"的 agent？

一个能自由调用所有工具的大 agent 看起来更"智能"，但它难测、难审计、出了错难归因，还会同时具备致命三要素。12-Factor Agents 的第 8 条"掌控你的控制流"和第 10 条"小而专注的 agent"讲的就是这件事：把确定的部分写成代码，只在真正需要判断的地方用模型。

5 · 怎么学这门课

  1. 先建立心智模型，再碰框架。第一部分全部用手写代码，不依赖任何 agent 框架。Anthropic 的建议是"先直接调用 API；如果用框架，确保你理解它底层的代码"。理解了 loop、工具和上下文之后，任何框架你都能在一天内看懂。
  2. 每部分做一个跟练项目。项目从 100 行的最小 agent 开始，逐步加上结构化输出、审批、记忆、MCP、评测和编码 agent 驾驭器，最后拼成毕业项目。所有项目都用"假模型"离线测试，不需要花钱也能把逻辑测透。
  3. 读 trace，而不是只看结果。每次 agent 表现不对，养成习惯去看它当时拿到了什么上下文、调了哪些工具、收到了什么结果。评测领域的共识是：错误分析（亲手读真实 trace）是一切改进的起点。
  4. 追一手资料。每章末尾有原始出处。这个领域半年就会有一批新实践，比如 MCP 规范在 2026-07-28 又发布了一个大版本、把协议改成了无状态；课程讲的是原理与权衡，具体参数以原文为准。

关于"该不该一开始就用 agent 框架"，下面哪种说法最符合主流官方建议？

  1. 一定要用框架，自己写 loop 是重复造轮子
  2. 先直接用 API 写清楚 loop 与工具，理解底层后再决定是否引入框架
  3. 框架和手写没有区别，看个人喜好
  4. 永远不要用框架
Anthropic《Building effective agents》明确建议先直接使用 LLM API，并提醒框架会增加抽象层、遮住底层的提示词和响应，让调试更难。这不是反对框架，而是要求你在用之前看得懂它。
本章要点
  • Agent 工程师的核心产出是围绕模型的控制流、工具、状态、护栏和度量，而不是模型本身。
  • 新增的三大能力：组织上下文、约束不可靠的决策、度量概率性的质量。
  • 七种典型失败里大部分是系统设计问题，换更强的模型解决不了。
  • 贯穿示例"办公助理 agent"同时具备读不可信内容、访问私有数据、对外发送三个特征，是练习 agent 工程的理想靶子。
  • 先手写、再框架；每部分做项目；读 trace；追一手资料。
