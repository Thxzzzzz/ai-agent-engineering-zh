1 · 从 ReAct 到原生工具调用

2022 年 Yao 等人的 ReAct 论文（ICLR 2023）提出让模型交替产出 Thought（推理）→ Action（动作）→ Observation（观察）：先想一想，再调用工具，把结果读回来，再想下一步。只用一两个示例，它就在问答和事实核查任务上明显减少了幻觉，在 ALFWorld 和 WebShop 这类交互任务上分别取得 34% 和 10% 的绝对提升。

当年的 ReAct 靠提示词约定格式、用正则解析"Action: search[...]"。今天这套循环已经内置进了模型 API：

ReAct 概念今天的对应物
Thought模型的推理（thinking）或 assistant 消息里的文字
Actionassistant 消息里的结构化 tool_call（工具名 + JSON 参数 + 调用 id）
Observation你回填的 tool 消息（对应调用 id 的执行结果或错误）
"直到得出答案"模型某一轮不再调用工具，只输出文本

格式解析不再是问题，但循环本身仍然是你的代码：停止条件、错误处理、并发、权限、预算，没有一样是 API 替你做的。12-Factor Agents 的第 8 条"掌控你的控制流"说的就是这个。

2 · 共用接口

本课程的代码和跟练项目 P1 都基于下面这组最小接口。它刻意不依赖任何 SDK：真实模型只需写一个适配器把 Anthropic 或 OpenAI 的响应转成这个形状，测试时换成假模型即可。


export type ToolCall = { id: string; name: string; args: unknown };

export type Message =
  | { role: 'system' | 'user'; content: string }
  | { role: 'assistant'; content: string; toolCalls: ToolCall[] }
  | { role: 'tool'; toolCallId: string; content: string; isError?: boolean };

export type ToolSpec = { name: string; description: string; inputSchema: Record<string, unknown> };

export type Usage = { inputTokens: number; outputTokens: number; cachedInputTokens: number };

export interface Model {
  generate(req: { messages: Message[]; tools: ToolSpec[]; signal?: AbortSignal }): Promise<{
    content: string;
    toolCalls: ToolCall[];
    usage: Usage;
    stopReason: 'end' | 'tool_use' | 'max_tokens' | 'refusal';
  }>;
}
  • ToolCall.args 是 unknown：模型给的东西在校验之前不可信，类型上就要逼你先校验。
  • tool 消息靠 toolCallId 对应到某次调用；isError 告诉模型"这次没成功"。
  • stopReason 区分四种结束：正常结束、要调用工具、被截断、拒答。后两种需要单独处理。

4 · 完整实现

先定义工具的形状。和第 3 章一样用 Zod 描述参数，同时标注它有没有副作用：


import * as z from 'zod';
import type { ToolSpec } from './types';

export interface ToolContext {
  signal: AbortSignal;       // 合并了用户取消与单工具超时
  idempotencyKey: string;    // 有副作用的工具必须把它传给下游服务
}

export interface Tool<S extends z.ZodType = z.ZodType> {
  spec: ToolSpec;
  schema: S;
  mutates: boolean;          // 发信、改日程、建任务等会改变外部世界的工具
  run(args: z.infer<S>, ctx: ToolContext): Promise<string>;
}

export function defineTool<S extends z.ZodType>(def: {
  name: string; description: string; schema: S; mutates: boolean;
  run: (args: z.infer<S>, ctx: ToolContext) => Promise<string>;
}): Tool<S> {
  const { $schema: _ignored, ...inputSchema } = z.toJSONSchema(def.schema) as Record<string, unknown>;
  return { spec: { name: def.name, description: def.description, inputSchema }, schema: def.schema, mutates: def.mutates, run: def.run };
}

然后是 loop 本身。逐段看注释：


import * as z from 'zod';
import type { Tool } from './tool';
import type { Message, Model, ToolCall, Usage } from './types';

export interface RunOptions {
  runId: string;               // 用来派生幂等键
  maxSteps?: number;           // 默认 12
  maxInputTokens?: number;     // 整个任务的输入 token 预算
  toolTimeoutMs?: number;      // 单个工具的超时，默认 30 秒
  maxResultChars?: number;     // 单条工具结果上限，默认 6000 字
  signal?: AbortSignal;        // 用户取消
  onEvent?: (e: AgentEvent) => void;  // 接到 trace（第 14 章）
}

export type AgentEvent =
  | { type: 'model'; step: number; usage: Usage; toolCalls: ToolCall[] }
  | { type: 'tool'; step: number; call: ToolCall; ok: boolean; ms: number };

export interface RunResult {
  text: string;
  usage: Usage;
  steps: number;
  mutated: boolean;            // 是否执行过有副作用的工具：决定了失败后能不能整体重来
  hitStepLimit: boolean;
}

export class AgentError extends Error {
  constructor(message: string, readonly messages: Message[], readonly mutated: boolean) {
    super(message);
  }
}

export async function runAgent(model: Model, tools: Tool[], messages: Message[], opts: RunOptions): Promise<RunResult> {
  const byName = new Map(tools.map((t) => [t.spec.name, t]));
  const specs = tools.map((t) => t.spec); // 顺序固定，利于提示缓存（第 2 章）
  const maxSteps = opts.maxSteps ?? 12;
  const usage: Usage = { inputTokens: 0, outputTokens: 0, cachedInputTokens: 0 };
  let mutated = false;

  const call = async () => {
    opts.signal?.throwIfAborted();
    if (opts.maxInputTokens && usage.inputTokens >= opts.maxInputTokens) {
      throw new AgentError(`超出输入 token 预算（${opts.maxInputTokens}）`, messages, mutated);
    }
    const res = await model.generate({ messages, tools: specs, signal: opts.signal });
    usage.inputTokens += res.usage.inputTokens;
    usage.outputTokens += res.usage.outputTokens;
    usage.cachedInputTokens += res.usage.cachedInputTokens;
    if (res.stopReason === 'refusal') throw new AgentError('模型拒绝执行', messages, mutated);
    if (res.stopReason === 'max_tokens') throw new AgentError('模型输出被截断', messages, mutated);
    messages.push({ role: 'assistant', content: res.content, toolCalls: res.toolCalls });
    return res;
  };

  for (let step = 1; step <= maxSteps; step++) {
    const res = await call();
    opts.onEvent?.({ type: 'model', step, usage: res.usage, toolCalls: res.toolCalls });
    if (res.toolCalls.length === 0) return { text: res.content, usage, steps: step, mutated, hitStepLimit: false };

    const results = await executeCalls(res.toolCalls, byName, step, opts);
    for (const r of results) {
      messages.push(r.message);
      if (r.mutated) mutated = true;
    }
  }

  // 步数用完：工具定义保持不变（不改前缀，缓存照样命中），但明确要求不再调用工具
  messages.push({
    role: 'user',
    content: '已达到步数上限。不要再调用工具，根据目前掌握的信息直接回答，并列出还没完成的部分。',
  });
  const final = await call();
  return { text: final.content, usage, steps: maxSteps, mutated, hitStepLimit: true };
}

执行工具的部分单独拆出来。它的职责是：无论发生什么，都给每个 tool call 产出一条 tool 消息——除非用户取消了整个任务。


type Executed = { message: Message; mutated: boolean };

async function executeCalls(
  calls: ToolCall[], byName: Map<string, Tool>, step: number, opts: RunOptions,
): Promise<Executed[]> {
  const isWrite = (c: ToolCall) => byName.get(c.name)?.mutates === true;
  const done = new Map<string, Executed>();
  // 只读工具互不影响，并行跑；有副作用的工具按模型给出的顺序逐个执行
  const reads = calls.filter((c) => !isWrite(c));
  const outs = await Promise.all(reads.map((c) => executeOne(c, byName, step, opts)));
  reads.forEach((c, i) => done.set(c.id, outs[i]));
  for (const c of calls.filter(isWrite)) done.set(c.id, await executeOne(c, byName, step, opts));
  return calls.map((c) => done.get(c.id)!); // 结果按调用顺序回填
}

async function executeOne(call: ToolCall, byName: Map<string, Tool>, step: number, opts: RunOptions): Promise<Executed> {
  const fail = (content: string, mutated = false): Executed => ({
    message: { role: 'tool', toolCallId: call.id, content, isError: true },
    mutated,
  });
  const tool = byName.get(call.name);
  if (!tool) return fail(`没有名为 ${call.name} 的工具。可用的工具：${[...byName.keys()].join('、')}`);

  const parsed = tool.schema.safeParse(call.args);
  if (!parsed.success) return fail(`参数不合法，请修正后重新调用：\n${z.prettifyError(parsed.error)}`);

  const signals = [AbortSignal.timeout(opts.toolTimeoutMs ?? 30_000)];
  if (opts.signal) signals.push(opts.signal);
  const started = Date.now();
  try {
    const text = await tool.run(parsed.data, {
      signal: AbortSignal.any(signals),
      idempotencyKey: `${opts.runId}:${call.id}`,
    });
    opts.onEvent?.({ type: 'tool', step, call, ok: true, ms: Date.now() - started });
    return { message: { role: 'tool', toolCallId: call.id, content: truncate(text, opts.maxResultChars ?? 6000) }, mutated: tool.mutates };
  } catch (err) {
    opts.onEvent?.({ type: 'tool', step, call, ok: false, ms: Date.now() - started });
    if (opts.signal?.aborted) throw err; // 用户取消：整个任务中止，不再回灌
    const reason = err instanceof Error ? err.message : String(err);
    if (tool.mutates) {
      // 超时或网络错误时请求可能已经生效：不能让模型盲目重试
      return fail(`执行结果未知（${reason}）。该操作可能已经生效，不要直接重试；先用查询工具确认当前状态。`, true);
    }
    return fail(`执行失败：${reason}`);
  }
}

function truncate(text: string, max: number): string {
  if (text.length <= max) return text;
  return `${text.slice(0, max)}\n…（已截断，原文共 ${text.length} 字。请缩小查询范围或翻页）`;
}
为什么错误要回灌而不是抛出？

模型在大多数情况下能自己修正：参数格式不对就改格式，工具不存在就换工具，查不到就换关键词。Manus 团队的经验是"把错误留在上下文里"——模型看到失败的动作和报错，会更新自己的判断，降低重复犯错的概率。12-Factor Agents 的第 9 条"把错误压缩进上下文"也是同样的意思。只有当错误是系统性的（用户取消、预算耗尽、模型拒答）才应该中止整个任务。

5 · 四类工具错误与回灌内容

错误常见原因回灌给模型的内容要点
工具不存在模型凭印象编了个工具名，或用了旧名字列出可用的工具名
参数不合法缺字段、类型错、枚举值写错、多余字段具体字段路径 + 合法值；可附"先调用某工具"的建议
只读工具执行失败 / 超时外部服务抖动、查询太宽失败原因；可以重试或换个查询
有副作用的工具失败 / 超时网络错误、下游 5xx状态未知，不要直接重试，先查询确认（第 10 章用幂等键与动作记录从根本上解决）
工具结果也会"失败"：太长

一次返回几万字的搜索结果不会报错，但会挤爆上下文、稀释注意力（第 2 章的 context rot），还会让后面每一轮都多付这些 token 的钱。截断时告诉模型"已截断、共多少、怎么缩小范围"，比悄悄截掉好得多。Claude Code 的工具返回默认上限是 25,000 token，可以作为一个量级参考。

三个场景各演示一个要点：

  • 正常完成：第一轮模型同时发出两个互不依赖的只读调用，loop 并行执行；之后两次有副作用的调用串行执行。
  • 参数错误回灌：模型把"下周三"直接塞进日期参数，校验失败的具体信息被回灌，模型按提示先解析日期再查询。
  • 绕圈与步数上限：模型反复用相同的关键词搜索，loop 在第 4 步停下，要求它基于已有信息作答。

只读工具 mail_search 调用时外部服务返回 503。loop 应该怎么做？

  1. 抛出异常，结束整个任务
  2. 把"执行失败：503 服务暂时不可用"作为 isError 的 tool 消息回灌，让模型决定重试还是换个办法
  3. 悄悄返回空结果，假装没搜到
  4. 把这次 tool call 从历史里删掉，重新请求模型
只读工具失败没有副作用风险，回灌错误让模型决策即可。返回空结果会让模型得出"没有相关邮件"的错误结论；删历史会破坏 tool call 与 tool 消息的对应关系，也会让模型重复同样的调用。

7 · 并行调用、超时与取消

并行

主流模型可以在一轮里发出多个工具调用，意味着它认为这些调用互不依赖。并行执行它们能显著降低延迟——Anthropic 的多智能体研究系统把子 agent 内部的工具调用改为并行后，复杂查询的耗时最多下降了 90%。实现上要注意：

  • 结果必须按调用 id 一一回填，顺序与调用顺序一致，便于阅读与调试。
  • 只并行只读工具。两个有副作用的调用即使模型认为独立，也按顺序执行——"改日程"和"发通知"同时进行，通知里的时间可能是旧的。
  • 一个调用失败不影响其他调用的结果回填。

超时与取消

每个工具都要有超时，否则一个卡死的外部请求会卡住整个 agent。用 AbortSignal.timeout() 与用户的取消信号合并（AbortSignal.any()），并把信号一路传给 fetch 等下游调用。区分两种中止：单个工具超时回灌给模型；用户取消立即终止整个任务。

8 · 有副作用的工具：最危险的地方

设想这个时间线：模型调用 mail_send → 邮件成功发出 → 下一轮请求模型时 API 返回 500 → 你的代码捕获异常，从头重跑整个任务。结果：邮件发了两次。

这就是 RunResult.mutated 和 AgentError.mutated 存在的原因：

  • 没执行过有副作用的工具：整个任务可以安全地重来，甚至换一个模型重来（第 2 章的回退）。
  • 执行过：不能整轮重试，也不能换模型从头跑。应当从中断处恢复（保存了消息列表就能续上），或者把状态交给人决定。

幂等键 ${runId}:${call.id} 能在同一次运行里防止重复（比如工具内部的网络重试），但如果整个任务重跑，模型会生成新的调用 id，幂等键就变了。真正的保护需要把"要执行的动作"先持久化成一条记录（状态：待执行 → 执行中 → 已完成），用记录 id 作为幂等键——这是第 10 章和跟练项目 P3 的内容。

高风险动作不该由 loop 直接执行

对于办公助理来说，"发邮件给客户"这类动作最好根本不在工具循环里直接执行：工具只负责生成一个待审批的提案（"建议发送以下邮件"），人批准后由独立的执行器带幂等键发出。OpenAI Agents SDK 的工具也提供 needsApproval，让 loop 在执行前暂停等待批准。第 8 章细讲。

agent 已经调用 calendar_event_update 把会议改到了周四，接着请求模型时遇到 API 限流（429）。正确的处理是？

  1. 换一个模型，从用户的原始请求开始重跑
  2. 等一会儿从原始请求开始重跑
  3. 保留当前的消息列表，退避后用同一份历史继续请求模型（续上而不是重来）
  4. 直接告诉用户任务失败，让他手动再发一次请求
已有副作用发生，从头重跑会重复修改（甚至重复通知参会人）。消息列表本身就是 agent 的完整状态（12-Factor Agents 第 5、12 条），保存它就能从断点继续。④会把同样的问题推给用户，他重发一次就是重跑一次。

9 · 历史增长与上下文管理的预告

每一轮都往 messages 追加至少两条消息。一个 20 步的任务，最后一轮的输入可能是第一轮的好几倍。第 2 章的计算器已经展示了成本的超线性增长。loop 层面能做的有：

  • 截断过长的工具结果（上面的 truncate）。
  • 设步数上限与 token 预算，并在任务开始前按复杂度分配预算——Anthropic 建议简单任务 3–10 次工具调用就够。
  • 只追加、不改写历史，保持缓存命中。

更系统的手段——压缩历史、把细节写进文件、子 agent 隔离上下文——属于上下文工程，见第 5 章。

10 · 用假模型离线测试

loop 的大部分逻辑和模型能力无关：错误有没有正确回灌、步数上限是否生效、有副作用的工具会不会被调两次。这些都可以用一个按脚本回复的假模型测试，不花钱、不联网、结果确定。


import type { Message, Model, ToolCall } from './types';

type Reply = Awaited<ReturnType<Model['generate']>>;
type Step = (messages: Message[]) => Reply;

export const say = (content: string): Reply => ({
  content, toolCalls: [], stopReason: 'end',
  usage: { inputTokens: 100, outputTokens: 20, cachedInputTokens: 0 },
});
export const use = (...toolCalls: ToolCall[]): Reply => ({
  content: '', toolCalls, stopReason: 'tool_use',
  usage: { inputTokens: 100, outputTokens: 20, cachedInputTokens: 0 },
});

/** 按顺序返回预先写好的回复；每次收到的消息列表都留档，供测试断言 */
export class FakeModel implements Model {
  readonly seen: Message[][] = [];
  constructor(private readonly script: Step[]) {}
  async generate(req: { messages: Message[] }) {
    this.seen.push(structuredClone(req.messages));
    const next = this.script.shift();
    if (!next) throw new Error('FakeModel 的脚本已用完：loop 比预期多请求了一次模型');
    return next(req.messages);
  }
}

      () => use({ id: 'c1', name: 'calendar_events_search', args: { start_date: '下周三' } }),
      () => use({ id: 'c2', name: 'calendar_events_search', args: { start_date: '2026-12-02' } }),
      () => say('下周三有 2 个会'),
    ]);
    const r = await runAgent(model, [search, send], start(), { runId: 't1' });
    const feedback = model.seen[1].at(-1);
    expect(feedback).toMatchObject({ role: 'tool', toolCallId: 'c1', isError: true });
    expect(feedback && 'content' in feedback && feedback.content).toContain('start_date');
    expect(r.text).toBe('下周三有 2 个会');
  });

  // 拦截：步数上限失效导致死循环，或超限后直接抛错丢掉了所有进展
  test('达到步数上限后要求模型直接回答，而不是继续执行工具', async () => {
    const loop = () => use({ id: crypto.randomUUID(), name: 'calendar_events_search', args: { start_date: '2026-12-02' } });
    const model = new FakeModel([loop, loop, loop, () => say('没找到更多信息')]);
    const r = await runAgent(model, [search], start(), { runId: 't2', maxSteps: 3 });
    expect(r.hitStepLimit).toBe(true);
    expect(r.text).toBe('没找到更多信息');
  });

  // 拦截：有副作用的工具失败后被自动重试，或失败时没有标记 mutated
  test('有副作用的工具失败时不自动重试，并提示模型先确认状态', async () => {
    sent.length = 0;
    const model = new FakeModel([
      () => use({ id: 'm1', name: 'mail_send', args: { subject: '周会改期' } }),
      () => say('发送结果未知，请确认'),
    ]);
    const r = await runAgent(model, [send], start(), { runId: 't3' });
    expect(sent).toEqual(['周会改期']);
    expect(r.mutated).toBe(true);
    const feedback = model.seen[1].at(-1);
    expect(feedback && 'content' in feedback && feedback.content).toContain('不要直接重试');
  });
});
假模型测什么、不测什么

假模型测的是你的代码：控制流、错误处理、状态。它测不了"模型会不会在这种情况下做出正确决策"——那是评测（第 13 章）的工作，要用真实模型、真实或逼真的数据、多次运行看通过率。两者缺一不可，但不要混在一起。

下面哪个测试最没有价值？

  1. 断言系统提示等于某段固定文字
  2. 工具不存在时，回灌的错误消息里包含可用的工具名
  3. 用户取消后 loop 不再请求模型
  4. 超过 token 预算时任务以明确的错误结束
把提示词原样抄进断言，锁住的是实现而不是行为：改一个字测试就挂，但真正的 bug（比如错误没回灌）它一个也拦不住。提示词的效果要靠评测来验证。
真实项目复盘

本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

  • D5 · devtask 的完成判定按子串匹配"完成"，实测 is_completed("未完成") 返回 True
本章要点
  • ReAct 的 Thought/Action/Observation 已内置为原生工具调用，但循环、停止条件、错误处理仍是你的代码。
  • 每轮先检查取消与预算，再调用模型；拒答和截断单独处理。
  • 工具不存在、参数不合法、执行失败都以 isError 回灌，让模型自我修正；只有系统性错误才中止。
  • 只读工具并行，有副作用的工具串行并带幂等键；结果按调用顺序回填。
  • 执行过副作用后不能整轮重试或换模型重跑：保存消息列表，从断点续上。
  • 步数用完时要求模型基于已有信息作答，而不是丢掉一切。
  • 用假模型测控制流，用评测测模型决策。
