复盘：两个真实项目里的知识短板

前面 16 章讲的都是"应该怎么做"。这一章反过来：拿两个真实项目，逐条找出因为缺了哪块知识而走的弯路，再对比"有这块知识时会怎么设计"。这是整门课最值得反复看的一章，因为每一条都真实发生过。

约 50 分钟前置：读完第 1–15 章31 条发现 · 10 条做对的事
学完你能
  • 把课程里的每个知识点和一次真实的返工、事故或隐患对上号
  • 识别两个项目共有的 6 类根因，在下一个项目里提前避开
  • 拿到一份按优先级排好的整改清单，知道先修哪几处

1 · 这份复盘是怎么来的

审计对象有两个：

  • niuma-agent：TypeScript/Bun 写的个人工作消息助理。它读 IM 消息，做分析、出提案，经用户审批后代发、建任务、派发给外部 agent，还有记忆、信任矩阵、知识库编译和对话助手。审计范围是 2026-10-02 至 11-24 的 378 个提交，src 约 8.3 万行，44 份提示词，31 份 ADR。
  • devtask：Python 写的 agent 插件。用户在聊天里提开发需求，插件发授权卡，批准后用 git worktree 启动 Claude Code 等编码 agent，读 git/gh 跟进进度并回写卡片，最后收尾。审计范围是两个月的 146 个提交（其中 64 个是 fix），非测试代码 55 个文件、1.33 万行。

方法：2026-11-25 对照本课程 15 章的知识域只读审计，每条发现都要有证据，即代码位置、提交哈希或文档里记下的事故与日期；只有推测的会注明。几条高严重度的发现我又亲手复核过，比如 devtask 的完成判定，在 Python 里实际运行了 is_completed('未完成')，返回 True。

先说清楚：这不是在否定这两个项目

两个项目都已经自己摸索出了不少业界最佳实践，第 7 节逐条列出。复盘的意义在于算清"缺这块知识"的代价：同一个结论，有知识储备时是第一天的设计决定；没有时，要付出一次事故、几天返工，或者一个至今没被发现的隐患才能学到。

5 · 六类共性根因

31 条发现归并下来，其实只有 6 类根因。每一类都对应课程里的一两章。

根因在两个项目里的表现对应章节
① 让模型做了该由代码做的事devtask：让模型自报"用户已同意"、宣布完成、搬运 ID、充当调度中枢。niuma：一次调用同时出十几个判断。第 1 章 · 第 3 章
② 先扩功能，后建评测niuma：87 个改提示词的提交里，只有 17 个附了回放数据；结清判断没达标就上线。devtask：482 个单测没有一条测 agent 行为。第 13 章
③ 用提示词打补丁niuma：分析提示词里有 53 处"不要/一律/除非"，还写进了具体事故里的业务名词。devtask：SKILL.md 里 59 处同类措辞，升级说明累计 24 条。第 5 章
④ 没有威胁模型两个项目都同时具备"不可信输入 + 私有数据 + 对外动作"（lethal trifecta）。devtask 授权后谁都能经模型驱动编码 agent，权限确认还交给另一个 LLM 代按。第 9 章 · 第 8 章
⑤ 耦合实现而非协议devtask 读终端画面、会话文件和进程环境来判断编码 agent 的状态，contracts.py 的存在本身就说明了这一点；Claude、Orca 相关的修复有 22 个。第 11 章 · 第 12 章
⑥ 可靠性靠事故驱动缓存、超时、熔断、token 预算、端到端 trace，都是出了事才补，或者至今没有。第 10 章 · 第 14 章

devtask 用"状态文本里含不含'完成'"来判断任务是否结束。下面哪种改法最符合本课程的思路？

  1. 把匹配词改成"已完成"，避免误判"未完成"
  2. 在 SKILL.md 里加一条规则："不要写'未完成'"
  3. 状态改成枚举；终态只能由插件根据 PR 合并、CI 通过等可核实条件写入，模型最多提议"请人工 review"
  4. 让另一个模型复核状态文本
选项 1 和 2 都是在补丁上再打补丁，下一个"完成了一半"照样误判。选项 4 用一个不可靠的判断去复核另一个不可靠的判断。根因是"完成"这种有后果的状态由模型的自由文本决定：第 3 章说状态要用枚举，第 12 章说完成要由可验证的条件门控。

niuma 的分析提示词里写进了一串具体的业务名词（来自某次事故涉及的几个业务模块），用来纠正一次值班误判。这种做法最大的问题是什么？

  1. 提示词变长，费用增加
  2. 判例写进提示词，只能覆盖见过的情形，规则越积越多还互相牵制；它应该进评测集，确定性的归属判断交给代码
  3. 模型看不懂中文业务名词
  4. 违反了提示缓存的前缀规则
这正是 Anthropic 说的"if-else 式提示词"，见第 5 章"合适的高度"。判例的正确去处是标注集（第 13 章）；"归不归我们组"这类能确定性判断的事，交给代码去比对职责清单。项目后来确实改成了"摘出职责原文、由代码核对"，方向是对的。

6 · 如果重来：按优先级的整改清单

按"风险 × 修复成本"排序。前 5 条是安全和正确性问题，建议先处理。勾选状态会保存在你的浏览器里。

  • devtask：授权卡显示将要执行的完整指令（或摘要加哈希），执行时校验；指令改了就重新授权。见 D7。
  • devtask：去掉模型自报确认。user_confirmed 这类参数一律改成引用插件记录的消息 ID 或按钮回调。见 D3。
  • devtask：完成判定改成枚举，并由可核实条件门控；先把"未完成会被判成完成"这个现存 bug 修掉。见 D5。
  • devtask：编码 agent 用受限的权限模式；权限请求不交给话题 agent 代按；非创建人的消息只当建议。见 D8、D9。
  • niuma：写一份威胁模型；外发草稿只用本会话上下文；自动派发强制沙箱、出网白名单和最小上下文包。见 N7、N8。
  • niuma：交付证据改为回查 PR 状态与 CI 结果，任意 URL 不再算证据。见 N10。
  • 两个项目：每个 LLM 节点建标注集，30–50 条人工金标；改提示词前后各跑 k=3 次，看 pass^k。见 N4、D13。
  • niuma：瘦身分析提示词，只留 5–7 条原则，判例迁进评测集，把单次分析拆成链。见 N2、N3。
  • niuma：上下文按 token 预算组装，把档案移到静态规则之后，并记录每一节的占比。见 N11、N12。
  • devtask：用 headless/ACP 持有编码 agent 会话，用结构化事件代替读终端和内部文件；定义 CodingAgent 接口。见 D6、D14。
  • 两个项目：通知和发送走 outbox，区分可重试与不可重试，配熔断和死信；启动时做对账。见 N15、D12。
  • niuma：trace 带批次和卡片的关联 id；助手工具按意图分组、按需下发。见 N16、N17。

7 · 已经做对的事

这些是两个项目自己摸索出、与业界最佳实践一致的做法。它们也说明，缺的往往不是工程能力，而是提前知道该往哪里用力。

  • 模型不填长 ID：上下文里用 M/U/R 短编号，由代码映射回真实 ID；回答里的【m3】引用由系统换成跳转链接。这是第 3 章的防呆设计（poka-yoke）。
  • 可靠执行：提案状态机配幂等键，键里含正文（actions.ts:484）；派发前先记"派发中"；重启后把执行中的卡退回待审批，不自动重发（repo/proposals.ts:470）。这是第 10 章的教科书做法。
  • 确定性护栏：read_local_file 只读用户亲手给出的路径；safe-fetch 防止 DNS 解析后换成内网地址；MCP 的只读标注只当提示，另配白名单；执行过写操作的工具循环出错后不换模型重来（tool-loop.ts:48）。
  • 评测基础设施：提示词带版本号；回放按提案时刻截断上下文，防止后来的信息泄进来；新草稿和本人写的话做盲测；有影子提示词。
  • 多 agent 刹车与分级：答复执行方最多两轮、有并发上限、可叫停、回查 60 秒超时；按任务分配模型；主体是 workflow，只有对话助手是 agent loop；ADR 写了推翻条件。
  • 创建人 ID 由插件记录、覆盖模型填的值（plugin.py:77、672，有测试）。这是在一次编造 ID 的事故之后改的，方向完全正确。
  • 审批按钮不进模型，在锁内幂等：第一条有效决定获胜，重开后旧决定作废（service/intake.py:148-187）；确认方案时核对创建人原话，单次有效。
  • 客观读取进度：从 git 和 gh 读提交、PR、CI；自动状态只往前推（progress.py:388-417）；发布到环境分支由插件确定性执行，不经过模型。
  • Stop hook 写得规范：stop_hook_active 时放行，每轮只提醒一次；用 python3 -I 运行，跑 git 时关掉仓库 hook 和 fsmonitor；用真实 Claude Code 验证过。
  • 把隐性依赖显性化：contracts.py 在版本变化时自动核对，doctor 也会检查；缺的能力整理成文档提给上游。另有每个任务的事件日志、看板和 gh_health 记账。
本章要点
  • 两个项目的 31 条发现可以归成 6 类根因：模型越权、评测后置、提示词打补丁、没有威胁模型、耦合实现、可靠性靠事故驱动。
  • 最危险的几条都在授权与执行的边界上：模型自报确认、授权看不到指令、权限请求由另一个模型代按、完成判定用子串匹配。
  • 缺知识的代价，是把"第一天的设计决定"变成了"一次事故之后的补丁"。缓存、超时、熔断、评测，本都该是默认配置。
  • 两个项目已经摸索出不少正确做法：短编号、幂等状态机、客观进度、规范的 Stop hook。缺的主要是提前知道往哪里用力。
