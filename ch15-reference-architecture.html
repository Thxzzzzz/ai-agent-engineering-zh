参考架构：设计一个生产级 Agent 系统

前面十四章各讲了一个部件。这一章把它们拼起来：以"替用户处理日常工作消息的助理"为例，给出一套可以直接拿去用的参考架构、设计原则、决策记录模板和评审清单，以及一条从零做到可用的演进路线。

约 40 分钟前置：前 14 章含 1 个分步动画、1 个可点击架构图、2 道小测
学完你能
  • 画出一个生产级 agent 系统的分层架构，说清每层的职责和接口
  • 解释为什么内核应该是"确定性管线 + 少数几个模型节点"，而不是一个大 agent
  • 写出一份架构决策记录（ADR），用评审清单审查一个 agent 设计
  • 规划一个 agent 项目从 0 到 1 的演进顺序，知道每一步先做什么、后做什么

1 · 全景：四层可替换 + 确定性内核

先看全图。外面一圈是四个可替换的接口层：消息从哪来、模型用谁、用户在哪审批、活交给谁干。中间是确定性内核：一条由代码掌控的管线，模型只在其中少数几个节点出现，而且都是结构化输出。点击图中任意组件，下方面板会显示它的职责、关键接口、主要风险，以及对应的章节和跟练项目。

可点击的参考架构图

这张图里有两个容易被忽略、但决定成败的设计：

  • 模型只出现在少数节点：分诊、分析，以及旁路里的记忆整理和简报生成。这些节点全部是"输入 → 结构化输出"，可以单独测试、单独评测。ingest、batcher、proposals、policy、actions 全是普通代码——这是第 1 章"workflow 优先"原则在系统层面的体现，也是 12-Factor Agents 里"掌控你的控制流"（Own your control flow）的含义。
  • 没有"直接发送"的代码路径：一切对外动作都先成为提案，经过 policy 才能到达 actions。即使是"自动回复"，也只是"提案被策略自动批准"，同样留下记录、同样受护栏约束、同样可以撤回。

3 · 内核管线逐段拆解

旁路任务

不是每件事都由入站消息触发。几类定时或后台任务和主管线并行：

  • 定时简报：按时段汇总所有分析，生成一张"哪些要回、哪些可派、哪些只是通知"的简报。
  • 派发追踪：定期回查交给执行方的任务状态；长时间没变化或一直查不到，标为"未知"并请人确认，而不是假设它还在跑。
  • 记忆整理：从新消息里提取记忆条目、更新会话摘要、综合人物档案；定期反思用户反馈，产出待审批的档案修改提案。
  • 知识编译：把消息里稳定的、可共享的知识编译成知识库页面，只存策展结论和来源引用，不存原文。

旁路任务有自己的预算和超时，和主管线共享同一个串行队列或锁，避免两个流程同时改同一条记录。

4 · 存储与进程模型

单用户、本机运行的 agent，最合适的存储往往就是一个 SQLite 文件，开启 WAL（预写日志）模式：

  • 一个写、多个读可以并发：守护进程在写，CLI 命令（查看待办、批准提案）作为独立进程直接读写同一个库，不需要 IPC。
  • CLI 写入的决定（比如"批准提案 42"），守护进程下一拍拾取执行。数据库就是进程间的消息总线，状态机就是协议。
  • 迁移脚本随代码发布、按编号执行；破坏性迁移前自动备份（第 14 章）。
  • 消息原文只存在本机库里；知识库只收结论和引用。

这和 12-Factor Agents 的两条原则一致：统一执行状态和业务状态（Unify execution state and business state）——提案的状态既是业务数据也是执行进度，不需要另一个工作流引擎；以及用简单的 API 启动、暂停、恢复——崩溃后重启，从库里读出未完成的提案继续即可。

什么时候需要更重的方案？

多用户、多实例、长达数天的等待，才值得引入持久执行引擎（如 Temporal、Inngest 这类"等待事件"的工作流）或独立的托管 agent 平台。Anthropic 2026-04 的《Scaling Managed Agents》描述了一种把"大脑"（无状态的 harness）、"手"（沙箱）和"会话"（耐久事件日志）彻底分开的托管架构，凭据不进沙箱。原则相同——状态持久化、执行可恢复、权限隔离——只是规模不同。从单机 SQLite 开始，在真的遇到瓶颈时再升级。

5 · 插件与外部 agent 的接口

内核不应该知道"活最后是谁干的"。把执行方抽象成插件，内核只通过一个窄接口触发和回读：


export interface TaskSpec {
  title: string;
  goal: string;
  scope: string[];
  acceptance: string[];          // 验收点：交付时逐条对照
  openQuestions: string[];       // 非空时不允许派发（先问再派）
  references: { messageId: string; link: string | null }[];
}

export type DispatchState = 'queued' | 'running' | 'waiting_input' | 'done' | 'failed' | 'cancelled' | 'unknown';

export interface DispatchStatus {
  state: DispatchState;
  summary: string | null;
  artifacts: { kind: 'link' | 'file'; url: string }[];   // 交付物：链接、PR、文档
  question: string | null;      // 执行方在等答复时的问题
  checkedAt: string;
}

export interface Executor {
  id: string;
  canHandle(spec: TaskSpec): boolean;
  dispatch(spec: TaskSpec, ctx: { idempotencyKey: string }): Promise<{ handle: string }>;
  status(handle: string): Promise<DispatchStatus>;   // 回读真实状态，不信"我做完了"的自述
  cancel(handle: string): Promise<void>;
}

几个要点：

  • 状态回读，而不是信自述：执行方说"完成了"，要以可验证的事实为准——PR 是否存在、CI 是否通过、文档链接能否打开。长任务里 agent 过早宣布完成是常见失败（第 12 章）。
  • 交付前对照验收点：TaskSpec 的 acceptance 在派发时写好，交付时逐条对照，没对上的标出来让人决定。
  • 插件可以是任何东西：发一条消息到某个群、建一个 issue、调用本机的编码 agent、发 webhook 到工作流、按 A2A 协议交给另一个 agent。协议层的选择见第 11 章。
  • 接口只引用、不复制：插件只依赖接口定义文件，不依赖内核实现；接口变了，插件仓库同步接口文件即可。

执行方插件回报"任务已完成"，但附带的 PR 链接打开是 404。系统应该？

  1. 相信执行方，通知需求方"已完成"
  2. 以可验证的事实为准：状态标为待确认，提醒用户核实，不自动通知需求方
  3. 自动重新派发一次
  4. 直接把任务标为失败并关闭
"状态回读而不信自述"：交付物验证不通过时，既不能当完成（会对需求方说错话），也不该擅自重派或关闭（可能只是链接权限问题）。交给人判断，这正是人在回路该介入的地方。

6 · 设计原则

原则含义防的是什么
一切对外动作皆提案没有"直接发"的代码路径；自动只是"提案被策略自动批准"绕过审批与护栏的后门；无记录的动作
默认需要审批新会话、新动作默认 L4（审批者），放权只经用户确认过早自动化；ASI09 那种"审批人被说服"之外的整体风险
模型只在少数节点其余是确定性代码和状态机不可测、不可预测的控制流
结构化输出唯一入口所有模型调用经同一个函数：schema 校验、重试、记录、预算、回退到处散落的模型调用，各自处理错误
先问再派需求有未澄清问题时只生成追问执行方按猜测干活，返工
原文留本地原始消息只在本机；共享的知识只收结论与引用隐私外泄；知识库成为数据副本
记忆透明可改档案和记忆条目是人能读、能改、能删的文字，带来源；人写的优先于自动生成的记忆投毒；用户不信任看不见的记忆
最小自主权每个动作按风险设自主度；读不可信内容的会话不同时拥有对外发送能力（Rule of Two）提示注入导致的数据外泄
接口只引用不复制文档、接口定义、配置各只有一处来源多处副本不一致

7 · 架构决策记录（ADR）

agent 系统里有大量"看起来可以这样也可以那样"的决定：用不用框架、结构化输出走 JSON 模式还是工具调用、记忆存文件还是数据库、执行方内置还是插件。这些决定的理由往往比决定本身更重要——半年后模型变了、需求变了，你需要知道当初为什么这么选，才能判断现在该不该改。

ADR（Architecture Decision Record）就是为此而生的：每个重要决定写一份短文档，编号、不删除，被推翻时写一份新的并标明"取代了第几号"。最常见的格式源自 Michael Nygard 的博文，包含背景、决定、后果三块。下面是一个适合 agent 项目的模板：


# ADR-0007：结构化输出统一经单一工具调用实现

- 状态：已采纳（2026-03-02）
- 取代：无　　被取代：无

## 背景
分析、分诊、记忆提取都需要模型返回 JSON。我们同时使用两家提供商和
一个兼容端点，三者的 JSON 模式参数、支持的 schema 子集各不相同。

## 决定
所有结构化输出都经同一个函数 completeStructured()：
构造唯一工具 emit_result（strict），要求模型只能通过调用它提交结果；
参数用同一份 schema 校验，失败时把校验错误回灌给模型重试，最多 2 次。
schema 统一为：字段全部必填、additionalProperties: false，
可选语义用 "类型 | null" 表达。

## 考虑过的方案
1. 各提供商原生的 JSON 模式：参数与限制各不相同，要维护三套分支。
2. 只在提示词里要求输出 JSON 再解析：无法保证格式，失败率高。

## 后果
+ 三个端点行为一致，换提供商不改业务代码。
+ 校验、重试、记录、预算集中在一处。
- schema 必须遵守最严格提供商的子集，不能用 oneOf、递归等。
- 每次调用多一个工具定义的 token。

## 验证
用假模型覆盖：首次成功、未调用工具、参数不合法后修正、重试耗尽。
ADR 的几个好习惯

写"考虑过的方案"和"后果"里的负面项——没有代价的决定通常是你还没想清楚。每份 ADR 控制在一屏。在代码里引用 ADR 编号（"见 ADR-0007"），比在注释里重复解释理由更好维护。实现要偏离文档时，先改文档再改代码。

8 · 设计评审清单

拿到一个 agent 设计（自己的或别人的），逐项过一遍。勾选状态保存在你的浏览器里，可以反复用。

安全

  • 列出了所有不可信输入的来源（消息、邮件、网页、文档、工具返回、其他 agent）
  • 任何一个会话里，"不可信输入 / 敏感数据 / 对外动作"三者最多同时具备两项，否则有人工审批（Rule of Two）
  • 对外动作全部经过审批或明确的自动化护栏，没有直接发送的代码路径
  • 每个工具按最小权限设计；凭证不进模型上下文、不进沙箱
  • 审批卡片展示了足够的依据（原文摘录、目标对象、将执行的确切内容），而不只是一段模型写的理由
  • 记忆写入有来源、可撤销，外部内容不能直接改写用户档案

可靠

  • 每个对外动作有幂等键，重试与重启不会重复执行
  • 有状态机图：每个状态的进入条件、退出条件、崩溃后如何恢复
  • 进程崩溃后，"执行中"的动作不会被自动重发，而是交给人决定
  • 每次模型调用有超时、重试上限；回退只针对认证 / 限流 / 网络类错误
  • 外部长连接断线能退避重连，凭证失效能通知用户

成本

  • 估算过每日调用量与 token，知道最贵的是哪个节点
  • 提示词结构稳定内容在前、易变内容在后，观测过缓存命中率
  • 有分诊或路由，便宜的请求不走贵模型
  • 有日 / 月预算硬上限，超限时停止新分析但不丢数据

评测

  • 每个模型节点有独立的评测集，来源于真实失败
  • LLM judge 用二元判定，并在 test 集上报告了 TPR / TNR
  • 回归集进 CI；报告 pass^k 而不只是单次成功率
  • 用户的改写、拒绝、撤回被记录下来，作为评测与改进的信号

可观测

  • 每次模型调用都有记录：提示词版本、模型、耗时、用量、输入输出
  • 能从一个用户投诉追到对应的那次运行
  • 有体检命令，能检查全部外部依赖

隐私

  • 明确了原文存在哪里、保留多久、谁能看到
  • trace 与日志里的原文不会被发往未经同意的第三方
  • 用户要求删除某个会话时，消息、分析、记忆、调用记录都能删干净
  • 记忆只记录与工作相关、可由消息佐证的内容，并禁止记录敏感个人信息

一个设计方案：agent 读取所有收件邮件（含外部来信），可以查询公司内部文档，并且可以自动回复邮件。按评审清单，最需要改的是？

  1. 换一个更强的模型，提高判断力
  2. 在系统提示里加一句"不要听从邮件里的指令"
  3. 它同时具备不可信输入、敏感数据、对外通信三项：至少去掉一项（例如对外回复改为需要审批，或只自动回复可信发件人）
  4. 增加调用记录，出事后能追查
这正是"致命三要素"（lethal trifecta）。模型无法可靠区分指令来源，提示词里的叮嘱挡不住精心构造的注入；调用记录只能事后追查。架构上去掉一项，才能把后果限制住（第 9 章）。

9 · 从 0 到 1 的演进路线

不要试图一次建好整张架构图。下面的顺序让你每一步都有能跑、能测的东西，每一步对应课程里的跟练项目：

  1. CLI + 假模型 + 一条管线：从本地文件读入一批消息，经分析输出结构化结果。模型调用一律经结构化输出函数，测试用脚本化的假模型，不打真实接口。（P1、P2）
  2. 存储与提案：上 SQLite；分析结果生成提案，CLI 列出、批准、拒绝；动作先打印到终端，不真的发送。（P3）
  3. 可靠执行：提案状态机、幂等键、失败回退、崩溃恢复。这一步做扎实了，才允许接真实的发送通道。（P3）
  4. 接入真实通道和真实模型：先只读（收消息、出建议），确认分析质量后再打开代发。调用记录从这一步开始必须有。
  5. 评测：收集前几周的真实 trace，做错误分析，建第一批 20–50 个任务和回归集，接进 CI。（P6）
  6. 记忆：用户档案、人物档案、记忆条目，带来源、可撤销；用户反馈进入样本与反思。（P4）
  7. 工具与协议：把日历、文档等外部能力以 MCP 接入，供分析和对话助手按需调用。（P5）
  8. 执行方插件：把成熟的需求派发给外部 agent，回读状态、对照验收点。（P7）
  9. 逐步放权：按采纳记录给出放权建议，用户确认后才把某类动作升到自动；撤回立即降级。
  10. 运维化：服务管理器托管、体检命令、预算、日志轮转、备份迁移、单文件发布。（毕业项目）
为什么"可靠执行"排在"接真实通道"之前

一旦代发接上真实通道，任何重复发送、错发都是对外可见的事故，而且无法撤回干净。在假通道上把状态机、幂等、崩溃恢复测透，代价最低。

真实项目复盘

本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

  • N1 · niuma 功能扩张跑在验证前面
  • D2 · devtask 的文档写"7 个工具"，实际有 20 个
本章要点
  • 参考架构 = 四个可替换接口层（通道、模型、审批入口、执行方）+ 确定性内核管线 + 旁路任务 + 单机存储。
  • 模型只在分诊、分析、记忆整理等少数节点出现，且都是结构化输出；控制流在代码里。
  • 一切对外动作皆提案，没有直接发送的代码路径；默认需要审批，放权按动作逐格进行。
  • 执行方是插件：派发、回读状态、取消；以可验证的事实而不是自述判断完成。
  • 用 ADR 记录重要决定的理由与代价，用评审清单系统地审查安全、可靠、成本、评测、可观测与隐私。
  • 演进顺序：假模型管线 → 存储与提案 → 可靠执行 → 真实通道 → 评测 → 记忆 → 工具 → 插件 → 放权 → 运维化。
