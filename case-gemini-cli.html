Gemini CLI：工具系统、MCP 与上下文压缩

Gemini CLI 是 Google 开源的终端 agent，用 TypeScript 写成，和本课的跟练项目同一个语言栈，读起来最顺手。它最值得学的三处：一个按层级和优先级合并规则的策略引擎；一套把"失败"也设计进去的上下文压缩；以及把模型自己可能出的毛病（绕圈、停在半路）当成要监测的对象。

约 45 分钟前置：第 3、5、8、11 章研读版本：08e9a20（2026-11-24）
学完你能
  • 在 Gemini CLI 的 monorepo 里找到主循环、工具调度、策略引擎、压缩、记忆加载各自的文件
  • 讲清它的策略引擎如何把默认、扩展、工作区、用户、管理员五层规则合并成一个"允许 / 拒绝 / 询问"
  • 复述上下文压缩的每一步：何时触发、保留什么、怎么验证、失败时怎么办
  • 给自己的 agent 加上循环检测、按需加载的项目记忆和"无交互时询问即拒绝"

2 · 为什么读它

  • 和你的栈一样：TypeScript、Node 生态、zod，读到的模式能直接搬进 agent-lab。
  • 防御写在了显眼处：策略文件是 TOML，注释里把优先级分层写得清清楚楚；压缩、循环检测的每个阈值都是带注释的具名常量。好的工程习惯本身就是教材。
  • 它承认模型会犯错：绕圈、话说一半就停、压缩时漏掉关键细节，都有专门的代码去检测和兜底。这正是第 4、5、12 章反复强调的"不要相信模型自己说的"。

5 · 关键设计一：分层、按优先级合并的策略引擎

工具能不能执行，由 PolicyEngine 给出三种结论之一（policy/types.ts）：allow、deny、ask_user。规则写在 TOML 文件里，内置的在 packages/core/src/policy/policies/，比如 read-only.toml、write.toml、plan.toml、yolo.toml、non-interactive.toml。

多条规则命中时，取优先级最高的那条。精妙之处在优先级的编码方式，每个内置策略文件开头都有同一段注释：


# Priority bands (tiers):
# - Default policies (TOML): 1 + priority/1000 (e.g., priority 100 → 1.100)
# - Extension policies (TOML): 2 + priority/1000 (e.g., priority 100 → 2.100)
# - Workspace policies (TOML): 3 + priority/1000 (e.g., priority 100 → 3.100)
# - User policies (TOML): 4 + priority/1000 (e.g., priority 100 → 4.100)
# - Admin policies (TOML): 5 + priority/1000 (e.g., priority 100 → 5.100)
#
# This ensures Admin > User > Workspace > Extension > Default hierarchy is always preserved,
# while allowing user-specified priorities to work within each tier.

整数部分是"谁说的"，小数部分是"在同一层里多重要"。这样无论扩展作者把优先级写得多高，都压不过用户；无论用户写得多高，都压不过管理员。用户在界面里点"总是允许"，会落成用户层里的一条高优先级规则（注释里写的是 4.95）。

审批模式：同一套规则，按模式开关

ApprovalMode 有四档，按宽松程度排列为 plan → default → autoEdit → yolo（常量 MODES_BY_PERMISSIVENESS 就是这个顺序，注释要求：宽松模式下必须允许所有严格模式下允许的工具）。规则可以用 modes = [...] 指定只在某些模式下生效：

  • write.toml：replace（编辑）工具默认 ask_user（优先级 10）；在 autoEdit 模式下改为 allow（优先级 15），但同时挂一个 allowed-path 安全检查器，限制只能改允许的路径。
  • yolo.toml：* 一律允许（优先级 998），但 ask_user 这个"向用户提问"的工具仍然是询问（999）。
  • non-interactive.toml：无交互时 ask_user 工具直接拒绝。更关键的是引擎本身：nonInteractive 为真时，没有规则命中的默认结论从"询问"变成"拒绝"（policy-engine.ts:332）。

shell 命令的额外检查

工具级规则管不到命令内容，所以 applyShellHeuristics 会先解析命令，再按顺序检查。下面这几种情况会把结论强制改成"询问"：

情形为什么
命令的工作目录不在工作区内（yolo 除外）越界操作，默认需要人看一眼
在不受信任的目录里执行 git 命令仓库里的 git hooks、配置本身就能执行任意代码，陌生仓库里跑 git 等于运行它的代码
命令被判定为危险（yolo 下保留原结论）与 Codex 的危险命令启发式同理
"已知安全"的命令里含有未展开的 shell 变量或替换源码注释："分类器看到的是展开前的文本，替 bash 会改写的参数担保不了"
可迁移的经验：分类器要知道自己看不到什么

"含未展开的变量就不替它担保"是一个很好的思维方式：你的安全判断基于什么输入，输入在执行前还会不会变？会变，就不要放行。第 9 章讲的 TOCTOU（检查时与使用时不一致）在 agent 里非常常见，比如审批时看到的是草稿，发送时用的是另一个版本。

6 · 关键设计二：确认不只是"是 / 否"

工具确认的结果是一个枚举 ToolConfirmationOutcome：

选项含义对应课程概念
proceed_once只批准这一次标准审批
proceed_always / proceed_always_and_save本次会话内总是允许 / 并保存成持久规则第 8 章：按采纳记录逐步放权
proceed_always_server / proceed_always_tool信任整个 MCP 服务器 / 这个工具放权的粒度
modify_with_editor用编辑器改了参数再执行第 8 章：改写后再发
cancel取消拒绝

这几个选项覆盖了第 8 章讲的审批界面的全部要素：批准、拒绝、改了再批、按粒度放权。还有一点值得注意：确认请求走的是 MessageBus（confirmation-bus/），调度器和界面之间只交换消息。同一套确认流程因此可以同时服务交互界面、无交互入口和 ACP 客户端，三者只是对消息的处理方式不同。

7 · 关键设计三：把失败也设计进去的上下文压缩

ChatCompressionService 是本页最值得逐行读的一个文件。它的关键常量都在文件开头附近：

常量值含义
DEFAULT_COMPRESSION_TOKEN_THRESHOLD0.5历史超过模型上下文上限的 50% 就压缩
COMPRESSION_PRESERVE_THRESHOLD0.3压缩后保留最近 30% 的历史原文
COMPRESSION_FUNCTION_RESPONSE_TOKEN_BUDGET50,000保留部分里工具输出的 token 预算
RECENT_TURNS_PROTECTED3最近 3 个带工具输出的回合必须原样保留

压缩流程（简化后的顺序）：

  1. 逆序预算截断：从最新往最旧数工具输出的 token，超过 5 万之后，更旧的大块工具输出只保留最后若干行，全文另存为临时文件，历史里只留截断后的版本和文件位置。这就是 Manus 说的"压缩要可恢复"（第 5 章）。
  2. 找切分点：findCompressSplitPoint 按字符数找到前 70% 的位置，并且只在"用户发的、不是工具结果"的消息处切，保证不会把一次函数调用和它的结果切开。
  3. 生成状态快照：把前 70% 交给模型，生成一个 <state_snapshot>。如果历史里已经有上一次的快照，提示词会要求"必须把旧快照里仍然有效的信息合并进新的"，避免多次压缩后信息逐渐流失。
  4. 自我核对：再跑一轮："批判性地检查你刚写的快照，是否漏了具体的技术细节、文件路径、工具结果或用户约束？有就输出改进后的最终版，没有就原样重复。"
  5. 失败判定：摘要为空，或者压缩后的 token 数比原来还多，就判压缩失败、保留原历史，并记一个具体的失败状态（COMPRESSION_FAILED_EMPTY_SUMMARY、COMPRESSION_FAILED_INFLATED_TOKEN_COUNT 等）。
上下文压缩模拟器

每点一次"再来一回合"，历史里加一条用户消息、一条模型回复和一次工具输出（大小随机）。阈值、保留比例和工具输出预算取自源码；每条消息的大小和快照的大小是示意值。

红线 = 50% 阈值
用户模型工具输出已截断（全文存文件）状态快照
点"再来一回合"开始；历史超过红线时会自动压缩。

压缩后的 token 数反而比压缩前多，Gemini CLI 会怎么做？

  1. 照样用压缩后的历史，因为摘要的信息密度更高
  2. 重新压缩一次，直到变小为止
  3. 删除最旧的一半历史
  4. 判定压缩失败，保留原历史，并记录失败状态 COMPRESSION_FAILED_INFLATED_TOKEN_COUNT
压缩的目的就是变小。变大说明摘要质量有问题（比如模型把历史又复述了一遍），此时最安全的做法是不采用。这体现了一个通用原则：任何由模型产出、要替换原始数据的东西，都要有一个确定性的验收条件，过不了就回退。

8 · 关键设计四：监测模型自己的毛病

循环检测

checkToolCallLoop 把每次工具调用（名字加参数的 JSON）做 SHA-256 哈希，存入一个滑动窗口，然后检查最近的调用里是否存在长度为 1 到 5 的循环节，连续重复了 5 次（TOOL_CALL_LOOP_THRESHOLD = 5）。比如同一个调用连续 5 次，或者"读 A、读 B"交替出现 5 轮。

除了工具调用，它还检测流式文本里重复出现的内容块，而且在代码块里关闭这项检测，因为重复的代码结构很常见，并不意味着在绕圈。一个回合超过 30 轮之后，还会定期请模型判断"是不是陷入了循环"，置信度达到 0.9 才认定；检查间隔在 5 到 15 轮之间，按上一次判断的置信度动态调整。

循环检测器（按源码算法复刻）

点按钮模拟模型发出的工具调用。同名同参数视为同一个调用。

"话说一半"检查

模型有时会说"接下来我要运行测试"然后就停了，没有真的发起调用。checkNextSpeaker 用一次结构化输出判断下一位该谁说话（next_speaker 只能是 user 或 model）：如果上一条回复声明了要做的下一步，或者明显没说完，就判 model，客户端自动发一句"Please continue."。

注意：这个检查在当前版本里默认是跳过的（配置项 skipNextSpeakerCheck 默认为 true）。这本身也是一课：它多花一次模型调用，换来的收益取决于模型的毛病有多严重。随着模型变强，这类脚手架就成了第 12 章说的"不再承重的组件"，可以默认关掉，但保留开关。

9 · 关键设计五：记忆按需加载，MCP 按信任接入

GEMINI.md 层级记忆

启动时加载四类记忆，按类别分别拼接：global（~/.gemini/ 下）、extension、project（从每个受信任的根目录往上找，到 git 根为止）、userProjectMemory。更值得学的是 loadJitSubdirectoryMemory：读写文件、列目录这类"高意图"工具访问某个子目录时，才把那里的 GEMINI.md 加进来。前提是这个路径在某个受信任的根目录之内，否则直接跳过。

这就是第 5 章 just-in-time 检索和第 11 章 Skills"渐进披露"在项目记忆上的应用：monorepo 里每个子包都可以有自己的说明，但只有 agent 真的进入那个子包时才占用上下文。

MCP 接入

  • 命名空间：MCP 工具在模型面前的名字是 mcp_{服务器名}_{工具名}（MCP_TOOL_PREFIX = 'mcp_'），策略规则可以写成 服务器名__* 这样的通配，一次管住整个服务器。
  • 按信任启用：当前目录不受信任时，stdio 方式的 MCP 服务器不会启动，报错提示"use 'gemini trust' to enable it"。stdio 服务器就是在你机器上跑一个本地进程，陌生项目里配置的服务器不能自动运行。
  • 工具过滤：每个服务器可以配 includeTools / excludeTools，排除优先于包含。这正是复盘里 N17"工具面太宽"的直接解法之一。

检查点与 ACP

  • 检查点（默认关闭）：开启后，编辑、写文件这两类工具（EDIT_TOOL_NAMES）进入等待批准状态时，GitService.createFileSnapshot 往一个与用户仓库隔离的影子 git 仓库提交一次快照，/restore 可以把文件和对话一起回到那一刻。用影子仓库而不是用户自己的仓库，避免污染用户的提交历史。
  • ACP：--acp 启动时，CLI 通过 stdin/stdout 上按行分隔的 JSON-RPC 与编辑器通信，实现在 packages/cli/src/acp/（会话管理、提示执行、权限请求、文件系统访问都是协议里的结构化消息）。这就是第 11 章讲的"编辑器 ↔ 编码 agent"协议的一个真实实现。

10 · 值得借鉴 / 不宜照搬

值得借鉴不宜照搬
规则分层：整数位表示来源、小数位表示层内优先级，保证"管理员 > 用户 > 工作区 > 扩展 > 默认"永远成立沙箱默认关闭：对通用终端 agent 是体验取舍，但你的 agent 如果会执行模型生成的命令，默认应该更保守（对照 Codex）
无交互时，没有规则命中的默认结论从"询问"变成"拒绝"大量具名常量阈值：它们是针对特定模型调出来的，换模型后要用自己的评测重新校准，不要照抄数值
压缩：逆序预算截断并落盘、按消息边界切分、合并旧快照、自我核对、膨胀即失败"话说一半"检查：多一次模型调用，先确认你的模型确实有这个毛病再加
按哈希加循环节检测绕圈；在代码块里关闭文本重复检测以免误报
项目记忆按子目录按需加载；不受信任的目录里不启动本地 MCP 进程

11 · 对照复盘

和两个真实项目的对照
  • N12 上下文只按条数截断，没有 token 预算：Gemini CLI 的压缩以 token 计（阈值是上下文上限的比例），工具输出有单独的 token 预算，超出部分截断并落盘，压缩前后都计 token 并在膨胀时回退。按"最近 40 条"截断回答不了"现在有多满"。
  • N17 助手工具面太宽：Gemini 给每个 MCP 服务器配 includeTools / excludeTools，用命名空间加通配符整体管理，项目记忆也按子目录按需加载，而不是每轮把所有东西都发给模型。
  • D6 没用程序化协议：Gemini CLI 自带 ACP 和 stream-json 输出，外部程序应该通过它们驱动和观察 agent。

12 · 读码练习

练习 1：用户在界面里对某个工具点了"总是允许"，这条规则落在哪一层？为什么它压不过管理员策略里的 deny？

要点：看任一内置策略 TOML 的文件头注释：界面里的 Always Allow 落在用户层 4.95；管理员策略在 5.x。最终优先级 = 层号 + priority/1000，所以用户层无论写多高都低于 5。规则合并逻辑在 packages/core/src/policy/policy-engine.ts。

练习 2：findCompressSplitPoint 为什么只在"不含函数结果的用户消息"处切分？在别处切会怎样？

要点：函数调用（模型消息）和函数结果（用户角色消息）必须成对出现。如果在二者之间切，压缩后的历史里会出现没有调用的结果或没有结果的调用，下一次请求会被 API 拒绝或让模型困惑。看 context/chatCompressionService.ts 第 380 行起的实现，以及末尾"能否把全部历史都压缩"的判断：最后一条必须是没有函数调用的模型消息。

练习 3：工具调用序列 A B A B A B A B A B，第几次调用时会被判定为循环？如果是 A B C A B C……呢？

要点：循环节长度 k=2 时需要 k×5=10 次，所以第 10 次调用时命中；k=3 时需要 15 次。算法在 services/loopDetectionService.ts 的 checkToolCallLoop：对 k=1..5，取最近 k 个哈希作为循环节，向前检查 k×5 个位置是否完全匹配。可以用上面的检测器验证。

练习 4：无交互模式下，一个没有任何规则命中的工具调用会得到什么结论？在哪一行决定？

要点：policy/policy-engine.ts 构造函数里：defaultDecision = config.defaultDecision ?? (nonInteractive ? DENY : ASK_USER)。另外 non-interactive.toml 把 ask_user 工具本身设为 deny。两处一起保证没人值守时不会卡在等待确认上，也不会悄悄放行。

Gemini CLI 在"不受信任的目录"里执行 git 命令时强制询问用户，最主要的原因是？

  1. git 命令通常很慢
  2. 仓库自带的 git hooks 和配置可以在执行 git 时运行任意代码，陌生仓库里跑 git 相当于运行它的代码
  3. git 命令会修改远端仓库
  4. 模型不擅长写 git 命令
像 git status 这样看似只读的命令，也会读取仓库配置、可能触发 fsmonitor 等钩子。对陌生仓库，"只读命令"并不安全。这是第 9 章"不可信输入不只是文本"的好例子：一个目录本身就可以是攻击载体。
本章要点
  • 策略引擎给出允许 / 拒绝 / 询问三种结论；规则按"来源层 + 层内优先级"合并，管理员 > 用户 > 工作区 > 扩展 > 默认永远成立。
  • shell 命令额外做启发式检查：越界目录、不受信任目录里的 git、危险命令、未展开的变量都强制询问；无交互时默认拒绝。
  • 压缩流程：50% 触发、逆序预算截断并落盘、按消息边界切分、合并旧快照、自我核对，压完反而变大就回退。
  • 主动监测模型的毛病：哈希加循环节检测绕圈，按需检查"话说一半就停"，后者默认关闭。
  • 项目记忆按子目录按需加载；MCP 工具加命名空间，可按服务器过滤，陌生目录里不启动本地 MCP 进程。
