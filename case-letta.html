Letta：分层记忆与 sleep-time 整理

Letta 的前身是 MemGPT，那篇论文把大模型类比成操作系统：上下文窗口是内存，外部存储是磁盘，由 agent 自己调用工具在两者之间换入换出。Letta 把这个想法做成了一个"agent 即服务"的系统。读它，能看清长期记忆在工程上到底由哪些部件组成，以及"谁来写记忆"这个最容易被忽略的问题。

约 40 分钟前置：第 5、6 章研读版本：archive 分支 56ba9c2（2026-08-13）
学完你能
  • 画出 Letta 的三层记忆：上下文内的记忆块（core memory）、召回记忆（recall）、归档记忆（archival），并说出各自的读写工具
  • 解释记忆块怎样渲染进系统提示、为什么"只在记忆变化时才重建系统提示"
  • 讲清上下文接近上限时的滑动窗口压缩：何时触发、驱逐多少、切在哪里
  • 理解 sleep-time agent 的分工：前台 agent 只读，后台 agent 负责改写记忆，以及这种分工的收益与风险

2 · 为什么读它

第 6 章讲过记忆的分类和检索打分，但真要做一个"记得住、记得对"的 agent，还要回答一串工程问题：记忆放在上下文的什么位置？模型怎么改它？改坏了怎么办？上下文满了怎么办？谁有权写？Letta 给每个问题都留下了一份可读的实现：

  • 记忆是一等的数据对象：记忆块有标签、描述、字数上限、只读标记，存在数据库里，可以被多个 agent 共享。
  • 模型通过工具改记忆，工具的设计借鉴了编码 agent 的"精确替换"思路，带着防呆检查。
  • 上下文管理是自动的：接近窗口上限就压缩，被移出的消息仍在库里，可以检索。
  • 写记忆可以交给后台：sleep-time agent 在对话之后异步整理，前台 agent 专心回应。这就是论文《Sleep-time Compute》（arXiv 2504.13171）的工程落地，在 letta-code 里改名叫 dreaming。

5 · 关键设计一：记忆块

5.1 记忆块长什么样

一个记忆块（Block，schemas/block.py）有这些字段：label（如 persona、human）、value（正文）、limit（字数上限，常量里块默认 100000 字符，persona 和 human 的默认上限是 20000）、description（这个块用来记什么）、read_only。渲染进上下文时，它变成这样一段 XML（memory.py#L143 的简化示意）：


<memory_blocks>
The following memory blocks are currently engaged in your core memory unit:

<human>
<description>
关于用户的信息：身份、偏好、约定。
</description>
<metadata>
- chars_current=86
- chars_limit=20000
</metadata>
<value>
称呼：张经理。月报发给本人，抄送部门负责人。
</value>
</human>
</memory_blocks>

三个细节值得注意：

  • description 告诉模型这个块的用途，相当于每个块自带一份说明，决定什么内容该往哪里写。
  • metadata 把预算摆在模型眼前：当前多少字、上限多少字。模型写记忆时能看到"快满了"，自然倾向于精炼而不是追加。
  • 按模型提供方切换渲染方式：对 Anthropic 模型的几类 agent，正文会带"1→"这样的行号，并附一条警告：行号只用于显示，编辑时不要带上（#L175）。

5.2 改记忆的工具：精确替换 + 防呆

memory_replace 的函数说明里注明它基于 Anthropic computer-use 示例中的编辑工具（base.py#L310）。服务端实现（core_tool_executor.py#L346）按顺序做了这些检查：

  1. 块是只读的，直接报错。
  2. old_string 或 new_string 里带了显示用的行号前缀，或者带了那条行号警告，报错并说明原因。这是专门针对"模型把看到的行号抄进参数"这一常见失误的防呆。
  3. old_string 在块里出现 0 次，报错"没有逐字出现"；出现多次，报错并列出所在行号，要求它给出唯一的片段。
  4. 通过后才替换、写回，再调用 update_memory_if_changed_async 持久化。

对照第 3 章：错误信息说清楚错在哪、怎么改；不唯一时不猜，让模型给出能唯一定位的片段。这和 Aider 的 SEARCH/REPLACE "宁可失败不错改"是同一个思路。

5.3 只在记忆变化时重建系统提示

rebuild_system_prompt_async（agent_manager.py#L1523）里有一句注释："we only update the system prompt if the core memory is changed"。它先编译当前记忆，如果结果已经包含在现有系统消息里，并且没有强制刷新，就什么都不做。

这关系到第 2 章的提示缓存：记忆块位于系统消息里、整个上下文的最前面，每改一次都会让后面全部缓存失效。"没变就不动"至少保证了不会无端破坏缓存。反过来也提醒我们：把会频繁变化的记忆放在前缀里，是有成本的，这正是 sleep-time 按频率批量整理的另一层好处。

6 · 关键设计二：召回与归档

召回记忆就是 messages 表。每条消息都会落库，包括被压缩移出上下文的那些，所以"移出上下文"不等于"遗忘"。conversation_search（base.py#L87）支持按查询词（文本匹配加语义相似度的混合检索）、角色、日期范围过滤，日期参数的说明写得非常细，连"只给日期时包含当天全天"都写明了。这是第 3 章"工具说明要无歧义"的好例子。

归档记忆是 agent 主动写入的条目。archival_memory_insert 的说明（#L164）教模型：存自包含的事实或摘要，不要存对话碎片；加描述性标签。检索 archival_memory_search（#L194）按语义相似度排序，可用标签（any/all 两种匹配）和时间范围缩小范围。写入后服务端会强制重建系统提示（core_tool_executor.py#L307），让元数据里的条目数和标签列表保持最新。

元数据是"目录"，不是内容

系统提示里不放召回和归档的内容，只放"有多少条、有哪些标签"。模型知道外面有东西，需要时自己去查。这就是第 5 章的"即用即取"（just-in-time）：上下文里放引用和索引，而不是全文。

7 · 关键设计三：上下文满了怎么办

压缩逻辑在 summarize_via_sliding_window（#L99），核心几行：


goal_tokens = (1 - summarizer_config.sliding_window_percentage) * agent_llm_config.context_window
approx_token_count = agent_llm_config.context_window
# ...
while approx_token_count >= goal_tokens and eviction_percentage < 1.0:
    # more eviction percentage
    eviction_percentage += 0.10
    # calculate message_cutoff_index
    message_cutoff_index = round(eviction_percentage * total_message_count)

sliding_window_percentage 默认取 partial_evict_summarizer_percentage = 0.30（settings.py#L86），所以目标是压到窗口的 70% 以下。循环里每次多驱逐 10% 的消息，并把切点回退到最近的 assistant 消息（或带工具调用的审批消息），重新数一次 token。摘要模型可以单独配置；模式除了滑动窗口，还有"全部摘要"和"让 agent 自己摘要"几种（CompactionSettings.mode）。

另一条路径是请求真的超了：模型返回 ContextWindowExceededError 时，agent 会压缩后重试，最多 max_summarizer_retries = 3 次（letta_agent_v3.py#L1218）。系统提示本身就超过窗口时，压缩也救不了，会以专门的停止原因 context_window_overflow_in_system_prompt 结束。这说明了一个第 5 章没细说的风险：记忆块写得太大，最终会让 agent 无法工作，所以字数上限和"快满了"的提示是必要的。

上下文窗口模拟（简化示意）

窗口按 8000 tokens 计。每聊一轮加约 450 tokens 的消息。超过 90% 触发压缩：先驱逐最旧的 30%，不够再每次加 10%，直到低于 70%，并在最前面放一条约 250 tokens 的摘要。

70% 目标90% 触发
基础提示记忆块工具定义历史摘要上下文中的消息

8 · 关键设计四：sleep-time，把"写记忆"交给后台

MemGPT 论文里，记忆由同一个 agent 一边对话一边管理。这有两个问题：模型要在回应用户的同时分心整理记忆，回复更慢；而且整理得好不好，全看它在那一刻有没有想起来。Letta 的 sleep-time 把两件事拆开了。

  • 创建：create_sleeptime_agent_async（server.py#L756）新建一个 sleeptime 类型的 agent，把主 agent 的全部记忆块 ID 挂上去（共享，不是复制），另给它一个自己的 memory_persona 块写工作守则；再建一个组，记下管理者是主 agent、频率 5。
  • 权限分工：主 agent 开启 sleep-time 后只拿到 BASE_SLEEPTIME_CHAT_TOOLS（发消息、两种检索），后台 agent 拿到 BASE_SLEEPTIME_TOOLS（四个记忆编辑工具），见 agent_manager.py#L396–405。能写记忆的只有后台。
  • 输入：只把上次处理之后的新对话给后台 agent，并用一段系统提醒澄清角色："assistant"是主 agent，"user"是主 agent 的用户，你不是主 agent。这避免了后台 agent 把对话当成在和自己说话。
  • 可追踪：每次后台整理都是一个 Run，记录运行中、完成或失败，以及结果。
和 Anthropic 记忆文章的呼应

Anthropic 2026-11 的《The components of agent memory》也主张在两次会话之间离线回看记录、修正和提升记忆（文中叫 dreaming）。Letta 在 letta-code 里把 sleep-time 改名为 dreaming，README 写明可以用 /sleeptime 配置定期运行，也可以手动 /dream、/reflect。两边独立得出了同一个结论：写记忆应该是一个有节奏的后台过程，而不是对话中模型临时起意的副作用。

这种分工也有代价，值得在借鉴时想清楚：后台 agent 仍然是模型在判断"什么值得记"，没有人工审核；它读的是整段对话，同样会读到不可信的内容（第 9 章的记忆投毒，OWASP ASI06）；而且前台要等下一次触发才看得到新记忆，频率设得低，"刚说过的事"会有几轮记不住。

开启 sleep-time 后，用户在第 2 轮说了"以后月报抄送部门负责人"，第 3 轮问"月报要抄送谁？"。在默认配置下，最可能发生什么？

  1. 前台 agent 在第 2 轮就用 memory_replace 写进了 human 块，第 3 轮直接答对
  2. 后台 agent 每轮都运行，第 3 轮之前一定已经写好
  3. 后台整理默认每 5 轮触发一次，第 3 轮时记忆块大概率还没更新；但这句话仍在上下文中的消息里（或可用 conversation_search 查到），前台 agent 依然能答对
  4. 前台 agent 答不出来，因为没有记忆工具
开启 sleep-time 后，前台 agent 没有改记忆块的工具，后台默认每 5 轮整理一次。但"记忆块还没更新"不等于"不知道"：最近的对话仍在上下文中，较早的也能用 conversation_search 从召回记忆里查到。理解这几层记忆各自的时效，才能判断一个 agent"记得"什么。

9 · 现状：letta-code

当前的 Letta 以 letta-code（TypeScript，Apache-2.0，查看时的提交为 c67a0d5，2026-11-24）为主，定位是"有状态的 agent 驾驭器"，可以在终端、桌面、网页和 Slack、Telegram 等渠道里使用同一个 agent。从它的 README 和源码可以确认几处演进：

  • MemFS：README 写明"包括记忆块在内的全部上下文都用 git 追踪"，可以同步到自定义的 GitHub 仓库。源码里每个 agent 的记忆目录在 .letta/agents/<agent_id>/memory 下，其中 system 子目录对应会渲染进系统提示的部分（src/agent/memory-filesystem.ts）。archive 分支的 Memory 类里已经能看到 git 化的渲染分支（_render_memory_blocks_git）。
  • dreaming：sleep-time 改名为 dreaming，可以配置定期运行，也可以手动触发 /dream、/reflect（src/agent/reflection-runs.ts）。
  • 技能也是记忆：letta skills install 把 Skill 装进某个 agent 的记忆里，和第 11 章的 Agent Skills 接上了。

"记忆即文件、文件即 git"这个方向，让记忆天然有版本、有 diff、可回滚、可审阅，正好补上了上面说的"后台写记忆没人审核"的短板：至少每次改动都留下了可以检查和撤销的记录。

10 · 值得借鉴 / 不宜照搬

值得借鉴不宜照搬
记忆块是带元数据的数据对象：标签、用途说明、字数上限、只读，渲染时把预算告诉模型。记忆放在系统提示最前面：每次改写都会让整个前缀的缓存失效。记忆变化频繁的场景，要权衡它的位置和更新节奏。
记忆工具精确替换、拒绝歧义，专门拦截"把行号抄进参数"这类常见失误。写记忆没有人工审核：个人助理这类场景，影响路由或对外表述的记忆，应该像第 8 章那样走提案审批，或至少留可撤销的变更日志。
移出上下文不等于遗忘：消息全部落库，压缩后仍可检索。后台 agent 读全部对话：不可信内容可能借此写进长期记忆，需要来源标注和过滤（第 9 章）。
写记忆交给后台、按频率批量做，前台只读，职责清楚。整套服务端很重：数据库、迁移、多租户、组织权限……单用户的小系统用文件加 SQLite 就能实现同样的分层。
agent 状态全在库里，进程无状态、可重启。注释与实现不一致：见读码练习 3。读别人的代码要以实现为准，写自己的代码要让注释跟着改。

11 · 对照复盘

真实项目复盘
  • N13 · niuma 的记忆曾把旧的猜测回灌成证据，写入不经审核。Letta 用"前台只读、后台写"划清了写权限，letta-code 再用 git 给每次改动留版本；但它同样没有人工审核，对影响路由的记忆还要加一道佐证或审批。
  • D11 · devtask 的任务记忆要等模型"记得"调用工具才写入。Letta 的 sleep-time 把写记忆变成按轮次触发的后台流程，不依赖前台模型临时起意。
  • N12 · niuma 的上下文只按条数截断。Letta 按 token 估算触发压缩、按目标比例驱逐，并保证切点不拆开工具调用。

12 · 读码练习

练习 1：前台 agent 在开启 sleep-time 后为什么改不了记忆块？请找出决定这件事的代码。

看 agent_manager.py#L396–405：enable_sleeptime 为真时，主 agent 的工具集是 BASE_SLEEPTIME_CHAT_TOOLS，只有发消息和两种检索（constants.py#L133）。权限是用"给不给工具"来控制的，而不是在提示词里叮嘱"不要改记忆"。

练习 2：memory_replace 收到的 old_string 在块里出现了两次，模型会看到什么？这样设计比"替换第一处"好在哪？

看 core_tool_executor.py#L346 起：报错"No replacement was performed. Multiple occurrences …in lines […]"，并要求给出唯一片段。替换第一处可能改错位置，而且不会留下任何报错；明确失败、给出行号，模型下一次就能补上足够的上下文。

练习 3：读 thresholds.py 的 get_compaction_trigger_threshold，它的文档说明和实际返回值一致吗？

看 thresholds.py#L27–41。说明写的是"GPT-5 系列在 90% 主动触发，其他模型在 100% 触发"，参数里还有 force_proactive；但函数体只有一行，对所有模型都返回"窗口 × 0.9"，既没有判断模型，也没有用到这个参数。读代码要以实现为准，这也是"文档与代码不一致"在成熟项目里同样会出现的例子。

练习 4：滑动窗口压缩为什么要把切点回退到 assistant 消息？如果切在中间会发生什么？

看 summarizer_sliding_window.py#L155–176 的 is_valid_cutoff。如果切在一次工具调用和它的结果之间，保留下来的上下文里会出现"没有对应调用的工具结果"，多数模型 API 会直接拒绝这样的消息序列，即使接受，模型也看不懂前因后果。

练习 5：sleep-time agent 收到的消息里为什么要特意说明"assistant 是主 agent，user 是主 agent 的用户"？

看 sleeptime_multi_agent_v4.py#L202 起。后台 agent 收到的是一整段转录文本，如果不澄清角色，它可能把用户的话当成对自己的指令去执行，或者把主 agent 的承诺当成自己说过的话。这是第 5 章"上下文要讲清楚每段内容是什么"的具体例子，也是防注入的一个最低要求。

Letta 的系统提示里只放"召回里有 N 条消息、归档里有 M 条、可用标签有哪些"，而不放这些记忆的内容。这样设计最主要的理由是？

  1. 数据库查询太慢，来不及放内容
  2. 让模型知道外面有什么、需要时自己去查，上下文里只放索引，不放全文
  3. 防止模型看到历史消息
  4. 为了让系统提示永远不变
这是"即用即取"（just-in-time）的上下文策略：上下文是稀缺的注意力预算，常驻的只应是小而关键的记忆块和外部记忆的目录。元数据本身会随写入更新（归档写入后会强制重建系统提示），所以它并不是"永远不变"。
本章要点
  • Letta 的记忆分三层：记忆块常驻系统提示，召回是全部消息，归档是主动写入的带向量条目；后两者靠工具检索。
  • 记忆块是带用途说明、字数上限和只读标记的数据对象，渲染时把预算展示给模型；编辑工具精确替换、拒绝歧义。
  • 上下文超过窗口的 90% 时，按 30% 起、每次加 10% 驱逐旧消息直到低于 70%，切点对齐 assistant 消息，原文仍可检索。
  • sleep-time 把写记忆交给后台 agent、前台只读，按轮次批量整理；letta-code 进一步把记忆放进 git，并改名叫 dreaming。
  • 借鉴时要补上两块：影响行为的记忆需要佐证或审批，后台读到的不可信内容需要来源控制。
