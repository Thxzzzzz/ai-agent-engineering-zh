名作研读：怎么读一个成熟 Agent 项目的源码

前面的章节告诉你"应该怎么做"，复盘告诉你"缺了知识会怎样"。这一部分补上第三块：看业界最成熟的那批 agent 项目实际是怎么做的。读懂它们的源码，是从"会写 agent"走向"能评判、能设计 agent 系统"最快的路。

1 · 为什么要读成熟项目的源码

博客和论文讲的是作者想让你看到的设计。源码里才有那些没人写进文章的东西：防御性的边界检查、被注释掉的旧方案、为某个线上事故加的特判、注释与实现的不一致。这些恰恰是高级工程师的判断力来源。

这一部分的 9 篇研读有三条共同约定：

  • 固定版本：每篇都钉在一个具体提交上（2026 年 5–11 月），文中每条源码链接都带完整的提交号和行号，项目以后怎么改都不会失效。
  • 说法可核实：关于代码的每一句话都在克隆下来的源码里核对过；核对不了的不写，或者明确标"示意"。
  • 对照课程：每个关键设计都链回对应的章节；与复盘里的问题相关时，也链到复盘条目。
研读中顺带发现的"成熟项目也会有的问题"

这些都写进了对应篇目的读码练习里，值得专门留意：Letta 的压缩阈值函数注释说按模型区分 90% 和 100%，实现对所有模型都返回 0.9 倍窗口；Aider 的编辑格式里有一段模糊匹配被一行 return 提前关掉了；mini-swe-agent 自称"约 100 行"，实测核心类 190 行（去掉空行、注释和文档字符串后 158 行）。读源码时，注释和 README 都只是线索，以代码为准。

2 · 六问读码法

面对一个陌生的 agent 仓库，不要从目录树第一个文件开始读。带着下面六个问题去找答案，每个问题对应课程的一章：

几个省时间的习惯
  • 先读测试再读实现：测试的名字往往就是一份行为规格。
  • 用提交历史找"为什么"：对一个奇怪的判断执行 git log -L 或 git blame，常能找到对应的事故或 issue。
  • 只读不跑：陌生仓库是不可信代码，研读阶段只用 grep 和阅读器，不执行它的安装脚本。
  • 画一张自己的图：读完六问，凭记忆画出数据流图，再回去对照源码。画不出来的地方就是没读懂的地方。

3 · 同一个问题，九种做法

选一个问题，看 9 个项目分别怎么做、去哪个文件读。源码链接都固定在各篇研读的版本上。标"—"的格子表示研读页没有展开这一点，不代表项目没有这个能力。

你在一个 agent 项目的源码里看到一段注释："阈值按模型区分，部分模型为 100%"，但函数体对所有模型都返回窗口的 0.9 倍。你应该怎么理解它的实际行为？

  1. 以注释为准，注释代表设计意图
  2. 以 README 为准
  3. 以代码为准：实际行为就是 0.9 倍；注释说明作者曾经或打算区分模型，值得去提交历史里找原因
  4. 两者都不可信，需要实际运行才能知道
运行时只认代码。注释和 README 是理解意图的线索，和代码不一致时，往往说明有过一次改动没同步注释。这正是 Letta 研读页里的一道读码练习。
本章要点
  • 读源码要固定版本、只读不跑、带着问题读：循环、工具、上下文、权限、恢复、记忆。
  • 同一个问题在 9 个项目里有完全不同的解法，比较它们才能看清取舍，而不是记住某一种写法。
  • 注释和 README 只是线索，以代码为准；测试和提交历史能告诉你作者为什么这样写。
