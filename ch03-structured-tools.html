结构化输出与工具调用

agent 能做事，靠的是模型输出"机器能读的东西"：一个合法的 JSON、一次参数正确的工具调用。这一章讲两件事：怎么让模型可靠地输出结构化数据，以及怎么设计让模型用得好的工具。

约 40 分钟前置：第 2 章含 1 个分步动画、1 个 schema 校验演示器、3 道小测
学完你能
  • 说出 strict 模式对 JSON Schema 的约束，并据此设计兼容各家 API 的 schema
  • 实现"单一工具 + 校验 + 错误回灌重试"的结构化输出函数
  • 正确处理拒答、截断、枚举大小写和语义层面的校验失败
  • 按官方最佳实践设计工具：粒度、命名、返回格式、错误信息

1 · 为什么需要结构化输出

办公助理读完一封邮件，要产出：一句话摘要、紧急程度、是否需要回复、提炼出的待办。如果让模型自由发挥，你会收到"这封邮件比较紧急，建议回复……"之类的散文，然后不得不用正则去捞字段——格式稍有变化就崩。

结构化输出把模型的产出变成一个有类型的对象，下游代码可以直接分支、入库、渲染卡片。它也是工具调用的本质：12-Factor Agents 的第 4 条说得直接——"工具只是结构化输出"。模型说"我要调用 send_email，参数是……"，和模型说"摘要是……，紧急程度是……"，在机制上是同一件事。

2 · 三种做法与它们的可靠性

做法原理可靠性适用
提示词里要求"只输出 JSON"纯靠模型听话低：会夹带解释文字、漏字段、写错类型原型阶段
结构化输出 / JSON 模式（response format）服务端按 schema 约束解码高：strict 模式下语法层面保证符合 schema单一 API、schema 在其支持范围内
工具调用（function calling）把 schema 当成一个工具的参数定义高：strict 工具同样受约束解码保护需要跨厂商一致行为、或本来就在工具循环里

OpenAI 在 2024-08-06 发布 Structured Outputs 时公布的内部评测是：开启 strict 后，模型遵循复杂 schema 的比例达到 100%，而更早的模型只靠提示词不到 40%。Anthropic 在 2025-11-13 推出结构化输出公测，现在已经稳定，支持 JSON 输出和工具上的 strict: true 两种方式。

"语法上合法"不等于"语义上正确"

约束解码保证的是"JSON 能解析、字段齐全、类型对"，不保证"摘要准确"、"日期没有写成过去"、"引用的邮件 ID 真实存在"。所以即使用了 strict 模式，你的代码仍然要做校验，只是校验的重点从格式转向了语义。

3 · strict 模式的约束：写出兼容的 schema

约束解码要求 schema 足够"规整"，所以各家 strict 模式都只支持 JSON Schema 的一个子集。下面是 2026-11 核实的主要约束：

约束OpenAI Structured OutputsAnthropic 结构化输出
必填所有字段都必须列进 required支持可选参数，但有数量上限
可选语义用 null 联合表达："type": ["string", "null"]同左也可用
额外字段每个对象都要 additionalProperties: false对象必须 additionalProperties: false
根节点必须是 object，不能是 anyOf—
组合关键字不支持 allOf / not / if-then-else；支持 $defs 与递归不支持递归与 oneOf，也不支持数值、长度约束
规模上限最多 5,000 个属性、10 层嵌套、1,000 个枚举值单次请求最多 20 个 strict 工具、24 个可选参数、16 个联合类型参数
其他模型拒答时返回 refusal，解析前要先检查编译后的语法缓存 24 小时；不能和 citations、prefill 同用；枚举大小写不保证
可移植的写法：取交集

如果你的系统要能在多家模型之间切换，就按最严格的交集来设计 schema：所有字段必填、每个对象 additionalProperties:false、可选语义一律用"类型或 null"、不用递归、不用 oneOf/allOf、不依赖 minLength/maximum 这类约束（这些约束改到你自己的校验代码里做）。这样一份 schema 走遍各家的 strict 模式。

用 Zod 4 写 schema，再用 z.toJSONSchema() 转成 JSON Schema 发给模型，类型和运行时校验都从同一处来。Zod 4 的 z.object() 在转换时默认带 additionalProperties: false，.nullable() 转出来是 ["string", "null"]，正好符合上面的交集：


import * as z from 'zod';

export const TaskItem = z.object({
  title: z.string().describe('一句话的待办，动词开头'),
  owner: z.string().nullable().describe('负责人姓名；邮件里没说时为 null'),
  due_date: z.string().nullable().describe('YYYY-MM-DD；没有明确期限时为 null'),
});

export const Triage = z.object({
  summary: z.string().describe('不超过 50 字的摘要'),
  urgency: z.enum(['low', 'normal', 'high']),
  needs_reply: z.boolean().describe('对方是否在等我答复'),
  tasks: z.array(TaskItem),
  evidence: z.array(z.string()).describe('支持判断的原文引用编号，如 m1、m3'),
});
export type Triage = z.infer<typeof Triage>;
"全部必填"会不会让模型乱填？

会，如果你不给它一个合法的"没有"。owner 设成必填的 string，邮件里没提负责人时模型就会编一个名字。设成 string | null 并在描述里写明"没说时为 null"，模型就有了诚实表达"不知道"的出口。这也是为什么评测里建议给 LLM 判官一个"Unknown"选项（第 13 章）。

4 · 可移植的模式：单一工具 + 校验 + 错误回灌

各家的 response format 参数写法不同、支持的 schema 子集不同、"强制调用某个工具"（tool choice）的语义也不完全一致。一个在实践中跨厂商行为最稳定的做法是：

  1. 把输出 schema 包装成唯一的工具 emit_result（开启 strict），系统提示末尾写明"必须且只能通过调用该工具提交结果"。
  2. 收到响应后找到 emit_result 的调用，用 Zod 校验参数（含语义校验）。
  3. 没调用工具：追加一条用户消息要求调用。参数不合法：追加一条 isError 的工具结果，把具体的校验错误告诉模型，让它修正。
  4. 重试到上限仍失败就抛错，把这次的 trace 留作评测用例。

点"下一步"看一次带修正的完整往返：


import * as z from 'zod';
import type { Message, Model, ToolCall, Usage } from './types';

const TOOL = 'emit_result';

export class StructuredOutputError extends Error {
  constructor(message: string, readonly attempts: number, readonly lastCall?: ToolCall) {
    super(message);
  }
}

export async function completeStructured<S extends z.ZodType>(
  model: Model,
  schema: S,
  req: { system: string; user: string },
  opts: { maxAttempts?: number; signal?: AbortSignal } = {},
): Promise<{ value: z.infer<S>; attempts: number; usage: Usage }> {
  const { $schema: _ignored, ...inputSchema } = z.toJSONSchema(schema) as Record<string, unknown>;
  const tools = [{ name: TOOL, description: '提交最终结果。必须且只能调用一次。', inputSchema }];
  const messages: Message[] = [
    { role: 'system', content: `${req.system}\n\n必须且只能通过调用 ${TOOL} 工具提交结果，不要输出其他文字。` },
    { role: 'user', content: req.user },
  ];
  const usage: Usage = { inputTokens: 0, outputTokens: 0, cachedInputTokens: 0 };
  const maxAttempts = opts.maxAttempts ?? 2;
  let lastCall: ToolCall | undefined;

  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    const res = await model.generate({ messages, tools, signal: opts.signal });
    usage.inputTokens += res.usage.inputTokens;
    usage.outputTokens += res.usage.outputTokens;
    usage.cachedInputTokens += res.usage.cachedInputTokens;

    // 拒答与截断不是"格式错误"，重试通常没用，直接上报
    if (res.stopReason === 'refusal') throw new StructuredOutputError('模型拒绝回答', attempt);
    if (res.stopReason === 'max_tokens') throw new StructuredOutputError('输出被截断，调大 max_tokens 或缩小输出', attempt);

    messages.push({ role: 'assistant', content: res.content, toolCalls: res.toolCalls });
    const call = res.toolCalls.find((c) => c.name === TOOL);
    if (!call) {
      messages.push({ role: 'user', content: `你没有调用 ${TOOL}。请调用它提交结果。` });
      continue;
    }
    lastCall = call;
    const parsed = schema.safeParse(call.args);
    if (parsed.success) return { value: parsed.data, attempts: attempt, usage };
    messages.push({
      role: 'tool',
      toolCallId: call.id,
      isError: true,
      content: `参数校验失败，请修正后重新调用 ${TOOL}：\n${z.prettifyError(parsed.error)}`,
    });
  }
  throw new StructuredOutputError(`${maxAttempts} 次尝试后仍未得到合法结果`, maxAttempts, lastCall);
}

几个容易忽略的细节：

  • 先追加 assistant 消息，再追加 tool_result：工具结果必须能对应到上一条 assistant 消息里的某个 tool call id，否则大多数 API 会直接报错。
  • 语义校验写进 schema：用 Zod 的 .refine() 或在 safeParse 之后再查一遍（"evidence 里的编号是否都在本批邮件里"），失败时走同样的回灌路径。
  • 可以有"修复"步骤，但要克制：如果某种偏差反复出现且意思毫无歧义（比如枚举大小写），可以在校验前做一次规范化。不要写成"什么都能宽松解析"——那会掩盖真正的问题。

模型返回了一个结构化结果，但因为 stop_reason 是 max_tokens，JSON 在中间被截断了。最合适的处理是？

  1. 带着"JSON 解析失败"的错误回灌，让模型重新输出
  2. 用容错的 JSON 解析器补全括号
  3. 当作独立的失败类型处理：调大输出上限或缩小要求输出的内容，并把这次记录下来
  4. 换一个模型重试
截断说明输出本身就超出了上限，回灌重试大概率再次被截断，白白多花一次钱；补全括号会得到缺字段的"假合法"结果。截断、拒答和格式错误是三种不同的失败，应该分开处理和统计。

6 · 给 agent 设计工具

结构化输出解决了"模型怎么说"，工具设计解决的是"模型拿什么做事"。Anthropic 把这一层叫做 ACI（agent-computer interface），并建议在它上面投入和 HCI（人机界面）同样多的精力。下面是《Writing effective tools for agents》（2025-09-11）的核心原则：

原则反例正例
按任务设计，不按 API 逐个包装list_contacts：返回全部联系人让模型自己找search_contacts(query)：一次拿到要的人
工具少而精把 30 个内部接口全挂上去按用户任务合并成几个高层工具；"工具多不等于效果好"
命名空间search、getmail_search、calendar_events_search，避免混淆
参数名无歧义useruser_id 或 user_email
返回语义字段一堆 UUID 和内部编码名字、标题、可读的时间；需要 ID 时也给，但别只给 ID
控制返回量一次返回几万 token 的原始 JSON分页、过滤、截断，并告诉模型"还有更多，用 page=2 继续"
提供详略开关永远返回完整详情response_format: "concise" | "detailed"；文中实例里简洁版约省 2/3 token
错误信息可执行Error 400"日期格式应为 YYYY-MM-DD，你传入的是 '下周三'。可先调用 calendar_resolve_date 解析相对日期。"

export const calendarEventsSearch = {
  name: 'calendar_events_search',
  description:
    '按时间范围和关键词搜索当前用户日历中的会议。返回会议标题、时间、参会人姓名。' +
    '相对日期（如"下周三"）请先调用 calendar_resolve_date 转成具体日期。结果最多 20 条，超出时用 page 翻页。',
  inputSchema: {
    type: 'object',
    additionalProperties: false,
    required: ['start_date', 'end_date', 'keyword', 'page', 'response_format'],
    properties: {
      start_date: { type: 'string', description: 'YYYY-MM-DD，含当天' },
      end_date: { type: 'string', description: 'YYYY-MM-DD，含当天' },
      keyword: { type: ['string', 'null'], description: '标题关键词；不限时为 null' },
      page: { type: 'integer', description: '从 1 开始' },
      response_format: { type: 'string', enum: ['concise', 'detailed'], description: 'concise 只返回标题、时间与 event_id' },
    },
  },
};

防呆设计（poka-yoke）

《Building effective agents》里有一个经典例子：Anthropic 发现模型在切换目录后经常用错相对路径，于是把工具改成只接受绝对路径，这类错误就消失了。思路是改工具让错误不可能发生，而不是在提示词里反复叮嘱。常见手法：

  • 用短引用代替长 ID：给模型看的邮件编号为 m1、m2，代码里再映射回真实的消息 ID。模型抄错 36 位的 UUID 的概率远高于抄错 m3，而且一旦抄错，校验时能立刻发现"m9 不存在"。
  • 用枚举代替自由文本：动作类型、状态、优先级都用 enum。
  • 危险参数不暴露：发件人、抄送范围由代码决定，不让模型填。
  • 让工具幂等：同一个请求重复调用不会产生两份结果（第 10 章）。
把工具当成产品来测

Anthropic 推荐的流程是：本地快速做出工具原型 → 构造一批需要多次工具调用、结果可验证的真实任务 → 让 agent 跑 → 读 transcript 看它在哪里困惑、哪个参数总填错 → 改描述或改工具 → 再跑。他们在多智能体研究系统里仅靠改写工具描述，就让任务完成时间下降了 40%。工具描述本身就是提示词，值得同样的迭代。

agent 调用 mail_send 时经常把收件人写成同事的中文名而不是邮箱地址，导致发送失败。最好的改进是？

  1. 在系统提示里加粗强调"收件人必须是邮箱"
  2. 改工具：收件人参数改为联系人引用（由 contacts_search 返回的短编号），代码负责映射成邮箱；错误时返回"请先用 contacts_search 查找此人"
  3. 换一个更强的模型
  4. 捕获异常后静默重试三次
这是典型的防呆问题：与其要求模型记住格式，不如让错误的输入形态不可能出现，并在出错时给出可执行的下一步。提示词强调可以作为补充，但不应该是唯一的防线。

下面哪个 schema 片段最符合跨厂商 strict 模式的"交集"写法？

  1. {"type":"object","properties":{"owner":{"type":"string"}}}
  2. {"type":"object","properties":{"owner":{"type":"string","minLength":1}},"required":["owner"]}
  3. {"oneOf":[{"type":"object"},{"type":"null"}]}
  4. {"type":"object","additionalProperties":false,"required":["owner"],"properties":{"owner":{"type":["string","null"]}}}
交集写法：对象带 additionalProperties:false、所有字段 required、可选用"类型或 null"、不用 oneOf、不依赖 minLength 这类约束（改在自己的校验代码里做）。①缺 required 与 additionalProperties，②用了长度约束，③根节点不是 object 且用了 oneOf。
真实项目复盘

本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

  • D3 · devtask 让模型自己填 user_confirmed 来"证明"用户已同意
  • D4 · devtask 的模型编造过不存在的 open_id、漏传 task_id
  • N3 · niuma 的一次分析调用要同时输出十几个判断
本章要点
  • 工具调用就是结构化输出；两者共用 schema、校验和回灌机制。
  • strict 模式保证语法合法，不保证语义正确，代码里永远要校验。
  • 可移植 schema 取各家交集：全必填、additionalProperties:false、null 联合表达可选、不用递归与组合关键字。
  • "单一工具 + 校验 + 错误回灌"是跨厂商最稳定的结构化输出模式；拒答、截断、格式错误分开处理。
  • 工具按任务设计、少而精、命名空间、语义化返回、控制返回量、错误信息可执行；用防呆设计消灭错误而不是叮嘱模型。
