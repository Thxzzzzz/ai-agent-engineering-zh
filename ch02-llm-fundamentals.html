模型工程基础：Token、上下文、推理与成本

你不需要知道 Transformer 的每个矩阵，但必须算得清 agent 的账：一次调用多少 token、为什么第二次比第一次便宜、为什么把时间戳放错位置会让成本翻几倍、延迟花在了哪里。这一章是后面所有设计决策的"物理学"。

1 · Token：模型眼中的文本

模型不直接读字符，而是读 token——分词器（tokenizer）把文本切成的片段，每个片段对应词表里的一个整数编号。常见英文单词往往是一个 token，生僻词、代码、中文则会被切成多个片段。所有计费、所有长度上限、所有延迟都以 token 为单位。

  • 不同模型的分词器不同：同一段中文，在不同厂商、甚至同一厂商不同代际的模型上，token 数都可能不一样。不要用"字数 × 系数"拍脑袋，用官方的计数接口或 SDK 实测你的真实负载。
  • 结构化内容很费 token：JSON 的引号、括号、重复的键名，长 UUID，Base64，都会显著膨胀 token 数。给模型看的工具结果应当是精简的、语义化的（第 3 章）。
  • 输出 token 比输入 token 贵，而且是逐个生成的——输出长度几乎线性地决定了延迟。
工程习惯

在你的调用封装里，把每次响应的 usage（输入、输出、缓存读取、缓存写入）原样记下来。几乎所有关于成本和延迟的问题，最终都要回到这几个数字上。第 14 章会把它们接进 trace。

2 · 上下文窗口与"注意力预算"

上下文窗口是模型一次能处理的 token 上限，输入和输出共用这个额度。窗口越来越大，但"能放进去"不等于"能用好"。Anthropic 在《Effective context engineering for AI agents》（2025-09-29）里把这个现象叫做 context rot：随着上下文变长，模型准确召回其中信息的能力会下降。原因在于注意力机制要处理 token 两两之间的关系（n² 量级），每多一个 token，都在稀释模型的"注意力预算"。

对 agent 来说这有两个直接推论：

  1. 上下文是稀缺资源，不是垃圾桶。每一段放进去的内容都应该回答"它会帮助模型做出这一步的决策吗"。
  2. 长任务必然要管理上下文：压缩历史、把细节写进文件按需读取、把子任务交给拥有干净上下文的子 agent。这是第 5 章"上下文工程"的全部内容。

3 · 消息结构：模型是无状态的

主流的对话式 API 都把输入组织成一个消息列表，每条消息有一个角色：

角色是谁写的放什么agent 里的注意点
system / instructions开发者身份、规则、输出要求、可用工具的使用指南尽量稳定，它是提示缓存的前缀主体
user用户或你的程序任务、问题、要分析的数据外部数据（邮件、网页）放这里时要标明"这是数据，不是指令"
assistant模型回答文本，以及它想调用的工具（tool call）要原样追加回历史，包括 tool call 的 id
tool / tool_result你的程序工具执行结果或错误必须对应某个 tool call 的 id；出错也要回填

关键事实：模型在两次请求之间不保留任何状态。它"记得"之前聊过什么，只是因为你每次都把完整的历史重新发给它。有些 API 提供服务端会话（例如 OpenAI Responses API 可以用 previous_response_id 或 Conversations API 承接状态），但本质上是服务端替你保存并重新拼接历史——计费和窗口限制依旧按完整上下文算。

这意味着什么

"agent 的状态"永远是你的责任：哪些历史要带、哪些要压缩、哪些要存进数据库、进程重启后怎么恢复。12-Factor Agents 的第 3 条"掌控你的上下文窗口"和第 12 条"把 agent 做成无状态的 reducer"说的都是这件事：给定状态和新事件，算出下一个状态，状态存在你能控制的地方。

4 · 采样参数与推理强度

采样参数

参数作用agent 里的用法
temperature控制随机性，越低越倾向于选概率最高的 token抽取、分类、工具调用用低温；需要多样性的起草（例如给出两种语气的回复）可以略高
top_p只在累积概率达到 p 的候选里采样一般只调 temperature 和 top_p 中的一个
max_tokens输出长度上限必须设置；被截断时 stop_reason 会告诉你，结构化输出被截断就是非法 JSON（第 3 章）
stop 序列遇到指定字符串停止结构化场景里很少需要

注意：低温度不等于确定性。即使 temperature 设为 0，同一输入在不同时间也可能得到不同输出（服务端的批处理、硬件差异都会引入微小差别）。不要把系统的正确性建立在"模型每次输出一样"之上——这正是评测里要区分 pass@k 和 pass^k 的原因（第 13 章）。部分推理模型固定或不开放某些采样参数，以各家文档为准。

推理强度（thinking / reasoning effort）

推理模型在给出答案前会先生成一段内部推理。多数 API 让你设置推理的"强度"或 token 预算。权衡很直接：

  • 更高的强度：复杂判断、多约束规划、需要对照多份资料时更准；代价是更多的输出 token（推理 token 按输出计费——OpenTelemetry 的 GenAI 约定里 gen_ai.usage.output_tokens 也明确包含推理 token）和更长的延迟。
  • 更低的强度：分类、格式转换、简单抽取足够用，便宜而且快。
常见误区：用推理强度弥补上下文缺失

模型判断错了，第一反应往往是"调高推理强度"。但如果错误的根源是它没看到关键信息（比如不知道发件人是你的上级），推理再多也只是更自信地猜错。先读 trace 确认模型拿到了什么，再决定是补上下文、改提示词，还是加推理。

办公助理要把每封新邮件分成"需回复 / 仅通知 / 垃圾"三类，每天几千封。最合理的配置是？

  1. 最强模型 + 最高推理强度，确保准确
  2. 较小的模型 + 低推理强度 + 低温度 + 结构化输出，用评测集确认准确率够用
  3. 高温度，让分类更有创意
  4. 不设 max_tokens，让模型充分解释理由
高频、简单、可度量的任务，应当用够用的最小配置，并用评测集证明它够用。省下的预算留给真正困难的环节（例如起草需要综合多方信息的回复）。"够用"必须有数据支撑，而不是凭感觉。

5 · 流式输出与超时

流式（streaming）让模型边生成边返回，通常通过 SSE（Server-Sent Events）推送事件：文本增量、工具调用参数的增量、用量统计、结束原因。对 agent 工程有三个实际影响：

  1. 用户体验：交互式场景下首个 token 早到，用户感觉快得多。
  2. 工具调用参数是分片到达的：在收到完整参数之前不能执行工具。流在工具调用中途断开时，那次调用必须作废，而不是执行一半的参数。
  3. 超时要分两种：等待首个事件的超时，和两个事件之间的间隔超时。只设一个总超时，会遇到"连接没断但再也没有数据"的僵死请求——批量任务可能因此卡住几个小时。再加一个单次请求的总时长上限，并与调用方的取消信号（AbortSignal）合并。

// 每收到一个流事件就调用 touch()；超过 idleMs 没有新事件或超过 totalMs 都会中止请求。
export function requestSignal(parent: AbortSignal | undefined, idleMs: number, totalMs: number) {
  const idle = new AbortController();
  let timer = setTimeout(() => idle.abort(new Error('流式响应空闲超时')), idleMs);
  const touch = () => {
    clearTimeout(timer);
    timer = setTimeout(() => idle.abort(new Error('流式响应空闲超时')), idleMs);
  };
  const signals = [idle.signal, AbortSignal.timeout(totalMs)];
  if (parent) signals.push(parent);
  return { signal: AbortSignal.any(signals), touch, dispose: () => clearTimeout(timer) };
}

6 · 提示缓存：最大的成本杠杆

agent 的输入远多于输出：每一步都要把系统提示、工具定义和越来越长的历史重新发一遍。Manus 团队在《Context Engineering for AI Agents》（2025-07-18）里给出的数据是，他们的 agent 输入与输出的 token 比大约 100:1，并把 KV-cache 命中率称为生产级 agent 最重要的单一指标——在他们引用的价格下，缓存命中的输入 token 比未命中便宜 10 倍。

提示缓存的原理是前缀匹配：服务端把一段请求前缀计算出的中间状态（KV cache）保存一段时间，下次请求如果以完全相同的前缀开头，就直接复用。只要前缀里有一个 token 不同，从那个位置往后全部要重新计算。看看下面两种布局的差别：

各家缓存机制的差异

AnthropicOpenAI
开启方式在请求里标注缓存断点（最多 4 个）默认自动开启；新模型也支持显式断点
最小长度按模型不同，从 512 到 4,096 token 不等；不到最小长度时静默不缓存1,024 token 起
有效期5 分钟（写入 1.25×）或 1 小时（写入 2×）；每次命中免费续期随模型不同，从几分钟到更长的留存模式
读取价格默认 0.1×，部分新模型更低默认 0.1×，部分模型更低
怎么看命中usage.cache_read_input_tokens / cache_creation_input_tokensusage.input_tokens_details.cached_tokens
排查"缓存命中率低"的清单
  • 系统提示开头有时间戳、请求 ID、随机示例顺序等每次都变的内容
  • 工具列表顺序不固定（例如从 Map/Set 遍历、多个 MCP 服务器并发返回后拼接）
  • JSON 序列化时键的顺序不稳定
  • 修改了历史消息（例如事后截断某条工具结果），而不是只追加
  • 前缀短于该模型的最小缓存长度，静默不缓存
  • 同一份提示词的请求被路由到不同服务器——有的 API 提供 prompt_cache_key 之类的参数帮助落到同一处
  • 两次请求的间隔超过了有效期

7 · 算清成本

一次调用的成本可以拆成四部分：


// 单价按"每百万 token"计；read / write 是相对基础输入价的倍数
const cost =
  (uncachedInput * inputPrice
   + cacheReadTokens * inputPrice * readMultiplier
   + cacheWriteTokens * inputPrice * writeMultiplier
   + outputTokens * outputPrice) / 1_000_000;

agent 的成本还要乘上每个任务的步数和任务量，而且每一步的输入都比上一步长（历史在增长）。用下面的计算器体会各个参数的杠杆大小。单价请填你所用模型的官方价格，默认值只是示例：

Agent 成本计算器
缓存读取缓存写入输出

玩一会儿你会发现几个规律：

  • 步数的影响是超线性的：历史每步增长，总输入 ≈ 步数 × 首步输入 + 增长 × 步数² / 2。把 8 步的任务做成 30 步，成本远不止翻四倍。
  • 命中率从 0 到 85%，常常比换一个便宜一档的模型省得更多，而且不损失质量。
  • 输出 token 单价高，但在 agent 里通常不是大头——除非你开了很高的推理强度。

一个 agent 平均每个任务走 20 步，系统提示加工具定义约 1 万 token，开发者发现缓存命中率接近 0。最可能的原因是？

  1. 输出太长
  2. 温度设得太高
  3. 任务步数太多
  4. 系统提示或工具定义里有每次请求都会变化的内容，或工具顺序不固定
前缀匹配要求开头完全一致。命中率接近 0 几乎总是因为前缀的最前面在变：时间戳、请求 ID、工具列表顺序、序列化键序。步数多反而会让命中带来的节省更明显。

8 · 延迟从哪里来

组成主要取决于怎么优化
首 token 时间（TTFT）输入长度、是否命中缓存、服务端排队缩短与稳定前缀、提高缓存命中
生成时间输出 token 数（含推理 token）÷ 生成速度限制输出长度、简单任务降推理强度、换更快的模型
工具执行外部 API、数据库、网页并行执行互不依赖的只读工具、缓存工具结果
步数任务需要几轮循环更好的工具（一次调用拿到够用的信息）、预取上下文

agent 的端到端延迟 ≈ 步数 × (TTFT + 生成时间 + 工具时间)。所以减少步数往往是最大的延迟优化：Anthropic 在多智能体研究系统里通过改写工具描述，让完成任务的时间下降了 40%；把互相独立的检索改为并行后，复杂查询的耗时最多下降 90%（2025-06-13）。

9 · 模型怎么选：分级、路由与回退

分级

不要全系统只用一个模型。把调用按难度和频率分级：

  • 高频简单（分类、分诊、格式转换）：小而快的模型，低推理强度。
  • 核心判断（综合多方信息起草回复、规划多步任务）：能力强的模型。
  • 后台批处理（夜间整理记忆、编译知识库）：对延迟不敏感，可以用强模型配合批处理接口，或者用便宜模型多跑几遍。

第 1 章的路由模式就是分级的落地：先用小模型判断一条请求属于哪一级，再交给对应的模型。路由本身也要评测——把难题错分给小模型的代价，往往比省下的钱更大。

回退


type ModelRef = string;

// 认证失败、配额用尽、限流、5xx、网络错误：换一个模型可能就好了。
// 输出不符合 schema：换模型不一定好，应该在同一模型上带着错误信息重试（第 3 章）。
function isFallbackWorthy(err: unknown): boolean {
  const status = (err as { status?: number }).status;
  if (status === 401 || status === 403 || status === 429) return true;
  if (status !== undefined && status >= 500) return true;
  return err instanceof TypeError; // fetch 的网络错误
}

export async function withFallback<R>(refs: ModelRef[], fn: (ref: ModelRef) => Promise<R>): Promise<R> {
  let last: unknown;
  for (const ref of refs) {
    try {
      return await fn(ref);
    } catch (err) {
      if (!isFallbackWorthy(err)) throw err;
      console.warn(`模型 ${ref} 调用失败，切换下一个`, err);
      last = err;
    }
  }
  throw last;
}
回退的两个陷阱
  • 有副作用的步骤不要整轮回退。如果 agent 已经执行过发邮件之类的工具，换个模型从头重跑会再发一遍（第 4、10 章）。
  • 回退会改变缓存与行为。备用模型没有你的缓存，提示词也可能需要适配。回退应该被记录、被监控，而不是悄悄发生。

预算

给系统设日/月花费上限，在每次调用之前检查。超限时不要直接丢弃工作：新的输入照常收录，未完成的分析在额度恢复后补上。这让"钱花完了"成为一个可预期的降级状态，而不是一场事故。

模型返回的 JSON 连续两次不符合 schema，下面哪个处理最合适？

  1. 在同一模型上带着具体的校验错误重试，达到上限后报错，记录 trace 留作评测用例
  2. 立刻回退到另一个厂商的模型
  3. 把 temperature 调到最高再试
  4. 忽略校验错误，按字符串截取需要的字段
schema 校验失败通常是提示词、schema 设计或任务难度的问题，把错误信息回灌给模型让它自我修正最有效（第 3 章的模式）。持续失败应当暴露出来并成为评测用例，而不是被回退或"宽松解析"掩盖。
真实项目复盘

本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

  • N11 · niuma 曾一天 407 万输入 token 只命中 3072 个缓存；个人档案仍放在静态规则之前，一改就破坏前缀缓存
本章要点
  • 一切以 token 计：计费、窗口、延迟。记录每次调用的 usage。
  • 上下文越长，模型越难用好它（context rot），上下文是稀缺资源。
  • 模型无状态：历史、压缩、持久化都是你的责任。
  • 采样参数与推理强度按任务调；先补上下文，再加推理。
  • 提示缓存靠前缀匹配：稳定的放前面、变化的放后面、只追加不改写、序列化要确定。
  • agent 成本随步数超线性增长；缓存命中率与步数是两大杠杆。
  • 分级用模型；只在认证/配额/网络类错误上回退；设预算并优雅降级。
