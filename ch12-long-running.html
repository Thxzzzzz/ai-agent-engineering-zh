长任务与编码 Agent 的驾驭

让 agent 回答一个问题只要几秒；让它实现一个功能、修完 CI、处理完评审意见，可能要几小时、跨好几个会话。这一章讲怎样给长任务搭一副"驾驭器"（harness），以及当你要编排的是现成的编码 agent 时，哪些工程手段能让它可控、可追踪、可收尾。

约 45 分钟前置：第 4、5、8、10 章含 1 个分步动画、1 个模拟器、3 道小测
学完你能
  • 说清 harness 由哪些部件组成，以及"拆掉不再承重的组件"的含义
  • 识别长任务的两类典型失败，并用功能清单、进度文件、端到端验证去对付它们
  • 用 headless 模式调用编码 agent，拿到结构化结果与会话 ID，并能续跑
  • 用 git worktree 隔离并行任务，用 hooks 写确定性的守门逻辑
  • 设计一个从授权、执行、跟进到收尾的完整任务生命周期，用 git 和 CI 而不是 agent 自述判断进度

1 · Harness：模型之外的一切

同一个模型，放在不同的"外壳"里，表现可以天差地别。这个外壳就叫 harness（驾驭器）：循环本身、工具集、上下文管理（压缩、笔记、子 agent）、权限与审批、持久化、验证手段、以及会话之间如何交接。可以粗略地写成：

Agent = 模型 + Harness。模型决定"能想到什么"，harness 决定"能稳定地做成什么"。

Harness 不是越多越好。Anthropic 在 2026-03 的《Harness design for long-running application development》里描述过一个演化：他们先为长任务加了"sprint 合同"等机制，等到更强的模型出现后，又把 sprint 删掉了。原则只有一句——拆掉不再承重的组件。每个 harness 部件都在弥补模型的某个短板；短板消失了，部件就成了负担：多余的 token、多余的延迟、多余的出错点。

把 harness 当成"假设清单"来维护

给每个部件写下它在弥补什么："进度文件——因为新会话不记得上次做到哪""端到端验证——因为模型会在单测通过后就宣布完成"。模型升级后，用第 13 章的评测逐项去掉、对比结果。假设不再成立的部件，删。

2 · 长任务的两类失败

Anthropic 在 2025-11-26 的《Effective harnesses for long-running agents》里，让 agent 从零构建一个完整的应用，观察到两类反复出现的失败：

失败表现根因
一次做太多想在一个会话里做完整个应用，上下文中途耗尽，留下一堆半成品，下一个会话面对的是一个说不清状态的代码库上下文窗口是有限的；agent 不会自己控制每次的工作量
过早宣布完成看到部分功能能跑，或单元测试、curl 通过，就宣布"全部完成"，实际上端到端用不了没有客观的完成标准；agent 倾向于对自己的工作乐观

这两类失败和模型"聪不聪明"关系不大，它们是结构性的：没有外部记忆，就无法跨会话接力；没有外部验证，就无法可信地判断完成。所以解法也是结构性的。

3 · 跨会话接力：Initializer + Coding Agent

同一篇文章给出的方案是两个角色，它们的系统提示和工具完全相同，只有第一条提示不同：

  • Initializer 只运行一次：搭好环境，写出 init.sh（启动开发环境、跑基本测试的脚本）、进度文件，做第一次 git 提交，并把需求展开成一份 JSON 格式的功能清单——文中的例子超过 200 条，初始全部标记为未通过。
  • Coding agent 每个会话只做一个功能，做完提交，并在进度文件里写一段摘要。

[
  {
    "id": "export-filter-01",
    "description": "月报导出页可以按部门筛选，默认显示全部部门",
    "steps": ["打开月报页", "在部门下拉框选择一个部门", "点击导出", "下载的 CSV 只含该部门的行"],
    "passes": false
  },
  {
    "id": "export-filter-02",
    "description": "筛选条件为空时导出按钮置灰并提示原因",
    "steps": ["清空月份", "导出按钮不可点击", "悬停显示'请先选择月份'"],
    "passes": false
  }
]

几个看似细小、实际关键的设计：

  • 用 JSON 而不是 Markdown：模型更不容易随手改写 JSON 的结构。规则是 coding agent 只许改 passes 字段，不许删改功能描述和测试步骤——否则"让测试通过"最省事的办法就是改测试。
  • 每次开工的固定流程：确认工作目录 → 读 git log 和进度文件 → 从清单里挑优先级最高的未通过功能 → 运行 init.sh 和基本的端到端测试，先确认环境是好的，再开始新工作。
  • 明确要求端到端验证：文中用浏览器自动化工具（Puppeteer MCP）像真实用户一样点一遍。没有这条要求时，模型经常跑完单测或 curl 就宣布功能完成。

为什么功能清单要求 coding agent "只许改 passes 字段"？

  1. 为了让 JSON 文件更小，节省 token
  2. 防止 agent 通过修改或删除验收标准来"完成"任务
  3. 因为 JSON 不支持修改其他字段
  4. 为了让多个 agent 可以同时写这个文件
验收标准是"外部的、客观的完成定义"，一旦允许 agent 修改，它就既是运动员又是裁判。这和第 13 章评测里"不要让被测系统接触评分逻辑"是同一个原则。

4 · 把评估者独立出来

2026-03 的后续文章把角色拆成了三个，灵感来自生成对抗网络（GAN）：

角色职责
Planner把需求拆成若干 sprint，每个 sprint 开始前与 generator 约定"合同"：做什么、怎么验收、硬性阈值
Generator按合同实现
Evaluator用 Playwright 像真实用户一样实测，按合同判定是否通过；不通过则给出具体意见

为什么要独立？因为让同一个 agent 评估自己的工作，它会倾向于宽容；一个独立的评估者更容易被调成"持怀疑态度"的角色。代价也很直观：文中同一个任务，单个 agent 直接做花费约 9 美元，但核心功能不可用；完整的 planner/generator/evaluator harness 花费约 200 美元，产出能真正使用。

这组数字值得反复体会：便宜但不可用的结果，成本是无穷大。同时也提醒你，harness 的每个部件都有价格，要用评测证明它值得。

5 · 大脑与手分离

当 agent 从"在你电脑上跑一会儿"变成"在服务端长时间运行的产品"时，架构会再变一次。Anthropic 在 2026-04 的《Scaling Managed Agents: Decoupling the brain from the hands》里把系统拆成三块：

  • 工具接口统一成 execute(name, input) → string：harness 不关心手在哪里、是什么。
  • Harness 无状态：所有状态都在 session 的事件日志里，进程崩了用 wake(sessionId) 接着跑——这和第 10 章"状态机 + 持久化"是同一个思想。
  • 按需创建容器：只在真正要执行时才起沙箱，首个 token 的延迟中位数降低约 60%，p95 降低超过 90%。
  • 凭据不进沙箱：沙箱里跑的是模型生成的代码，凭据经代理从凭据库取用，模型永远看不到原文。

OpenAI 在 2026-04-15 对 Agents SDK 的升级走的是同一个方向：harness 与计算分离、原生沙箱、凭据不进沙箱、支持快照与恢复。两家不约而同，说明这已经是长任务 agent 的标准架构。

6 · 编排现成的编码 agent

多数时候你不会从零写一个编码 agent，而是编排一个现成的：Claude Code、OpenAI Codex 等。你的程序负责接需求、准备环境、启动 agent、跟进进度、汇报结果；编码 agent 负责在仓库里干活。这时你写的就是一个"外层 harness"。

Headless 调用：把编码 agent 当成一个函数

官方还建议脚本调用 Claude Code 时加 --bare，并说明它将来会成为 -p 的默认行为。下面是一个用 Bun 启动编码 agent、拿回结构化结果的写法（参数细节以各自 --help 和官方文档为准）：


// 让编码 agent 在指定 worktree 里工作，并要求它用固定结构汇报结果
const ReportSchema = {
  type: 'object',
  properties: {
    status: { type: 'string', enum: ['done', 'blocked', 'needs_input'] },
    summary: { type: 'string' },
    questions: { type: 'array', items: { type: 'string' } },
  },
  required: ['status', 'summary', 'questions'],
  additionalProperties: false,
};

export async function runCodingAgent(opts: { worktree: string; prompt: string; resume?: string }) {
  const args = [
    'claude', '-p', opts.prompt,
    '--output-format', 'json',
    '--json-schema', JSON.stringify(ReportSchema),
    '--permission-mode', 'acceptEdits',
    '--allowedTools', 'Read,Edit,Write,Bash(bun test:*),Bash(git:*)',
  ];
  if (opts.resume) args.push('--resume', opts.resume);

  const proc = Bun.spawn(args, { cwd: opts.worktree, stdout: 'pipe', stderr: 'pipe' });
  const [stdout, code] = await Promise.all([new Response(proc.stdout).text(), proc.exited]);
  if (code !== 0) throw new Error(`编码 agent 异常退出（${code}）：${await new Response(proc.stderr).text()}`);

  const out = JSON.parse(stdout);
  return {
    sessionId: out.session_id as string,   // 存下来：之后续跑、交接都靠它
    costUsd: out.total_cost_usd as number, // 记账，第 14 章的预算控制用
    report: out.structured_output,          // agent 的自述，仅供参考，见第 8 节
  };
}
权限要按任务收紧

无人值守运行时，没人能在终端里点"允许"。正确的做法不是一把打开所有权限，而是只放行这个任务需要的工具（如只允许跑测试和 git），其余一律拒绝；真正有风险的动作（推主干、删分支、对外发消息）留给你的编排器在审批后执行。

Worktree：每个任务一个独立的工作目录

同时跑两个编码 agent，如果它们在同一个目录里工作，互相覆盖改动是迟早的事。git worktree 让同一个仓库检出多个工作目录，每个在自己的分支上：


# 从最新主干为任务新开分支和工作目录
git fetch origin
git worktree add ../worktrees/export-filter -b feat/export-filter origin/main

# 任务结束、确认分支已合并或不再需要后再清理
git worktree remove ../worktrees/export-filter
git branch -d feat/export-filter   # -d 只删已合并的分支；未合并时会拒绝，这正是你想要的保护

Claude Code 也内置了这个能力：claude -w <name> 会在 .claude/worktrees/<name> 下、分支 worktree-<name> 上开一个会话（配合 -p 时不会自动清理）。它的后台会话（agent view，2026-05 起的研究预览）会在写文件前自动隔离到各自的 worktree，会推分支、开 draft PR，但从不推主干、不强推、不合并——这几条"从不"，也是你自己的编排器应该遵守的底线。

7 · Hooks：在 agent 生命周期里插入确定性代码

提示词里写"完成前一定要提交代码"，agent 大多数时候会照做，但不是每次。Hooks 让你在 agent 生命周期的特定时刻运行你自己的代码，把"大多数时候"变成"每一次"。Claude Code 的常用事件包括：

事件时机典型用途
SessionStart会话开始注入任务背景、进度摘要
UserPromptSubmit用户提交提示补充上下文、拦截不合规请求
PreToolUse工具执行前按规则 allow / deny / ask / defer
PostToolUse工具执行后自动格式化、记录审计日志
PreCompact压缩上下文前把关键决定写进笔记，防止压缩丢失
Stopagent 准备停下检查是否真的完成，不满足就让它继续

（完整列表目前有三十多个事件，以官方文档为准。）

示例：提交检查

一个非常实用的守卫：agent 停下时如果还有未提交或未推送的改动，就拦下来提醒它一次。


// 从 stdin 读取 hook 输入；输出 {"decision":"block","reason":…} 让 agent 继续工作
const input = await Bun.stdin.json();

// 防死循环：如果这次停止本身就是被 Stop hook 拦下后的继续，就放行
if (input.stop_hook_active) process.exit(0);

const git = (...args: string[]) =>
  Bun.spawnSync(['git', ...args], { cwd: input.cwd }).stdout.toString().trim();

const dirty = git('status', '--porcelain');
const unpushed = git('log', '--oneline', '@{u}..HEAD'); // 无上游分支时为空，这里按"无未推送"处理

if (dirty || unpushed) {
  const reason = [
    '停下前请处理：',
    dirty && `有未提交的改动：\n${dirty}`,
    unpushed && `有未推送的提交：\n${unpushed}`,
    '如果这些改动是有意不提交的，在回复里说明原因后再停下。',
  ].filter(Boolean).join('\n');
  console.log(JSON.stringify({ decision: 'block', reason }));
}
process.exit(0);

三个最常见的 hook 陷阱
  • 退出码 1 不阻断：要阻断必须退出码 2（stderr 作为理由），或者输出 decision: "block" 的 JSON。很多人用 exit 1 以为拦住了，其实什么都没发生。
  • 死循环：Stop hook 每次都 block，agent 就永远停不下来。务必检查 stop_hook_active；系统另有上限，连续续跑 8 次后强制结束（可用 CLAUDE_CODE_STOP_HOOK_BLOCK_CAP 调整），但别依赖它。
  • 多个 PreToolUse 冲突：优先级是 deny > defer > ask > allow，任何一个 deny 都会生效；defer 只在 -p 模式下有意义。

你写了一个 Stop hook，在测试没通过时 exit 1 并在 stderr 打印"测试未通过"。实际运行中 agent 照样停下了。最可能的原因是？

  1. hook 没有执行权限
  2. stderr 的内容太长被截断
  3. 退出码 1 不表示阻断，应该用退出码 2 或输出 decision: "block"
  4. Stop hook 只能在交互模式下生效
这是 hooks 最经典的陷阱：非 0 不等于阻断。退出码 2 才是阻断信号（stderr 会作为理由交给 agent），或者以 0 退出并输出包含 decision: "block" 和 reason 的 JSON。

8 · 相信 git，不相信自述

编码 agent 说"已完成，测试全部通过"——你应该怎么对待这句话？答案是：当成线索，不当成事实。agent 的自述会有乐观偏差，会遗漏，偶尔也会编。编排器应该自己去读客观状态：


const sh = (cmd: string[], cwd: string) => Bun.spawnSync(cmd, { cwd }).stdout.toString().trim();

export function readProgress(worktree: string, branch: string) {
  const head = sh(['git', 'rev-parse', '--short', 'HEAD'], worktree);
  const dirty = sh(['git', 'status', '--porcelain'], worktree) !== '';
  const prJson = sh(['gh', 'pr', 'view', branch, '--json', 'url,state,reviewDecision,statusCheckRollup'], worktree);
  const pr = prJson ? JSON.parse(prJson) : null;
  const checks: { conclusion: string | null }[] = pr?.statusCheckRollup ?? [];
  return {
    head,
    dirty,
    prUrl: pr?.url ?? null,
    ci: checks.length === 0 ? 'none'
      : checks.some((c) => c.conclusion === 'FAILURE') ? 'failed'
      : checks.every((c) => c.conclusion === 'SUCCESS') ? 'passed' : 'running',
    reviewDecision: pr?.reviewDecision ?? null, // 例如 CHANGES_REQUESTED
  };
}

有了这些客观信号，"完成"就可以被定义成可检查的条件：有 PR、没有未提交改动、CI 全绿、没有待处理的评审意见、验收点逐条对照过。只有满足条件，编排器才去通知人；不满足，就把具体差距（哪个检查失败了、评审意见原文）回传给 agent 继续做。

9 · 一个任务的完整生命周期

把前面的部件串起来，看一个"给月报导出加部门筛选"的开发任务从开始到收尾经过了哪些环节。注意每一步是谁在做决定：

编码 agent 在结构化汇报里写 status: "done"，但编排器读到 PR 的 CI 还在运行中。编排器最合理的做法是？

  1. 暂不通知人，等 CI 结束；失败就把失败详情回传给同一个会话继续修
  2. 立即通知人"任务已完成"，因为 agent 说完成了
  3. 立即关闭 agent 并删除 worktree，节省资源
  4. 让 agent 自己去改 CI 配置，让检查更快通过
agent 的自述是线索，客观状态才是事实。完成的判定应该是可检查的条件，CI 还没结束就不满足条件。选项 4 是"改测试来通过测试"的变体，必须禁止。

11 · 交接与收尾

换一个 agent 接手

有时需要中途换 agent：当前 agent 卡住了、想换一个更擅长的、或者原会话已经无法恢复。交接的要点是把接手者需要的上下文显式地交给它，并让它先核对现场：


const handoffPrompt = `
你将接手一个进行到一半的开发任务。
## 原始需求
${task.requirement}
## 验收点
${task.acceptance.map((a, i) => `${i + 1}. ${a}`).join('\n')}
## 当前状态（由编排器从 git / CI 读取，不是上一个 agent 的自述）
分支：${progress.branch}，最新提交：${progress.head}，PR：${progress.prUrl ?? '尚未创建'}，CI：${progress.ci}
## 最近发生的事
${recentEvents.join('\n')}
## 开始前请先
1. 运行 git status 和 git log -5，核对上面的状态，并检查是否有未提交的改动。
2. 如有未提交的改动，先判断它们是否属于本任务，再决定提交还是询问。
`;

一个稳妥的细节：确认新 agent 已经成功启动并收到了交接提示之后，再关闭旧的那个、更新任务记录。顺序反过来，一旦新 agent 启动失败，任务就无人负责了。

收尾

  • 收尾是一个有破坏性的动作（删目录、删分支），要有闸门：分支已合并、工作区干净、没有开着的 PR——任何一条不满足就停下来问人。
  • 不是编排器创建的目录（比如用户手工检出的）一律保留。
  • 把会话记录、花费、最终状态归档。失败的任务尤其要留着：它们是第 13 章评测集最好的来源。

12 · 常见反模式

  • 一个会话做所有事：上下文中途耗尽，留下说不清的半成品。每个会话只做一件事。
  • 让 agent 自己判定完成：没有外部的、不可修改的验收标准，"完成"就只是一种心情。
  • 相信自述："测试都通过了"——去读 CI。
  • 所有权限一把打开：无人值守不等于无限授权。按任务放行最小工具集，推主干、合并、删除留给审批后的编排器。
  • 多个 agent 共用一个工作目录：用 worktree 隔离。
  • Stop hook 无条件阻断：没有 stop_hook_active 判断，agent 永远停不下来。
  • 只加不减的 harness：模型升级后不重新评估，harness 越来越重、越来越慢。
真实项目复盘

本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

  • D5 · devtask 的"完成"由模型用自由文本宣布
  • D6 · devtask 没用 headless/ACP 持有会话
  • N10 · niuma 的交付通知只要带任意链接就算有"客观证据"
本章要点
  • Agent = 模型 + harness；harness 的每个部件都在弥补一个模型短板，短板消失就拆掉。
  • 长任务的两类失败：一次做太多、过早宣布完成。对策：功能清单（只许改 passes）、进度文件、每会话一个功能、强制端到端验证、独立评估者。
  • 长时间运行的 agent 走向"大脑（无状态 harness）/ 手（沙箱）/ 会话（事件日志）"三分，凭据不进沙箱。
  • 编排编码 agent：headless 调用拿结构化结果与会话 ID；worktree 隔离；hooks 写确定性守门；退出码 2 才阻断。
  • 授权后才启动，用 git 与 CI 判断进度，满足客观条件才通知人，收尾前有闸门。
