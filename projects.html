跟练项目：一个仓库，长成一套 agent 系统

读懂原理只是一半。七个跟练项目都在同一个仓库 agent-lab 里累积：后一个项目直接复用前一个的代码，最后长成一个有审批、有记忆、接得上 MCP、有评测、能驾驭编码 agent 的系统——这就是你作品集里的第一件作品。

总计约 18 小时语言：TypeScript（Bun 运行时）全部可以离线跑测试
这一页帮你
  • 看清七个项目的先后关系，以及各自练的是哪几章的能力
  • 把开发环境搭好：Bun、TypeScript、zod、目录约定、环境变量
  • 理解"假模型"测试法：为什么 agent 代码也能写确定性的单元测试
  • 知道怎么接一个真实模型，以及怎么把这个仓库包装成作品

1 · 成长路线

点任意一个节点进入项目页。箭头方向就是推荐顺序：每个项目都假设你已经做完了它前面的那个。

完整参考实现在仓库的 agent-lab/ 目录

P1–P7 的全部代码都已在一个统一的 agent-lab 项目里实现并跑通：bun test 全部通过、tsc 严格模式无错，各项目页里的代码就是从它直接生成的。建议先按页面自己写，卡住了再对照；运行方式见 agent-lab/README.md。

2 · 七个项目一览

约 1.5 小时P1 · 100 行写一个 Agent练：agent loop、工具定义与参数校验、错误回灌、路径穿越防护、厂商适配器。
产出：能查时间、算数、读笔记的命令行 agent。 约 2 小时P2 · 工单分诊管线练：结构化输出、校验重试、路由、提示词版本、去抖合批。
产出：把一批工单变成"摘要 + 待办 + 追问 + 回复草稿"。 约 2.5 小时P3 · 提案与审批练：状态机、事务性发件箱、幂等键、崩溃恢复、自动化策略与护栏。
产出：一个"不批准就不发、批准两次也只发一条"的 CLI。 约 2.5 小时P4 · 长期记忆模块练：事实抽取、ADD/UPDATE/INVALIDATE、双时间轴、检索打分、反思提案。
产出：会记事、会改口、不乱记的记忆库。 约 2 小时P5 · MCP Server 与接入练：MCP 协议、工具暴露、客户端接入、权限边界。
产出：把自己的能力做成任何 agent 都能用的 MCP 服务。 约 2.5 小时P6 · 评测流水线练：错误分析、评测集、代码判官与模型判官、pass^k、回归。
产出：改一行提示词就能看到分数变化的评测命令。 约 2.5 小时P7 · 编码 Agent 驾驭器练：长任务驾驭、进度文件、验收闸门、隔离工作区。
产出：把任务派给编码 agent 并自动验收的驾驭器。 自定毕业项目把上面的部件组合成一个完整产品，配齐文档、评测数字与演示。

3 · 环境准备

  1. 安装 Bun 1.3 以上。Bun 同时是运行时、包管理器和测试框架，TypeScript 不用编译就能直接跑。安装方式见 bun.sh，装好后 bun --version 确认版本。
  2. 初始化仓库。 
    
mkdir agent-lab && cd agent-lab && git init
bun init -y                     # 生成 package.json、tsconfig.json；删掉它附带的 index.ts 和示例文件
bun add zod                     # 参数与输出的 schema（zod 4，自带 z.toJSONSchema）
bun add -d typescript @types/bun
mkdir -p src/models src/triage src/store src/memory tests notes prompts
  3. 用下面的 tsconfig.json 和 package.json 覆盖生成的版本。严格模式全开，noUncheckedIndexedAccess 会逼你处理"数组里可能没有这一项"——模型返回的数据尤其需要。 
    
{
  "compilerOptions": {
    "target": "ESNext",
    "module": "Preserve",
    "moduleResolution": "bundler",
    "lib": ["ESNext"],
    "types": ["bun"],
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "verbatimModuleSyntax": true,
    "allowImportingTsExtensions": true,
    "noEmit": true,
    "skipLibCheck": true
  },
  "include": ["src", "tests", "mcp-server", "evals", "harness"]
}

    
{
  "name": "agent-lab",
  "type": "module",
  "private": true,
  "scripts": {
    "test": "bun test",
    "typecheck": "tsc --noEmit -p .",
    "agent": "bun run src/main.ts",
    "triage": "bun run src/triage/main.ts",
    "cli": "bun run src/cli.ts"
  },
  "dependencies": {
    "zod": "^4"
  },
  "devDependencies": {
    "@types/bun": "latest",
    "typescript": "^7.0.2"
  }
}
    TypeScript 6 起 types 默认为空

    不写 "types": ["bun"] 的话，tsc 会报找不到 process、fetch、AbortSignal。Bun 运行时不看类型，所以 bun test 能过、bun run typecheck 却挂——两个都要跑。

  4. 准备环境变量。复制成 .env 并填好（Bun 会自动读取项目根目录的 .env）。.env 加进 .gitignore，密钥永远不进仓库。 
    
# 任意 OpenAI Chat Completions 兼容端点：云厂商、模型网关，或本机推理服务
LLM_BASE_URL=https://api.example.com/v1
LLM_API_KEY=替换成你的密钥
LLM_MODEL=替换成模型名
  5. （可选）装一个格式化与检查工具，比如 Biome：bun add -d @biomejs/biome。不装也不影响任何项目。

4 · 假模型：让 agent 代码也能写确定性测试

agent 难测，是因为模型的输出不确定。但仔细看，你写的代码里真正需要测的几乎都不是模型，而是"模型回了某种东西之后，你的代码怎么处理"：工具名写错了怎么办、参数不合法怎么办、拒答怎么办、输出被截断怎么办、同一个动作批准两次怎么办。

所以每个项目都依赖同一个 FakeModel：你给它一份"剧本"（第 1 次回什么、第 2 次回什么），它按顺序演出，同时把每次收到的请求存下来，测试再断言"模型第二轮看到了什么"。

写测试前先说清它拦什么

每个项目页的测试都写明了"这个测试拦的是哪种 bug"。好测试的标准是：一个合理的错误改动会让它失败，而一次正确的重构不会。说不出它拦什么的测试，就不写。

5 · 接一个真实模型

P1 会写一个 OpenAI Chat Completions 兼容接口的适配器。这套接口是事实上的通用格式：大多数模型厂商、模型网关，以及 Ollama、vLLM、LM Studio 这类本机推理服务都提供它。你有三种选择：

方式LLM_BASE_URL 示例适合
云端模型服务厂商文档给出的 …/v1 地址效果最好，按量付费；评测时用它
模型网关网关地址一个密钥切换多家模型，方便做模型对比
本机推理服务Ollama 默认 http://localhost:11434/v1零成本、数据不出本机；小模型的工具调用能力弱，适合调通流程
选一个支持工具调用的模型

P1 起所有项目都依赖工具调用（function calling）。本机小模型要确认它的模型卡写明支持 tools；不支持的模型会直接无视工具定义，你会看到 agent 一轮就"答完"了。

6 · 把仓库变成作品

面试官和合作者看作品时，最想知道的是三件事：你解决了什么问题、你的设计取舍、你怎么证明它是好的。做完七个项目后，按下面的清单整理 agent-lab：

  • README 第一屏：一句话说清它做什么、一张架构图、一段 30 秒的演示录屏或 GIF。
  • 设计决策记录（ADR）：每个关键取舍一页，写"背景、选项、决定、后果"。比如"为什么用单一工具做结构化输出""为什么自动更新用失效而不是删除"。
  • 评测数字：P6 的评测集规模、通过率、pass^k，以及一次"改了什么、分数怎么变"的前后对比。
  • 失败故事：挑两三个你在 trace 里抓到的真实失败，写清现象、根因和修法。这比任何功能列表都更能说明你的水平。
  • 安全与边界：写明哪些动作需要审批、哪些数据不出本机、提示注入怎么防。
  • 一键复现：bun install && bun test 不需要任何密钥就能全绿。

P3 里有一个测试叫"同一条提案批准两次，只发出一条"。下面哪种改动会让它失败——也就是说，它拦的是哪种 bug？

  1. 把提案 id 从 8 位改成 12 位
  2. 把发件箱的表名从 outbox 改成 send_queue（同时改好所有引用）
  3. 批准时不再检查提案当前状态，并且幂等键改成每次随机生成
  4. 把发送失败的退避时间从 200ms 改成 500ms
前两个和最后一个是正确的重构或调参，测试不该、也不会失败。第三个让第二次批准又写进一条新的发件记录，对方会收到两条——这正是这个测试要拦的 bug。它锁的是行为（"只发一条"），不是实现细节（表名、id 长度）。
本页要点
  • 七个项目在同一个仓库里逐步生长，后一个复用前一个。
  • 单元测试一律用 FakeModel：测的是你的代码如何应对模型的各种输出，确定且免费。
  • 真实模型走 OpenAI 兼容接口，云端、网关、本机推理服务都能接；选支持工具调用的模型。
  • 作品集的核心是：问题、取舍、证据（评测数字与失败故事）。
