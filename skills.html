级别怎么划

初级 能独立做出一个能跑的 agent；中级 能让它在真实用户面前稳定、可控、可测；高级 能设计整套系统、做关键取舍、在模型和规范变化时判断哪些脚手架该拆该留。高级工程师不需要每条都勾满，但不应该有整块空白的能力域。

16 · 面试常见问题

下面是系统设计与原理题，先自己口述一遍答案，再展开看要点。答得出要点只是及格，能结合自己做过的项目举例才是加分项。

1. workflow 和 agent 的本质区别是什么？什么时候该用 agent？
  • 区别在于控制流由谁决定：workflow 由代码预先定义路径，agent 由模型在运行时决定下一步和用哪个工具。
  • 步骤数事先未知、需要看中间结果才能决定下一步时才用 agent；否则优先一次调用或 workflow，更便宜、可预测、好测。
  • 加分：提到 agent 的 token 成本（单 agent 约为对话的 4 倍、多 agent 约 15 倍）与复合误差。
2. 手写一个 agent loop，需要处理哪些边界情况？
  • 最大步数与超限后的收尾（要求模型直接作答或报错）。
  • 工具不存在、参数校验失败、执行出错：都以错误结果回灌，让模型自己修正。
  • 并行工具调用：每个 tool_call 都要有对应的 tool_result。
  • 中途取消、超时、预算上限；已执行写操作后不能整轮重放。
3. 如何让模型稳定输出符合 schema 的 JSON？
  • 优先用提供商的 strict 结构化输出或 strict 工具；schema 遵守限制（全部 required、additionalProperties:false、可选用 null 联合）。
  • 本地仍要校验：拒答、输出被截断（max_tokens）时可能不符合 schema。
  • 校验失败把具体错误回灌给模型重试，限制次数；跨提供商时"单一工具 + strict + 校验重试"行为最一致。
4. 什么是上下文工程？和提示词工程有什么不同？
  • 上下文工程是在每次推理时挑选、维护"最优的 token 集合"，包括系统提示、工具、示例、历史、检索结果、记忆；提示词工程只是其中一部分。
  • 关键概念：context rot、注意力预算、just-in-time 检索、压缩、结构化笔记、子 agent 隔离。
  • 工程手段：稳定前缀提高缓存命中、只追加不改写、错误留在上下文里。
5. 提示缓存为什么会失效？怎么设计提示词结构来提高命中率？
  • 缓存按前缀匹配：tools → system → messages，任何一层的改动都会让后面全部失效。
  • 常见坑：系统提示里放时间戳、每次重排工具顺序、改写历史消息、序列化顺序不确定。
  • 做法：静态内容在前、动态内容在后；只追加；工具列表固定顺序。用 usage 里的缓存读取 token 监控命中率。
6. 设计一个个人助理的长期记忆系统。
  • 分类型：常驻的小档案（身份、偏好）+ 可检索的事实条目 + 情景记录；程序性记忆可以落到提示词规则。
  • 写入：抽取 → 与相似记忆比对 → ADD / UPDATE / DELETE / NOOP；每条带来源、可追溯可删除。
  • 时间：事实有效期与写入时间分开，矛盾时旧事实失效而不删。
  • 读取：近因、重要性、相关性加权或混合检索；离线整理（反思）纠错；常驻部分保持很小。
  • 评测：LongMemEval、LoCoMo 这类基准考察的能力（时间推理、知识更新、拒答）。
7. 向量检索和 agentic search（让 agent 自己 grep / 读文件）怎么选？
  • 向量检索快、适合大规模语义匹配，但会丢失精确符号和因果关系，索引会过期。
  • agentic search 准确、总是最新，但慢、贵；对代码和结构化文件尤其好用。
  • 常见做法是混合：BM25 + 向量 + RRF，再加重排；或预取一部分、其余让 agent 按需查。知识库足够小时直接整体放进上下文。
8. 什么是提示注入？如何从架构上防御？
  • 模型分不清指令来自用户还是来自它读到的数据，攻击者把指令藏在网页、邮件、文档里。
  • "致命三要素"：私有数据 + 不可信内容 + 对外通信。Agents Rule of Two：一个会话里三项最多占两项，否则需要人审批或换新上下文。
  • 设计模式：Plan-Then-Execute、Dual LLM、Action-Selector、Code-Then-Execute（CaMeL）、Map-Reduce、Context-Minimization。
  • 护栏分类器只能降低概率，"拦住 95%"在安全上是不及格的。
9. 设计一个"经人审批后代发消息"的系统，如何保证不重复发送、不漏发？
  • 状态机：pending → approved → executing → done / failed；只有 approved 能被执行。
  • 批准与发送解耦（outbox），发送带幂等键（如提案 id + 正文哈希），服务端按键去重。
  • 崩溃恢复：残留的 executing 改回待处理并提示人工确认，不自动重发；重试次数有限。
  • 审批界面展示原文依据和将要发出的全文，避免走过场。
10. 自主度应该怎么设计？怎么逐步放权？
  • 按动作风险和对象分别设级别，默认对外动作需审批（审批者级）。
  • 放权基于数据：一段时间内原样批准率高、无撤回才建议升级，且升级本身需要用户确认。
  • 自动执行要可见（简报里列出"替你做了什么"）、可撤回，撤回即降级。
11. 单 agent 还是多 agent？
  • 多 agent 适合广度优先、可并行的读型任务（如调研），代价是数倍 token、更难调试。
  • 写操作和相互依赖的决策要连续：并行写容易产生冲突的隐含决策。
  • 收敛做法：一个 agent 负责写，其他 agent 只贡献"智能"（独立评审、子任务调研、向更强模型求助）。
12. MCP 解决什么问题？它和 A2A、Agent Skills 是什么关系？
  • MCP 标准化"agent 接入工具和数据"，一次实现、多个客户端可用。
  • A2A 解决 agent 与 agent 之间的协作；Skills 是打包给 agent 的"操作手册 + 脚本"，渐进披露以节省上下文。
  • 加分：MCP 工具太多会撑爆上下文，可以把 server 呈现为代码 API 让 agent 写代码调用；2026-07-28 版协议改为无状态。
13. 如何让编码 agent 可靠地完成一个需要几小时的任务？
  • 先由初始化步骤展开 JSON 功能清单（初始都是未通过）、写进度文件和启动脚本、做首个提交。
  • 每次会话只做一个功能：读 git log 和进度 → 选最高优先级未完成项 → 实现 → 端到端验证 → 提交并更新进度。
  • 防"过早宣布完成"：只允许改 passes 字段；用浏览器自动化做端到端验证；Stop hook 检查未提交改动；独立的评估者。
14. 你会怎么为一个 agent 建评测体系？
  • 先做错误分析：读至少几十条真实 trace，归纳失败分类，再决定测什么。
  • 从 20–50 条真实失败起步，每条有参考答案；能用代码判的用代码判，其余每种失败模式一个二元 LLM 判官，用人工标注校准。
  • 同时看 pass^k（稳定性）；能力评测与回归评测分开；每次试验从干净环境开始，评结果不评路径。
15. pass@k 和 pass^k 有什么区别？举个数字。
  • pass@k：k 次里至少成功一次的概率，k 越大越高，适合"多试几次挑一个"的场景。
  • pass^k：k 次全部成功的概率，k 越大越低，反映稳定性，面向用户的 agent 应看它。
  • 单次成功率 75% 时，pass^3 = 0.75³ ≈ 42%。
16. 线上 agent 出了一个错误回答，你怎么排查？
  • 找到那次调用的 trace：用的哪版提示词、模型和参数、完整输入、工具调用及返回。
  • 判断是信息缺失（上下文/检索）、工具问题（描述含糊、返回错误）、指令冲突还是模型能力边界。
  • 修方法而不只是修这个答案：改提示词或工具后，把这条加入评测集，用盲测验证没有引入回归。
17. 如何控制 agent 的成本？
  • 先测量：按功能、按提示词版本统计 token 与花费。
  • 手段：提示缓存（稳定前缀）、路由（简单任务用小模型）、按需开启推理、压缩上下文、限制工具返回量、批处理。
  • 兜底：日/月预算上限，超限时降级而不是崩溃；循环设最大步数。
18. 一个 agent 产品上线前，你的检查清单里有什么？
  • 功能：评测集通过率、pass^k、关键失败模式的判官结果。
  • 安全：威胁建模、最小权限、高风险动作审批、不可信内容的处理方式、敏感数据不进日志。
  • 可靠：幂等、重试与回退、崩溃恢复、超时、预算上限。
  • 可观测：trace、成本看板、告警；可以一键暂停自动动作。
