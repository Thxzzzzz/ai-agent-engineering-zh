检索与知识库

模型缺的往往不是能力，而是信息。检索（retrieval）负责在合适的时刻把合适的资料找出来放进上下文。这一章讲清楚各种检索手段的长短，以及一个常被忽略的上游问题：你要检索的知识，本身是否值得检索。

1 · 第一个问题：真的需要检索吗？

RAG（Retrieval-Augmented Generation，检索增强生成）几乎成了"做 AI 应用"的默认架构。但 Anthropic 在《Introducing Contextual Retrieval》（2024-09-19）里给过一条很朴素的建议：

如果你的知识库小于 20 万 token，可以直接把整个知识库放进提示里，不需要 RAG。配合提示缓存，这样做的成本和延迟都可以接受。

这句话值得反复想。检索系统引入了一整条可能出错的链路：分块切错、embedding 不懂行话、召回漏掉、排序不准、索引过期……每一环都需要调、需要测。如果资料本来就能整个装进上下文，最好的检索就是不检索。

当然，"能装下"还要结合第 5 章的注意力预算一起判断：一份 15 万 token 的资料放进去，模型能用，但每次调用都在为它付费，也在稀释其他信息。常见的折中是：小而常用的资料直接放（最好放在缓存前缀里），大而偶尔用的资料走检索。

2 · 两种召回：关键词与向量

2.1 关键词检索：BM25

BM25 是搜索引擎时代沉淀下来的经典算法：查询词在文档里出现得越多、这个词在整个语料里越少见（越有区分度），文档得分越高，同时对长文档做一定惩罚。它不懂语义，只认字面。

2.2 向量检索：embedding

embedding 模型把一段文字映射成一个高维向量，意思相近的文字向量也相近（余弦相似度高）。它能理解同义改写——"垫付的机票钱怎么要回来"和"差旅报销流程"字面上几乎不重合，向量却很接近。

关键词（BM25）向量（embedding）
擅长精确标识：错误码、型号、人名、项目代号、函数名同义改写、口语化提问、跨表述的语义匹配
失败用户换了个说法就找不到对没见过的专有名词、编号、内部黑话理解很差；"看起来相关"但其实不对
可解释性高：为什么命中一目了然低：很难解释为什么两段文字"相似"
成本建索引便宜，无需模型需要调用 embedding 模型；换模型要整体重建索引
结论：两路都要

它们的失败模式几乎互补。工程上的默认做法是混合检索（hybrid search）：两路分别召回，再融合。下面这个演示可以直观感受两者的差别。

3 · 混合检索与 RRF

两路召回的分数不可比：BM25 分数可能是 12.7，余弦相似度是 0.83。最常用、也最省心的融合方法是 RRF（Reciprocal Rank Fusion，倒数排名融合）——只看排名，不看分数：


// 对每个文档，把它在各路召回里的排名取倒数再求和；k 通常取 60
RRF(d) = Σ_路 1 / (k + rank_路(d))

一个文档在两路里都排得靠前，总分就高；只在一路里出现，也能凭借高排名入围。k 越大，排名之间的差距被抹得越平；原论文推荐 60。Elastic 的实验表明，精心调过权重的分数线性组合有时能比 RRF 更好，但 RRF 的优势是不需要对分数做任何校准，是一个稳健的起点。

    用户在知识库里搜内部系统的错误码"E1043"，纯向量检索返回了一堆"网络问题常见原因"的泛泛文章，真正记录这个错误码的文档没排上来。最直接的改进是？

    1. 换一个维度更高的 embedding 模型
    2. 加一路关键词检索（BM25），与向量检索融合
    3. 把 top-k 从 5 调到 50
    4. 让模型先把查询改写得更"自然"
    错误码、型号这类不透明的标识符，正是 embedding 的弱项、BM25 的强项。把它改写成自然语言反而丢掉了最有区分度的信息。混合检索是解决这类问题的标准做法。

    4 · 上下文化检索与重排

    检索系统还有一个隐蔽的问题：分块会丢失上下文。一篇季度经营报告被切成很多块，其中一块写着"本季度收入比上季度增长 3%"——哪家公司？哪个季度？单独看这一块，embedding 和 BM25 都无从得知，于是搜"2026 年三季度收入增速"时它可能根本排不上来。

    Anthropic 提出的 上下文化检索（Contextual Retrieval）就是针对这个问题。点"下一步"看完整流程：

    不用上下文化检索，也可以先做的便宜改进

    在每个块前面拼上文档标题、章节标题、日期、作者这些元数据。这只是字符串拼接，零模型成本，却能解决一大部分"块丢上下文"的问题。上下文化检索可以看作它的"智能版"。

    5 · Agentic search：让 agent 自己去找

    上面讲的都是预建索引：事先把资料切块、编码、入库，查询时由代码检索一次。另一条路线越来越常见：给 agent 搜索类工具（grep、glob、读文件、全文搜索、数据库查询），让它像人一样边找边读。编码 agent 基本都是这么工作的：不建向量库，用 grep 找符号、打开文件看上下文、顺着引用继续找。

    预建索引（RAG）Agentic search
    检索次数每个问题一次，由代码决定多次，由模型决定
    新鲜度取决于索引多久更新一次总是读到当前的数据
    多跳问题困难："先找到负责人，再找他上周说了什么"自然：根据上一次的结果决定下一次查什么
    延迟与成本低、稳定高、波动大
    失败形态召回漏掉没想到去找、找错地方、过早停止

    近期的实证结果倾向于 agentic 一侧，但要读懂代价：

    • LongMemEval-V2（2026-05）面向 web agent 的记忆评测中，把历史轨迹当作文件、让一个编码 agent 自己去查证据，得到 72.5% 的正确率；最强的 RAG 方案是 48.5%。
    • Anthropic《The components of agent memory》（2026-11）中，"离线整理出的 wiki + 搜索"比"只用搜索"高约 8 个百分点（61% 对 53%），而且每题节省约 2 万 token——说明事先整理好的知识能让 agentic search 更快更准。
    取舍的经验法则

    在线、对延迟敏感、问题模式固定（如"根据这封邮件检索相关制度"）：用预建索引的一次检索。离线、可以多花时间、问题开放或需要多跳（如"整理这个项目过去三个月的所有决定"）：用 agentic search。两者也可以组合：把混合检索本身做成 agent 的一个工具。

    办公助理要回答"上个月和财务部开的那几次会，最后关于预算模板定了什么？"最合适的检索策略是？

    1. 用这句话做一次向量检索，取 top-5
    2. 把过去一个月的所有邮件和纪要都放进上下文
    3. 给 agent 日历查询、纪要搜索、读文档的工具，让它先找出那几次会，再逐个读纪要，最后综合
    4. 只用 BM25 搜"预算模板"
    这是一个多跳问题：先要确定"哪几次会"（日历），再读每次会的纪要，最后综合出"最终定了什么"。一次检索很难同时命中所有环节；全部塞进上下文成本高、噪音大。agentic search 正适合这类开放、多步、可以多花点时间的问题。

    6 · 知识编译：把零散信息变成知识库

    前面讨论的都是"怎么找"。但如果被检索的材料本身是大量零散、重复、互相矛盾的聊天和邮件，再好的检索也只能找出一堆碎片。一个更上游的思路是知识编译：定期把零散的原始材料整理成策展过的知识页面，检索时优先检索这些页面。这正对应第 6 章记忆四层里的"加工后的表示"。

    设计一个编译式知识库时，最重要的几条原则：

    • 每个结论都带来源。页面里写"月报导出由小王负责"，后面必须能追溯到是哪条消息、哪次会议说的。没有来源的结论无法核实，也无法在来源被推翻时一并修正。
    • 事实有生效与失效。和第 6 章一样，"负责人换了"不应该覆盖掉历史，页面可以有一节"历史变更"。
    • 页面是纯文本、可 diff 的。用 Markdown 放在 git 仓库里，每次编译产生的变更可以像代码评审一样逐行审阅后再合入，也能回滚。人和其他 agent 都能读。
    • 原文与结论分开存放。原始消息可能包含隐私，留在本地受控的存储里；知识库只放策展后的结论与引用链接，方便共享。
    • 增量编译，而不是每次全量重写。新材料只触发相关页面的更新；全量重编昂贵，且会让 diff 失去可读性。

    7 · 引用与可追溯

    无论用哪种检索方式，回答时都应当引用来源。这不只是为了让用户放心，更是一个工程手段：

    1. 给每段检索结果编号，例如 [S1]、[S2]，在提示里要求每个事实性结论后标注编号。
    2. 用代码校验引用：回答里出现的编号必须是这一轮真实提供过的；结论引用的原文片段，必须真的出现在对应来源里。校验失败就重试或降级。
    3. 渲染成可点击的链接，让用户一键回到原始邮件或文档。
    
interface Source { id: string; title: string; url: string; text: string }
interface Claim { text: string; sourceIds: string[]; quote: string | null }

// 模型输出的每个结论都必须引用本轮真实提供的来源；带了原文摘录的，摘录必须能在来源里找到
export function checkCitations(claims: Claim[], sources: Source[]) {
  const byId = new Map(sources.map((s) => [s.id, s]));
  const problems: string[] = [];
  for (const c of claims) {
    if (c.sourceIds.length === 0) problems.push(`没有引用来源：${c.text}`);
    for (const id of c.sourceIds) {
      const src = byId.get(id);
      if (!src) problems.push(`引用了不存在的来源 ${id}：${c.text}`);
      else if (c.quote && !src.text.includes(c.quote)) problems.push(`摘录不在来源 ${id} 中：${c.quote}`);
    }
  }
  return problems; // 非空时，把问题作为错误回灌给模型重试（第 3 章的校验重试模式）
}

    模型的回答里写着"根据《数据导出权限申请》[S7]，导出个人信息需要主管审批"，但这一轮只提供了 S1–S5 五段资料。正确的处理是？

    1. 相信模型，它可能记得训练数据里的内容
    2. 把 [S7] 从回答里删掉后直接展示
    3. 代码校验出"引用了不存在的来源"，把错误回灌给模型重答，或在多次失败后降级为"未找到依据"
    4. 在提示词里加一句"不要编造引用"就够了
    引用必须由代码校验，而不是依赖模型自觉。删掉编号会让一个没有依据的结论看起来像有依据；只改提示词无法保证。校验失败时回灌错误让模型修正，是第 3 章"校验—重试"模式在检索场景的应用。

    8 · 让 RRF 跑起来

    把混合检索落到代码里非常简短。下面的实现把两路召回的结果按 RRF 融合：

    
interface Hit { id: string; score: number }

export function rrf(lists: Hit[][], k = 60, topN = 10): Hit[] {
  const fused = new Map<string, number>();
  for (const list of lists) {
    // 每一路先按自己的分数排序，只用排名参与融合
    [...list].sort((a, b) => b.score - a.score).forEach((hit, i) => {
      fused.set(hit.id, (fused.get(hit.id) ?? 0) + 1 / (k + i + 1));
    });
  }
  return [...fused.entries()]
    .map(([id, score]) => ({ id, score }))
    .sort((a, b) => b.score - a.score)
    .slice(0, topN);
}

// 用法：两路各取 50 个候选，融合后取前 20 个交给重排，再取前 5 个放进上下文

    9 · 新鲜度与维护

    检索系统上线之后，真正的工作才开始：

    • 增量更新与删除。文档改了要重建对应的块；文档删了，索引里的块也要删——"已经作废的制度还被检索出来"是最常见的线上事故之一。
    • 换 embedding 模型要全量重建。不同模型的向量空间不兼容。为此在每条向量旁边记下模型名与版本。
    • 权限要在检索层生效。用户不该看到的文档，不能先检索出来再让模型"别说"。按用户权限过滤候选，必须发生在放进上下文之前。
    • 单独评测检索。准备"问题 → 应命中的文档"标注集，持续跟踪召回率（recall@k）。检索的问题和生成的问题要分开定位（第 13 章）。

    10 · 反模式

    • 小知识库也上向量库：资料能装进上下文时，检索只会增加出错环节。
    • 只用向量检索：编号、人名、代号这类查询会系统性地失败。
    • 分块不带任何上下文：块里只有"增长 3%"，没有标题、日期、出处。
    • 只看最终回答，不看检索：回答错了，不知道是没找到还是找到了没用好。
    • 检索出来的内容当指令执行：文档里写着"忽略之前的指令……"，它仍然只是数据（第 9 章）。
    • 没有引用：用户无法核实，你也无法自动校验。
    真实项目复盘

    本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

    • N14 · niuma 的知识库没有基线就两天连升四版格式，中文仍按空白切词
    本章要点
    • 知识库小于约 20 万 token 时，先考虑直接放进提示（配合缓存），而不是建检索系统。
    • BM25 擅长精确标识，向量擅长语义改写；两者互补，默认用混合检索，RRF（k=60）是稳健的融合起点。
    • 分块会丢上下文：至少拼上元数据，进一步用上下文化检索；粗召回之后用重排精选。
    • Agentic search 新鲜、能多跳，但更慢更贵；事先整理好的知识能让它更快更准。
    • 知识编译把零散材料变成带来源、可 diff、可审阅的页面；回答必须带引用并由代码校验。
