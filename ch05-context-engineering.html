上下文工程

模型是无状态的，它每一轮"知道"的东西，全部来自你这一轮塞给它的上下文。上下文工程就是回答一个问题：在有限的窗口里，这一刻放什么、按什么顺序放、什么时候扔掉。这是 agent 质量、成本和延迟的总开关。

约 40 分钟前置：第 2、4 章含 1 个分步动画、1 个交互、3 道小测
学完你能
  • 解释 context rot 与"注意力预算"，说明为什么上下文不是越多越好
  • 按"稳定在前、易变在后"组装上下文，让提示缓存真正命中
  • 在预加载与即时检索（just-in-time）之间做取舍，控制工具返回的体积
  • 为长任务选择压缩、结构化笔记、子 agent 隔离三种手段
  • 写出一个有预算、有截断、顺序可控的上下文组装器

1 · 从提示词工程到上下文工程

早期大家讨论的是"提示词怎么写"：措辞、角色、示例。到了 agent 时代，一次任务要跑几十轮，每一轮的输入里，你亲手写的系统提示可能只占一小部分，其余是对话历史、工具定义、工具返回、检索结果、记忆、文件内容……这些东西的总和才决定模型这一轮看到了什么。

Anthropic 在《Effective context engineering for AI agents》（2025-09-29）里给了一个工程化的定义：

上下文工程，是在推理时选择并维护最优的 token 集合的一组策略——它的范围比提示词工程更大，包括提示词之外所有进入上下文的信息。

HumanLayer 的《12-Factor Agents》把同一件事说得更直白——第 3 条：Own your context window，自己掌控上下文窗口。不要让框架替你决定往里塞什么、按什么格式塞；上下文就是你和模型之间唯一的接口，它应该是你代码里一个看得见、测得了的产物。

2 · 注意力预算与 context rot

直觉上，窗口越大，塞得越多，模型知道得越多，效果越好。实际不是这样。Anthropic 那篇文章总结了一个被反复观察到的现象——context rot（上下文腐化）：上下文越满，模型从中准确召回某条信息的能力越差。

原因可以从 Transformer 的结构理解：每个 token 都要和其他所有 token 计算注意力，n 个 token 就有 n² 对关系。上下文越长，注意力被摊得越薄；而且模型训练时见到的短序列远多于超长序列，对长距离依赖的处理经验本来就少。所以文章把它比作注意力预算：

把每个 token 当成在花钱

每放进去一个 token，都在消耗模型有限的注意力。目标不是"塞满"，而是找到信号最强的最小 token 集合，让模型最可能做出你想要的行为。

这带来三条直接的工程后果：

  • 大窗口不是免费的午餐。窗口能放下，不等于模型能用好；无关内容会稀释关键信息，还会拉高成本与延迟。
  • "以防万一"地塞信息是有代价的。每一段上下文都应该回答"模型这一轮用得上吗"。
  • 长任务必须有"清理"机制。对话越跑越长是 agent 的天性，必须主动压缩、外置、隔离（第 7 节）。

3 · 系统提示：找到合适的"高度"

Anthropic 用"高度（altitude）"描述系统提示的抽象程度，两个极端都会失败：

太低：硬编码合适的高度太高：空泛
样子写满 if-else 式的规则："如果用户说 A 就回 B；如果邮件来自 C 就……"讲清目标、原则、边界和判断依据，给几个典型例子"你是一个乐于助人的助理，请尽力帮助用户。"
问题脆弱，规则互相打架，覆盖不了没写到的情况，维护成本越来越高——模型拿不到具体信号，只能靠猜，行为不稳定

写好一份系统提示的几条实操建议：

  • 分段并加标题（背景、目标、规则、工具使用指引、输出要求），用 Markdown 标题或 XML 标签分隔，方便模型定位，也方便你维护。
  • 从最小可用版本开始，用真实失败案例驱动增补——每加一条规则，都应该能对应到一个具体的失败。
  • 例子要少而多样：few-shot 用几个有代表性、彼此不同的典型例子，而不是把所有边界情况都列一遍。例子是"画像"，不是"规则表"。
  • 解释原因："不要在回复里承诺具体日期，因为排期由项目经理确认"比"不要承诺日期"更能让模型泛化到相近情形。

办公助理 agent 经常把"仅供参考"的抄送邮件也当成需要回复的邮件。下面哪种改法最符合"合适的高度"？

  1. 在系统提示里加一条：如果邮件标题包含"FYI"就不要回复
  2. 换一个更大的模型
  3. 写明判断原则："只有当发件人在等待你本人的决定、信息或行动时才需要回复；你只在抄送里、或邮件是通知性质时通常不需要"，并给 2–3 个不同类型的例子
  4. 把过去所有被误判的邮件都放进系统提示作为反例
选项 1 是"太低"的硬编码，覆盖不了没写"FYI"的通知；选项 4 会撑爆上下文，还容易让模型机械模仿；选项 2 不解决信号缺失。选项 3 给了判断依据和少量多样的例子，是可以泛化的写法。

4 · 组装顺序：稳定在前，易变在后

上下文里的内容不只有"放不放"的问题，还有"放在哪"的问题。顺序同时影响两件事：

4.1 提示缓存只认前缀

主流模型服务商都提供提示缓存（prompt caching）：如果这次请求的开头和最近某次请求的开头完全相同，这段相同前缀的计算结果可以复用，读取价格只有正常输入的一个零头（截至 2026-11 的官方文档：Anthropic 的缓存读取通常是基础输入价的 0.1 倍或更低，OpenAI 的自动缓存也是同一量级），延迟也明显下降。关键在于：

  • 缓存按前缀匹配。中间任何一个字节变了，从那个位置往后全部失效。
  • Anthropic 的缓存层级顺序是 tools → system → messages，改动前一层会让后面各层一起失效。
  • 所以：越稳定的内容越靠前，越易变的内容越靠后。"当前时间"这种每次都变的东西如果放在系统提示开头，整个缓存就废了。

Manus 团队在《Context Engineering for AI Agents: Lessons from Building Manus》（2025-07-18）里把 KV-cache 命中率称为生产级 agent 最重要的单一指标：他们的 agent 输入与输出的 token 比例约为 100:1（每轮都要重新读入整段上下文，而只输出一个短的工具调用），缓存与未缓存的单价相差 10 倍。他们给出的三条纪律：

  1. 前缀保持稳定：不要在系统提示里放精确到秒的时间戳。
  2. 上下文只追加，不改写：不要回头修改历史里的动作或观察。
  3. 序列化必须确定：同样的对象每次序列化出同样的字节（很多语言的 JSON 序列化不保证键顺序）。

4.2 位置也影响注意力

关键指令放在哪里也有讲究：大段资料放前面，具体任务与问题放在末尾，往往比反过来效果更好；最需要被遵守的约束在末尾再简短重申一次，也能对抗长上下文里的"中间遗忘"。这和缓存的要求恰好一致——易变的、和本轮直接相关的内容放后面。

上下文装箱器

一个办公助理 agent 要处理一封新邮件。勾选要放进上下文的块，用 ↑↓ 调整顺序，观察预算占用和可命中缓存的前缀比例。规则：遇到第一块"每次都变"的内容后，后面的内容都无法命中缓存；"追加型"的历史只有最新一条是新的。

    5 · 预加载，还是即时检索？

    传统做法是预加载：在调用模型前，先把可能相关的资料（检索结果、文档、历史）一股脑查出来放进上下文。Anthropic 观察到越来越多的 agent 转向另一种策略——即时（just-in-time）检索：上下文里只放"引用"（文件路径、查询语句、链接、ID），模型需要时自己用工具去取。

    预加载即时检索
    做法调用前由代码查好、放进上下文上下文只放引用，模型用 grep / 搜索 / 读文件工具按需取
    优点一轮就能答，延迟低；行为可预测上下文干净；信息总是最新的；能逐步探索，处理事先没想到的需求
    缺点容易塞进无关内容；索引可能过期多轮工具调用，更慢更贵；模型可能找错地方或不找
    适合需要的信息可预测、体量小信息量大、需求开放、探索式的任务（如编码）

    实际系统大多是混合的。Anthropic 举的例子是编码 agent：项目说明文件（如 CLAUDE.md、AGENTS.md）在开始时直接放进上下文，其余代码用 glob / grep 按需读取。12-Factor Agents 也有一条附加原则 Pre-fetch all the context you might need：如果你确定模型下一步一定会调用某个工具去拿某个信息，不如由代码提前取好放进去，省掉一轮来回。

    判断口诀

    确定会用的，预加载；可能会用的，给引用；不会用的，不放。对办公助理来说："发件人是谁、和我什么关系"几乎每次都要，预加载；"这个项目三个月前的讨论"可能要，给一个搜索工具；"公司全部制度文档"不放。

    6 · 工具返回：上下文最大的污染源

    在长任务里，占据上下文最多的往往不是你写的提示，而是工具返回：一次列表查询返回几百条记录、一次网页抓取返回整页 HTML、一个日志文件几万行。Anthropic《Writing effective tools for agents》（2025-09-11）给出的做法：

    • 分页、过滤、截断，并设上限。Claude Code 的工具返回默认上限是 25,000 token。截断时告诉模型"还有更多，可以用某参数继续取"。
    • 提供返回详略档位。例如 response_format: "concise" | "detailed"；原文实验中简洁档约只用详细档 1/3 的 token。
    • 返回语义字段，不返回技术 ID。返回人名、标题，而不是一串 UUID；模型用不上的字段只是噪音。
    • 与其包装底层 API，不如设计面向任务的工具。search_contacts(query) 比 list_contacts() 好——后者逼模型把整个通讯录读进上下文再自己找。
    • 错误信息要可执行。"参数 date 格式应为 YYYY-MM-DD，你传的是 '下周三'"比一个堆栈好得多。

    6.1 更进一步：让中间结果根本不进上下文

    Anthropic《Code execution with MCP》（2025-11-04）提出了另一种思路：把工具呈现为一个代码 API（例如文件系统里的 ./servers/drive/getDocument.ts），让 agent 写代码来调用工具、过滤和拼接数据，只把最终需要的结果返回给模型。原文示例里，一个需要在两个系统之间搬运大文档的任务，上下文从约 15 万 token 降到约 2 千 token（节省 98.7%）。代价是你需要一个安全的代码执行沙箱、资源限制和监控（第 9、11 章）。

    agent 需要"找出上个月所有金额超过 5000 元、还没审批的报销单"。工具设计上最好的选择是？

    1. 提供 list_all_expenses()，返回全部报销单，让模型自己筛
    2. 提供 search_expenses(month, min_amount, status, limit)，返回带标题、金额、申请人的精简列表，并提示是否还有下一页
    3. 提供 get_expense(id)，让模型逐个查询
    4. 把全部报销单预加载进系统提示
    筛选应该发生在工具里（你的代码），而不是模型的注意力里。选项 2 把过滤条件做成参数、限制条数、返回语义字段、提示分页，上下文最干净。选项 1 和 4 会把成百上千条无关记录塞进上下文；选项 3 需要模型先知道 ID，且要调用很多次。

    7 · 长任务：压缩、笔记与子 agent

    一个需要几十上百轮的任务（整理一季度的会议纪要、迁移一批文档、修一个复杂的 bug），无论怎么精简，上下文终究会被填满。Anthropic 总结了三种手段，下面的动画演示前两种，以及第三种如何配合：

    手段适合风险与对策
    压缩（compaction）需要大量来回对话、上下文连续性重要的任务摘要丢失关键细节 → 用真实的长 trace 调压缩提示词；先尽量召回（宁多勿漏），再逐步精简；保留引用（路径、链接）而不是内容本身，确保"可恢复"
    结构化笔记有明确里程碑、可以迭代推进的任务笔记变成流水账 → 规定固定结构（目标、已完成、进行中、待决、约定）；笔记要能独立读懂
    子 agent 隔离可以并行、需要大量阅读的探索型子任务子 agent 之间决策冲突、token 成倍增加 → 只让子 agent 做"读"，写操作留在主 agent（第 11 章）

    除了压缩，模型服务商也开始在 API 层提供"上下文编辑"能力：自动清理早期已经用不上的工具返回。Anthropic 在 2025-09-29 公布的内部评测里，仅用上下文编辑就让一项长任务的效果提升 29%，配合记忆工具提升 39%，在 100 轮的搜索任务里 token 消耗下降 84%。这类能力本质上就是本节手段的"托管版"。

    8 · Manus 的六条实战经验

    Manus 是一个通用 agent 产品，它的一个典型任务大约需要 50 次工具调用。他们在 2025-07 发布的经验总结，至今仍是上下文工程最有价值的一手资料之一：

    经验做法背后的原因
    围绕 KV-cache 设计稳定前缀、只追加、确定性序列化；必要时显式标注缓存断点输入输出约 100:1，缓存命中率直接决定成本和首 token 延迟
    屏蔽工具，而不是删除工具定义保持不变，用状态机在解码时屏蔽当前不该用的工具；工具名用统一前缀（如 browser_、shell_）便于成组约束动态增删工具会让缓存失效，且历史里引用了已删除的工具会让模型困惑
    把文件系统当上下文大块内容写进文件，上下文里只留路径；压缩必须是可恢复的（网页内容可丢，URL 要留）文件系统容量无限、持久，且 agent 可以自己读写
    用复述操控注意力让 agent 维护一个 todo.md，每完成一步就重写一遍，把目标"推"到上下文末尾对抗长任务里的目标漂移和"中间遗忘"
    把错误留在上下文里失败的调用和报错信息不要清理掉模型看到失败后会更新判断，减少重复犯同样的错（12-Factor 第 9 条也主张把错误压缩后放回上下文）
    不要被 few-shot 带偏在动作和观察的序列化格式、措辞上引入少量受控变化上下文里全是相同模式的历史，模型会陷入机械模仿，在批量任务里尤其明显
    "屏蔽而不是删除"与"按需加载工具"并不矛盾

    工具很多时（比如接了几十个 MCP 服务），把全部定义常驻上下文本身就是负担。这时的思路是第 11 章的"渐进披露"：先只给模型一个能查找工具的工具，或者像 Agent Skills 那样只放名称和一句描述。关键是常驻部分要稳定，变化发生在上下文末尾。

    9 · 实现：一个有预算的上下文组装器

    把以上原则落到代码里，核心是把"上下文"从散落各处的字符串拼接，变成一个显式、可测试的组装步骤。下面是一个简化但完整的实现思路：

    
// 稳定性决定位置：越稳定越靠前，才能命中提示缓存
type Stability = 'static' | 'session' | 'append' | 'volatile';
const ORDER: Record<Stability, number> = { static: 0, session: 1, append: 2, volatile: 3 };

interface Section {
  name: string;
  stability: Stability;
  text: string;
  priority: number;   // 超预算时先砍 priority 低的
  minTokens?: number; // 允许截断到的最小长度；不设则要么全留要么全砍
}

// 粗略估算：中文约 1 字 ≈ 1 token 以上，英文约 4 字符 ≈ 1 token。
// 生产中用服务商的 token 计数接口校准。
const estimate = (s: string) => Math.ceil(s.length / 1.5);

export function buildContext(sections: Section[], budget: number) {
  const kept = [...sections];
  let total = kept.reduce((n, s) => n + estimate(s.text), 0);

  // 1. 超预算：按优先级从低到高，先截断、再整段丢弃
  const byPriority = [...kept].sort((a, b) => a.priority - b.priority);
  for (const s of byPriority) {
    if (total <= budget) break;
    const size = estimate(s.text);
    const over = total - budget;
    if (s.minTokens !== undefined && size - over >= s.minTokens) {
      s.text = truncate(s.text, size - over);
      total -= over;
    } else {
      kept.splice(kept.indexOf(s), 1);
      total -= size;
    }
  }

  // 2. 稳定的在前，易变的在后；同级保持原顺序（sort 是稳定排序）
  kept.sort((a, b) => ORDER[a.stability] - ORDER[b.stability]);
  return { text: kept.map((s) => `## ${s.name}\n${s.text}`).join('\n\n'), tokens: total };
}

function truncate(text: string, tokens: number) {
  const chars = Math.floor(tokens * 1.5) - 40;
  // 截断要告诉模型"还有更多"，并给出取回的方式
  return text.slice(0, chars) + '\n…（已截断，如需完整内容请调用 read_more 工具）';
}

    这段代码体现了几个值得在真实系统里保留的设计：

    • 上下文是一个纯函数的输出：同样的输入得到同样的字节，可以写单元测试，也天然满足"确定性序列化"。
    • 稳定性是一等公民：每段内容声明自己多久变一次，排序由它决定，而不是靠写代码的人记住。
    • 预算超限有明确策略：谁先被截断、谁先被丢弃，由优先级决定，并且截断有提示。
    • 把组装结果连同 token 数写进 trace（第 14 章），出问题时你能看到模型那一轮到底看到了什么——这是排查 agent 问题最重要的一手证据。

    团队发现缓存命中率几乎为 0。排查后最可能的原因是？

    1. 对话历史太长
    2. 工具定义太多
    3. 用户问题每次都不一样
    4. 系统提示开头写着"当前时间：2026-11-25 14:03:27"，后面才是固定的规则和工具说明
    缓存按前缀匹配。用户问题本来就在末尾，变化不影响前面的命中；历史长、工具多反而让可缓存部分更大。精确到秒的时间戳放在最前面，会让后面每一个字节都无法命中——这正是 Manus 点名的反模式。把时间挪到上下文末尾，或者只精确到日期。

    10 · 反模式清单

    • "窗口够大，全塞进去"：成本、延迟、准确率三输。窗口大小是上限，不是目标。
    • 在上下文前部放易变内容：时间戳、随机 ID、会话计数器放在开头，缓存全部失效。
    • 回头改写历史：为了"整洁"修改之前的工具返回，既破坏缓存，又让模型看到的因果链断裂。要清理就用压缩或上下文编辑，一次性地做。
    • 每轮动态增删工具：缓存失效，且历史里引用的工具突然不存在。
    • 工具返回原样回灌：一个网页、一个 JSON 列表直接塞进去。永远在工具侧过滤、截断、精简。
    • 不可恢复的压缩：摘要里没留路径和链接，之后需要细节时再也找不回来。
    • 看不见上下文：上下文由框架在内部拼接，出了问题只能猜。每一轮的完整输入都应该能被记录和回放。
    真实项目复盘

    本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

    • N2 · niuma 的分析提示词从 1291 字涨到 6058 字，53 处"不要/一律/除非"
    • N12 · niuma 的上下文只按条数截断，没有 token 预算
    • D10 · devtask 同一条规则一个月翻了三次
    本章要点
    • 上下文工程 = 推理时选择并维护最优 token 集合；它比提示词工程范围更大。
    • context rot：上下文越满，召回越差。每个 token 都在消耗注意力预算。
    • 系统提示要在"硬编码规则"和"空泛指导"之间找到合适的高度，例子少而多样。
    • 稳定在前、易变在后、只追加、确定性序列化——这是提示缓存命中的前提。
    • 确定会用的预加载，可能会用的给引用；工具返回要分页、过滤、截断。
    • 长任务用压缩、结构化笔记、子 agent 隔离三件套，压缩必须可恢复。
