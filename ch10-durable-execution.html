可靠执行：状态机、幂等与持久化

模型会超时，网络会抖，进程会在最不巧的时候被杀掉。一个替你发邮件的 agent，比"偶尔答错"更不可接受的是"同一封邮件发了两遍"或"批准了却没发出去"。这一章讲怎样给不确定的模型套上一层确定的外壳。

约 40 分钟前置：第 4、8 章；了解数据库事务含 1 个分步动画、1 个交互、3 道小测
学完你能
  • 把 agent 系统拆成"少数 LLM 节点 + 确定性状态机"，并写出提案的状态迁移
  • 用幂等键和 transactional outbox 实现"恰好一次"的对外效果
  • 给错误分类，决定哪些重试、哪些换模型、哪些交给人
  • 设计崩溃恢复与优雅退出，在"不确定是否已发送"时做出正确选择
  • 判断什么时候该上 Temporal 这类持久执行框架，什么时候一个 SQLite 就够了

1 · 确定性外壳

回看一个办公助理的完整处理链：收消息 → 去重落库 → 攒批 → 分析 → 生成提案 → 策略 → 审批 → 执行 → 记录。这里面真正需要模型的只有"分析"一步（也许再加上起草和定期的记忆整理）。其余每一步都是普通的、可以穷举测试的代码。

这不是保守，而是工程上最有效的可靠性策略。12-Factor Agents 里有三条原则说的都是这件事：

  • Own your control flow：控制流在你的代码里，而不是藏在框架或模型的"自由发挥"里。
  • Unify execution state and business state：执行进度和业务状态存在一起（比如提案表的 status 字段），而不是一半在数据库、一半在某个进程的内存里。
  • Make your agent a stateless reducer：agent 的一步 = (当前状态, 新事件) → 新状态。状态在外部持久化，进程随时可以被杀掉重启。

2 · 领域状态机

提案（第 8 章）是这类系统的核心实体。把它的生命周期画成状态机，并只允许图上画出来的迁移：


import { Database } from 'bun:sqlite';

const ALLOWED: Record<string, string[]> = {
  pending: ['approved', 'rejected', 'expired'],
  approved: ['executing', 'expired'],
  executing: ['done', 'failed', 'pending'], // pending 仅用于崩溃恢复
  failed: ['pending'],
};

export function transition(db: Database, id: string, from: string, to: string, note: string | null = null) {
  if (!ALLOWED[from]?.includes(to)) throw new Error(`非法迁移 ${from} → ${to}`);
  const tx = db.transaction(() => {
    const res = db
      .query('UPDATE proposals SET status = ?, updated_at = ? WHERE id = ? AND status = ?')
      .run(to, Date.now(), id, from);
    if (res.changes !== 1) throw new Error(`提案 ${id} 已不在 ${from} 状态（可能被并发处理）`);
    db.query('INSERT INTO proposal_events (proposal_id, from_status, to_status, note, at) VALUES (?, ?, ?, ?, ?)')
      .run(id, from, to, note, Date.now());
  });
  tx();
}
条件更新就是你的锁

WHERE status = ? 让"检查状态"和"修改状态"成为一个原子操作。不要先 SELECT 看状态、再在应用代码里判断、再 UPDATE——两步之间别的进程（比如另一个审批入口）可能已经改了它。

3 · 幂等：让重复变得无害

分布式系统里没有"恰好一次投递"，只有"至少一次投递 + 幂等处理"。网络请求超时的时候，你无法知道对方是没收到、还是收到了但响应丢了。唯一安全的重试方式是让重复请求在对方那里不产生额外效果。

Stripe 的 Idempotency-Key 是这类设计的标杆：客户端为每个逻辑操作生成一个唯一键放在请求头里；服务端保存这个键至少 24 小时，同一个键的重试会直接返回第一次的响应，并带上 Idempotent-Replayed: true 头告诉你这是一次重放。

对 agent 来说，幂等键的设计有两个要点：

  • 键由业务身份派生，而不是随机生成：例如 proposal:{id}:{正文哈希}。随机键在进程崩溃后就丢了，重启后的重试会用一个新键，等于没有保护。
  • "同一个操作"的定义要想清楚：用户把被拒的草稿改写后再批准，那是一条新消息，应该得到新键；同一个正文的重试才用同一个键。所以正文哈希应该参与派生。

如果下游 API 不支持幂等键怎么办？有些消息平台允许客户端指定一个消息 ID 或去重标识，服务端按它去重——效果相同。如果什么都不支持，你就只能在本地记录"已发送"，并接受"响应丢失时不能自动重试，要交给人确认"（下面的模拟器里可以看到这种情况）。

4 · Transactional Outbox

还有一个更隐蔽的问题：数据库写入和外部调用无法放进同一个事务。

  • 先发送、后写库：发送成功后进程崩溃，库里没有记录，重启后再发一遍。
  • 先写库、后发送：写库成功后崩溃，库里说"已批准"，但永远没人去发。

Transactional outbox 模式的解法：在同一个本地事务里同时写业务状态和一条"待发送"记录（outbox 行），由一个独立的分发器读取 outbox、带幂等键调用外部服务、成功后标记完成。这样"要发"这件事一定和业务状态一起持久化；分发器可能会重复投递（至少一次），所以消费端——这里是带幂等键的外部 API——必须能去重。


import { Database } from 'bun:sqlite';
import { createHash } from 'node:crypto';

export function approve(db: Database, proposalId: string, text: string, approver: string) {
  const key = `proposal:${proposalId}:${createHash('sha256').update(text).digest('hex').slice(0, 16)}`;
  db.transaction(() => {
    const res = db
      .query("UPDATE proposals SET status = 'approved', approved_by = ?, final_text = ? WHERE id = ? AND status = 'pending'")
      .run(approver, text, proposalId);
    if (res.changes !== 1) throw new Error('提案已被处理或已失效');
    // 同一事务写入 outbox：要么两者都成功，要么都没发生
    db.query("INSERT INTO outbox (idempotency_key, proposal_id, payload, status, attempts) VALUES (?, ?, ?, 'queued', 0)")
      .run(key, proposalId, JSON.stringify({ text }));
  })();
}

export async function dispatchOnce(db: Database, sender: Sender) {
  const row = db.query("SELECT * FROM outbox WHERE status = 'queued' ORDER BY rowid LIMIT 1").get() as OutboxRow | null;
  if (!row) return;
  const claimed = db.transaction(() => {
    const res = db.query("UPDATE outbox SET status = 'sending', attempts = attempts + 1 WHERE rowid = ? AND status = 'queued'").run(row.rowid);
    if (res.changes !== 1) return false; // 被别的分发器抢走了
    db.query("UPDATE proposals SET status = 'executing' WHERE id = ? AND status IN ('approved', 'executing')").run(row.proposal_id);
    return true;
  })();
  if (!claimed) return;
  try {
    const { messageId } = await sender.send(JSON.parse(row.payload), { idempotencyKey: row.idempotency_key });
    db.transaction(() => {
      db.query("UPDATE outbox SET status = 'sent', result = ? WHERE rowid = ?").run(messageId, row.rowid);
      db.query("UPDATE proposals SET status = 'done', result = ? WHERE id = ?").run(messageId, row.proposal_id);
    })();
  } catch (err) {
    const retryable = isRetryable(err) && row.attempts + 1 < 3;
    db.query('UPDATE outbox SET status = ?, last_error = ? WHERE rowid = ?')
      .run(retryable ? 'queued' : 'failed', String(err), row.rowid); // 重试用同一个幂等键
    if (!retryable) db.query("UPDATE proposals SET status = 'failed', error = ? WHERE id = ?").run(String(err), row.proposal_id);
  }
}

朴素实现

    outbox + 幂等键

      为什么幂等键应该由"提案 ID + 正文哈希"派生，而不是每次发送时随机生成一个 UUID？

      1. UUID 太长，有些 API 不接受
      2. 哈希比 UUID 更难被猜到
      3. 进程崩溃重启后，重试必须拿到与第一次相同的键，服务端才能识别为重复；随机键在崩溃后就丢失了
      4. 正文哈希可以防止提示注入
      幂等键的价值在于"同一个逻辑操作永远得到同一个键"。由持久化的业务数据派生的键在任何时候都能重新算出来；正文参与派生，又保证了用户改写后的新正文被当成一条新消息。

      5 · 重试、回退与超时

      "失败了就重试"是最常见也最危险的一句话。正确的做法是先给错误分类：

      错误类型例子怎么处理
      瞬时错误网络断开、连接重置、429 限流、5xx同一模型 / 同一请求，指数退避加随机抖动重试，有次数上限
      认证与配额401/403、额度用尽、凭据过期重试无用；切换到回退链上的下一个模型或通知人重新登录
      输出不合格结构化输出校验失败、没调用工具把错误信息回灌给同一个模型让它修正（第 3 章），而不是换模型；换模型不解决提示词问题
      已发生写操作工具循环里已经调用过发送、建工单不能把整轮推理从头重来（会重复写）；只能从断点继续或交给人
      业务错误收件人不存在、权限不足不重试，标记失败，原因展示给人
      预算超限今日花费已达上限不算可切换的错误；停止新的调用，恢复后由定时任务补做
      
export async function withRetry<T>(fn: (attempt: number) => Promise<T>, opts = { max: 3, baseMs: 500, capMs: 8000 }): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await fn(attempt);
    } catch (err) {
      if (!isRetryable(err) || attempt >= opts.max) throw err;
      const exp = Math.min(opts.capMs, opts.baseMs * 2 ** (attempt - 1));
      await Bun.sleep(Math.random() * exp); // "full jitter"：避免大量客户端同时重试
    }
  }
}

export function isRetryable(err: unknown): boolean {
  const status = (err as { status?: number }).status;
  if (status === 429 || (status !== undefined && status >= 500)) return true;
  return /ECONNRESET|ETIMEDOUT|ENOTFOUND|socket hang up|Unable to connect/i.test(String(err));
}

      模型回退链

      配置一个有序的模型列表，只在认证、配额、网络类错误时切换到下一个；每次切换记一条日志。校验失败不回退——那通常是提示词或 schema 的问题，换模型只会掩盖它。

      超时要分两层

      • 空闲超时：等响应头、流式输出两次事件之间的最大间隔。防止"连接没断、但对方不再说话"的僵死。
      • 总时长上限：单次请求无论如何不能超过的时间。流式响应可能一直慢慢吐字，空闲超时永远不触发。

      两层超时都要和调用方的取消信号（AbortSignal）合并，让上层可以随时中止整条链路。

      6 · 崩溃恢复与优雅退出

      重启时怎么处理"进行中"的任务

      进程在 executing 状态被杀掉，重启后面对的是一个真正未知的状态：可能发出去了，也可能没有。三种选择：

      做法后果适用
      自动重发可能重复发送只有下游支持幂等键时才安全
      标记成功可能"批准了却没发"几乎永远不对
      退回待审批并说明"可能未发出，可直接重试"多一次人工确认下游不支持幂等，或对外消息这类重复代价高的动作

      如果下游支持按幂等键或去重标识查询，最好的做法是先对账（reconcile）：查一下这条到底发出去没有，再决定。

      优雅退出的顺序

      1. 停止接收新工作：不再从队列拉新任务，不再启动新的分析。
      2. 等进行中的对外动作结束：正在发送的那一条让它发完并落库，这是最容易产生"未知状态"的窗口。
      3. 等后台任务收尾：定时任务、事件回调都应登记在一个集合里，退出时逐个等待（设上限）。
      4. 最后关闭连接和数据库：先关外部连接，最后关库，保证前面的步骤都能写入。

      7 · 持久执行框架

      当流程变长——等待审批几天、跨多个服务、需要定时唤醒——手写状态机会越来越累。持久执行（durable execution）框架把"每一步的结果持久化、崩溃后从断点继续"变成了基础设施：

      方案核心概念等待人工
      TemporalWorkflow 必须是确定性的；所有副作用（含模型调用）放进 Activity，结果被记录，重放时直接取用Signal / 等待条件；与 OpenAI Agents SDK 有官方集成，agent 循环跑在 Workflow 里
      Inngest函数被拆成 step.run，每步结果持久化step.waitForEvent 按审批 ID 匹配事件，超时返回 null，等待期间不占算力
      Cloudflare Workflowsstep 持久化，运行在 Workers 上step.waitForEvent，默认超时 24 小时
      Vercel Workflow"use workflow" / "use step" 指令标记函数用 hook 暂停等待外部输入
      LangGraphcheckpointer 在每个节点后保存图状态interrupt()；恢复时整个节点重跑（第 8 章）

      Anthropic 在 2026-04 介绍 Managed Agents 时给出了另一种思路：把 agent 拆成无状态的 harness（大脑）、沙箱（手）和会话（一份持久的事件日志）。harness 随时可以挂掉，用 wake(sessionId) 从事件日志恢复——这正是"stateless reducer"在托管服务上的形态。

      持久执行框架没有替你解决的事

      所有这些框架都保证"步骤结果被记录、不会重复执行已记录完成的步骤"。但步骤内部的外部调用在"调用成功、结果还没记录"时崩溃，重放时仍会再调用一次。所以 Activity / step 里的对外动作依然需要幂等键。框架把问题缩小到了一个窗口，没有消灭它。

      什么时候不需要框架

      一个单用户、本机运行的 agent（比如替你一个人处理邮件和日程），一个开启 WAL 的 SQLite 加上本章的状态机和 outbox，通常就足够了：

      • WAL 模式允许一个写者和多个读者并发：常驻进程在写，命令行工具同时读写同一个库，彼此不阻塞读（写写之间设置 busy_timeout 排队）。
      • 审批天然异步：提案落库后 agent 这一轮就结束了，不需要"挂起的执行"；批准只是一次状态更新，执行器下一拍拾取。
      • 单实例：用 pid 文件保证同一时刻只有一个常驻进程，交给系统的服务管理器（launchd / systemd）做开机自启和异常拉起。

      当你需要多机部署、多租户、长达数周的多步流程、或复杂的定时与补偿逻辑时，再引入专门的框架。

      8 · 去抖批处理

      消息往往成串到达："在吗" "那个月报" "导出能不能加个部门筛选" "今天要"。每来一条就分析一次，不仅浪费，还会对半句话做出判断。常见做法是按会话去抖：会话安静 N 秒，或累计 M 条，再把这一批交给分析。

      
export class Batcher<T> {
  private buffers = new Map<string, { items: T[]; timer: ReturnType<typeof setTimeout> }>();
  constructor(private quietMs: number, private maxItems: number, private flush: (key: string, items: T[]) => void) {}

  push(key: string, item: T) {
    const buf = this.buffers.get(key);
    if (buf) clearTimeout(buf.timer);
    const items = [...(buf?.items ?? []), item];
    if (items.length >= this.maxItems) return this.emit(key, items);
    this.buffers.set(key, { items, timer: setTimeout(() => this.emit(key, items), this.quietMs) });
  }

  private emit(key: string, items: T[]) {
    const buf = this.buffers.get(key);
    if (buf) clearTimeout(buf.timer);
    this.buffers.delete(key);
    this.flush(key, items); // flush 内部把批次写入持久队列，而不是直接在内存里分析
  }
}

      注意内存里的缓冲在崩溃时会丢失。由于消息本身已经先落库（"去重落库"那一步），恢复时只需找出"已入库但还没被任何批次分析过"的消息重新入批即可——这又是"状态在外部"原则的一次应用。

      工具循环里，模型已经调用过一次 create_ticket，随后的一次模型请求因为 503 失败，回退链切换到下一个模型。正确的做法是？

      1. 用新模型把整轮对话从头再跑一遍
      2. 不从头重跑整轮：带着已有的消息历史（包括 create_ticket 的结果）继续；如果做不到，就停下来交给人，避免重复建单
      3. 把 create_ticket 的结果删掉，让新模型重新决定
      4. 503 不可重试，直接把整个任务标记失败
      已经发生的写操作不能被"重来"抹掉。503 本身是可重试的瞬时错误，可以退避后重试或换模型，但必须从当前状态继续，而不是从头重放。

      你用 Temporal 实现了审批流程，发送邮件放在一个 Activity 里。下面哪种说法正确？

      1. Temporal 保证 Activity 恰好执行一次，不需要幂等键
      2. Workflow 代码里可以直接调用模型，因为结果会被缓存
      3. 只要用了持久执行框架，崩溃恢复就不用考虑了
      4. Activity 在"发送成功、结果未记录"时崩溃会被重试，所以发送仍需幂等键
      持久执行框架记录的是"步骤已完成"。步骤内部的外部调用和"记录完成"之间仍有窗口；Activity 默认会被重试。Workflow 代码必须是确定性的，模型调用这类非确定的副作用要放进 Activity。

      9 · 反模式清单

      • 状态只在内存里："正在等审批"存在某个 Promise 里，进程一重启就全没了。
      • 先查后改：SELECT 判断状态再 UPDATE，并发下会被两个入口同时处理。
      • 随机幂等键：每次重试一个新 UUID，等于没有幂等。
      • 无差别重试：把校验失败、权限错误也拿去重试，或者对写操作整轮重跑。
      • "失败就换模型"：把提示词问题伪装成了可用性问题。
      • 重启自动重发未完成的发送：下游不支持幂等时，这就是重复消息的来源。
      • 只有空闲超时：慢吞吞的流式响应可以把一个任务卡住一个多小时。
      • 无限重试：没有上限、没有退避，一次故障被放大成一场重试风暴。
      真实项目复盘

      本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

      • N15 · niuma 遇到对方拒收，一天重试了三千多次
      • D12 · devtask 靠轮询和内存状态，通知可能无声丢失
      本章要点
      • LLM 只出现在少数节点并只产出数据；其余是确定性的状态机，状态持久化在外部。
      • 状态迁移用带旧状态条件的原子更新，并记录事件；只允许图上的迁移。
      • "恰好一次"的对外效果 = 至少一次投递 + 幂等处理；幂等键由业务身份派生。
      • Transactional outbox 让"要发"与业务状态在同一事务里持久化。
      • 重试前先分类：瞬时错误退避重试、认证配额走回退链、校验失败回灌修正、已有写操作不重跑。
      • 崩溃后的未知状态宁可交给人，也不要盲目重发；持久执行框架缩小但不消灭这个窗口。
      • 单用户本机 agent，SQLite WAL + 状态机 + outbox 往往就够了。
