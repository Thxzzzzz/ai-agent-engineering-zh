Agent 是什么：从 LLM 到智能体

"Agent"是这几年被用得最滥的词之一。这一章先把它钉死：它到底由什么组成，和"写死流程再调几次模型"有什么本质区别，以及什么时候不该用它。

约 30 分钟前置：调用过任意一个大模型 API含 1 个分步动画、1 个交互、3 道小测
学完你能
  • 用一句话说清 agent 的定义，并画出 agent loop 的每一步
  • 区分 workflow 与 agent，说出五种经典编排模式各适合什么
  • 用"自主度分级"描述一个系统里人和 agent 各自的角色
  • 面对一个需求时，按"复杂度阶梯"选出最简单够用的方案

1 · 一句话定义

业界目前最常被引用的定义来自 Anthropic 的《Building effective agents》（2024-12）：

Workflow：用预先写好的代码路径来编排 LLM 和工具。
Agent：由 LLM 动态地决定自己的流程和工具使用，自己掌控如何完成任务。

换成工程师的话：agent 是一个"模型在循环里调用工具、根据环境反馈决定下一步"的程序。三个关键词——循环、工具、反馈——缺一个都不算 agent：

  • 没有循环：模型只回答一次，那是一次 API 调用。
  • 没有工具：模型只能"说"不能"做"，影响不了外部世界，也拿不到新信息。
  • 没有反馈：模型做了动作却看不到结果，等于闭眼开车。

Lilian Weng 2023 年那篇经典综述把 agent 拆成 LLM（大脑）+ 规划 + 记忆 + 工具使用 四块。这个拆法到今天仍然好用，本课程的第一、二部分基本就是沿着它展开的。

2 · Agent Loop：一步一步看它怎么干活

下面用一个办公场景走一遍：用户说"把下周三的周会挪到周四同一时间，并通知参会人"。点"下一步"，看每一轮里模型、工具和环境之间发生了什么。

把这个过程写成伪代码，核心只有十几行。第 4 章和跟练项目 P1 会把它写成能跑的 TypeScript：


const messages = [system(prompt), user(goal)];
for (let step = 0; step < MAX_STEPS; step++) {
  const reply = await model.generate({ messages, tools });
  messages.push(reply);                       // 模型的回答（可能带 tool_call）
  if (reply.toolCalls.length === 0) return reply.text;  // 不再调用工具 = 完成
  for (const call of reply.toolCalls) {
    const result = await runTool(call);       // 你的代码执行，可做权限检查
    messages.push(toolResult(call.id, result)); // 结果回灌，形成反馈
  }
}
throw new Error('超过最大步数仍未完成');
工程师视角

"模型决定做什么，代码决定能不能做、怎么做"——这条分工贯穿整门课。模型是不可靠的决策者，你的代码是可靠的执行者和守门员。权限、幂等、审批、预算，全部长在代码这一侧。

在 agent loop 里，谁真正执行了"修改日历事件"这个动作？

  1. 模型直接调用了日历 API
  2. 模型提供商的服务器代为调用
  3. 你的程序收到模型输出的 tool_call 后，由你的代码调用日历 API
  4. 日历服务主动读取了模型的输出
模型只产出"想调用哪个工具、参数是什么"的结构化文本。执行权在你的代码手里——这正是你能加权限检查、审批和幂等保护的地方。（提供商的"托管工具"如网页搜索是例外，但对你自己的业务系统，执行永远在你这一侧。）

3 · Workflow 还是 Agent？

两者不是对立的，而是一条谱系的两端：越往右，模型掌控的决策越多，灵活性越高，可预测性越低、成本越高。

WorkflowAgent
谁决定下一步你写的代码模型
适合步骤明确、可以提前拆解的任务步骤数事先未知、需要根据中间结果调整的任务
可预测性高，每条路径都能测低，同一输入可能走出不同轨迹
成本与延迟可控随步数增长；Anthropic 实测单 agent 约为普通对话 4 倍 token，多 agent 约 15 倍
失败形态某一步输出不合格跑偏、绕圈、过早宣布完成、复合误差
先问自己：真的需要 agent 吗？

Anthropic 和 OpenAI 的官方指南给出的建议高度一致：从最简单的方案开始——一次精心设计的调用加上检索和几个示例，往往就够了。只有当规则难以穷举、需要处理大量非结构化信息、或者流程必须根据中间结果调整时，才值得引入 agent 的不确定性。

4 · 五种经典编排模式

这五种模式来自《Building effective agents》，它们是 workflow 的"设计模式"，也是组装复杂 agent 系统的积木。逐个点开看结构和适用场景：

Prompt chaining：把任务拆成固定的几步，每一步的输出是下一步的输入，步骤之间可以插入代码检查（gate）。

适合：能清晰拆成固定子任务的场景，用延迟换准确率。例：先抽取会议纪要里的待办，再把每条待办改写成任务描述。

Routing：先分类，再把输入交给专门的下游处理（不同提示词、不同模型、不同流程）。

适合：输入类别差异大、分开处理效果更好时。也是成本优化的主力：简单请求走便宜模型。

Parallelization 有两种：分段（sectioning）——把独立子任务并行跑，如一路检查内容是否违规、一路生成回答；投票（voting）——同一任务跑多次取多数，提高置信度。

适合：子任务互相独立，或需要多个视角/多次尝试才可靠的判断。

Orchestrator-workers：和并行化很像，区别在于子任务不是预先定好的，由编排者根据输入现场决定拆成几份、怎么拆。

适合：无法提前预知子任务的复杂工作，如"调研一个主题"、"改动涉及多个文件的代码"。Anthropic 的多智能体研究系统就是这个结构（第 11 章细讲）。

Evaluator-optimizer：一个模型生成，另一个按明确标准评审并给出意见，循环直到通过或达到上限。

适合：有清晰评价标准、且迭代确实能改进结果时，如翻译润色、按验收标准检查代码。长任务里把评估者独立出来，更容易把它调成"挑剔"的角色（第 12 章）。

需求：用户上传一份合同，系统要判断它属于"采购 / 劳务 / 保密协议 / 其他"中的哪类，再按类别套用不同的审查清单。最合适的起点是？

  1. 开放式 agent，让模型自己决定怎么审
  2. 路由：先分类，再交给对应类别的审查流程
  3. 编排者-工作者：动态拆分审查任务
  4. 投票：让五个模型各审一遍
类别有限、每类的处理方式已知——这是路由的教科书场景。每个分支内部可以再是一条提示链。只有当审查步骤无法事先确定时，才需要升级到 agent。

5 · 自主度：人在系统里扮演什么角色

"自主"不是一个开关，而是人和 agent 之间的分工方式。2025 年 Feng、McDonald、Zhang 的论文《Levels of Autonomy for AI Agents》按用户的角色把自主度分成五级。拖动滑块看每一级的含义：

自主度分级
L1 操作者L2 协作者L3 顾问L4 审批者L5 旁观者

对一个代表你对外沟通的 agent（比如替你回复消息），默认停在 L4 审批者是业界的主流做法：agent 准备好一切，你只需要点"批准/修改/拒绝"。随着信任积累，可以按"动作 × 对象"逐格放权到 L5——这套机制在第 8 章细讲。

一个判断准则

自主度应该按动作的风险分配，而不是按整个系统一刀切。"读邮件"可以全自动，"发邮件给客户"应该审批，"转账"可能永远需要人。好的系统能对不同动作设定不同的级别。

6 · 复杂度阶梯：选最简单够用的那一级

面对一个新需求，从下往上逐级尝试，只有当前一级确实不够时才往上走：

  1. 一次调用：好的提示词 + 少量示例 + 结构化输出。能解决的问题比你想象的多。
  2. 加检索：模型缺的往往是信息而不是能力，把相关资料放进上下文。
  3. Workflow：提示链、路由、并行——流程由代码掌控，每一步可单独测试。
  4. 单 agent + 少量工具：步骤数未知时才让模型掌舵，配上步数上限、预算和审批。
  5. 多 agent：只在"可以并行的读型任务"或上下文必须隔离时考虑，代价是数倍的 token 和更难的调试（第 11 章）。

以下哪种情况最能说明"该从 workflow 升级到 agent"了？

  1. 提示词越来越长
  2. 想用更强的模型
  3. 需要调用外部 API
  4. 完成任务所需的步骤取决于中间结果，无法提前写死
workflow 同样可以调用 API、用强模型、有长提示词。真正的分界线是控制流由谁决定：当下一步做什么只有看到上一步结果才知道时，才需要把控制权交给模型。

7 · 常见误区

  • "用了框架才算 agent"：框架会隐藏提示词和控制流，出问题时难以排查。官方指南都建议先直接用 API 写，理解底层后再决定是否引入框架。
  • "模型越强，越不需要工程"：模型变强改变的是"哪些脚手架可以拆掉"，而不是"不需要脚手架"。权限、审批、幂等、评测与模型强弱无关。
  • "agent 应该什么都能做"：通用 agent 难测难控。"小而专注"的 agent（12-Factor Agents 的第 10 条）更容易做到可靠。
  • "跑通一次 demo 就算完成"：agent 的难点在长尾。成功率 75% 的单步，连跑 3 次全成功的概率只有约 42%（第 13 章的 pass^k）。
真实项目复盘

本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

  • D1 · devtask 曾让模型当调度中枢，一个话题一天调用模型 311 次，后来连砍 agent 回合改成代码直接转发
  • N1 · niuma 53 天做了 108 个里程碑，功能扩张跑在验证前面
本章要点
  • Agent = 模型在循环里使用工具，根据环境反馈决定下一步；模型只决策，执行在你的代码里。
  • Workflow 由代码定流程，agent 由模型定流程；两者是一条谱系，生产系统多是组合。
  • 五种编排模式：提示链、路由、并行化、编排者-工作者、评估-优化。
  • 自主度按用户角色分五级，应按动作风险分别设定；对外沟通默认 L4（审批者）。
  • 永远从复杂度阶梯的最低一级开始。
