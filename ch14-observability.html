可观测性、成本与运维

一个上线的 agent 是一个会自己做决定、按 token 计费、7×24 小时运行的服务。你需要随时回答三个问题：它刚才为什么这么做？这个月花了多少钱、花在哪？它挂了会不会自己起来？

学完你能
  • 把一次 agent 运行建模成 trace 与 span，读懂瀑布图里的时间和 token 花在哪
  • 说出 OpenTelemetry GenAI 语义约定的现状和关键属性，知道哪些字段是敏感的
  • 用最低成本搭一套本地 JSONL 调用记录，让每次判错都能直接回看
  • 算清一次调用的 token 账，设计提示词结构让缓存命中，设预算与回退
  • 把 agent 部署成一个能自愈、能体检、能备份迁移的长期服务

1 · 为什么日志不够

普通服务出了问题，你看错误日志和堆栈。agent 的问题大多不报错：它成功地调用了工具、成功地返回了结果，只是结果是错的——回复了不该回的人，漏了一位参会人，把"下周五"理解成了本周五。

要排查这类问题，你需要知道的是：模型当时看到了什么、它决定了什么、工具返回了什么。这就要求按"一次运行"把所有步骤串起来，而且每一步都带着完整的输入和输出。这正是 trace 的结构：

日志（log）追踪（trace）
粒度一条条独立的事件一次运行，由父子嵌套的 span 组成
能回答"发生过什么错误""这次运行的每一步做了什么、花了多久、花了多少 token、为什么走到这里"
对 agent 的价值能发现崩溃和超时能发现"成功地做错了"；是错误分析和评测用例的直接来源（第 13 章）
trace 也是评测数据

一条完整记录的 trace，等于一个可以回放的评测用例：固定它的输入，就能复现当时的判断。没有 trace，判错时只能"大概是这样"地猜，然后靠重跑碰运气复现。

3 · OpenTelemetry GenAI 语义约定

OpenTelemetry（OTel）是业界通用的可观测性标准，它的 GenAI 语义约定规定了模型调用、agent、工具执行这些 span 应该叫什么、带哪些属性。按约定打点，你的 trace 就能被各种后端工具直接识别。截至 2026-11 的现状：

  • GenAI 约定已从主语义约定仓库迁到独立仓库 open-telemetry/semantic-conventions-genai，旧页面标为 "moved"。
  • 状态仍是 Development（实验性），还没有 Stable 版本。属性名可能变，打点代码最好集中在一处，便于跟进。
属性 / 约定含义与要点
gen_ai.operation.name操作类型。agent 相关取值有 create_agent、invoke_agent、invoke_workflow、plan；模型调用是 chat；工具执行用 execute_tool 的规范
span 名称{operation} {gen_ai.agent.name}，例如 invoke_agent 日程助手
gen_ai.provider.name / gen_ai.request.model模型提供方和请求的模型
gen_ai.agent.idagent 的标识
gen_ai.usage.input_tokens输入 token，包含命中缓存的部分
gen_ai.usage.output_tokens输出 token，包含推理（思考）token
gen_ai.conversation.id只在确实存在会话 ID 时填写，不许用随机 UUID 或 trace ID 冒充
消息内容、系统指令、工具定义属于 Opt-In 属性：可能包含敏感数据，默认不采集，需要显式开启
trace 里有用户的原文

最有用的那部分 trace——完整的输入输出——恰恰是最敏感的：邮件正文、聊天记录、客户信息都在里面。这就是 OTel 把它们设为 Opt-In 的原因。决定把 trace 发到哪里之前，先想清楚：这些原文能不能离开用户的机器？要保留多久？用户要求删除时你能不能删干净？


import { trace, SpanKind } from '@opentelemetry/api';

const tracer = trace.getTracer('schedule-agent');

export async function invokeAgent(goal: string) {
  return tracer.startActiveSpan('invoke_agent 日程助手', { kind: SpanKind.INTERNAL }, async (span) => {
    span.setAttributes({
      'gen_ai.operation.name': 'invoke_agent',
      'gen_ai.agent.name': '日程助手',
      'gen_ai.provider.name': provider,
      'gen_ai.request.model': model,
    });
    try {
      const result = await runLoop(goal);       // 里面的每次 chat / execute_tool 各开子 span
      span.setAttributes({
        'gen_ai.usage.input_tokens': result.usage.input,
        'gen_ai.usage.output_tokens': result.usage.output,
      });
      return result;
    } catch (err) {
      span.recordException(err as Error);
      throw err;
    } finally {
      span.end();
    }
  });
}

4 · 最低成本方案：本地 JSONL 调用记录

单机运行的个人 agent、早期项目，不一定需要一整套追踪后端。一个非常实用的起点是：每次模型调用结束时，往本地文件追加一行 JSON。它零依赖、不出机器、能用 grep 和 jq 查，判错时直接打开就能看到模型拿到了什么、回了什么。

每行应该记录：

  • 哪份提示词：名称 + 版本号。提示词改了之后，你要能区分新旧版本各自的表现。
  • 模型与参数：模型、思考强度、温度等。
  • 耗时、请求次数、用量：含缓存读写的 token 数。
  • 输入输出全文：系统提示、用户输入、结构化结果或回答；工具循环里每次工具调用的参数和返回（过长的截断）。
  • 失败原因：校验失败、超时、被限流、回退到了哪个模型。

import { appendFile, readdir, unlink } from 'node:fs/promises';
import { join } from 'node:path';

export interface CallRecord {
  at: string;              // ISO 时间
  prompt: string | null;   // 提示词名@版本，如 "triage@3"
  model: string;
  reasoning: string | null;
  ms: number;
  attempts: number;
  usage: { input: number; output: number; cacheRead: number; cacheWrite: number };
  system: string;
  input: string;
  output: unknown;
  tools?: { name: string; args: unknown; result: string }[];
  error?: string;
}

const MAX_FIELD = 4000;
const clip = (s: string) => (s.length > MAX_FIELD ? `${s.slice(0, MAX_FIELD)}…[截断 ${s.length - MAX_FIELD} 字]` : s);

export class JsonlTracer {
  constructor(private dir: string, private keepDays = 14) {}

  async record(r: CallRecord) {
    const day = r.at.slice(0, 10);
    const line = JSON.stringify({ ...r, tools: r.tools?.map((t) => ({ ...t, result: clip(t.result) })) });
    try {
      await appendFile(join(this.dir, `${day}.jsonl`), `${line}\n`, { mode: 0o600 });
    } catch (err) {
      console.warn('调用记录写入失败（不影响本次调用）', err);   // 记录失败绝不能让业务失败
    }
  }

  // 每天第一次写之前调用：前天及更早的压缩，超过保留期的删除
  async housekeep(today: string) {
    for (const name of await readdir(this.dir)) {
      const day = name.slice(0, 10);
      const age = (Date.parse(today) - Date.parse(day)) / 86_400_000;
      const path = join(this.dir, name);
      if (age > this.keepDays) await unlink(path);
      else if (age >= 2 && name.endsWith('.jsonl')) {
        await Bun.write(`${path}.gz`, Bun.gzipSync(await Bun.file(path).bytes()));
        await unlink(path);
      }
    }
  }
}
为什么昨天的不压缩

零点前后，可能还有别的进程（CLI、后台服务）在往昨天的文件里追加。只压缩"前天及更早"，就不会和正在写的进程打架。这类细节在单机多进程的 agent 里很常见。

用户反馈"agent 昨天下午把一封邮件回给了错误的人"。哪种记录最能帮你定位原因？

  1. 应用的错误日志
  2. 每次调用的耗时和 token 用量统计
  3. 那次运行的完整 trace：模型看到的上下文、它调用的工具及参数、工具的返回
  4. 当天的模型 API 账单
这次运行很可能没有任何报错——它"成功地"回错了人。只有看到模型当时的输入（比如上下文里有两个同名联系人）、它选择的工具参数和返回，才能找到原因。这也是为什么 trace 要保留输入输出全文。

5 · 成本：先算清一次调用的账

agent 的成本结构和聊天应用很不一样：

  • 输入远多于输出。每一轮都要把系统提示、工具定义、历史和工具结果重新发一遍。Manus 团队在 2025-07 的文章里提到，他们的 agent 输入输出比大约是 100:1。
  • 轮数放大一切。一个 10 步的任务，系统提示要被计费 10 次。Anthropic 测得单 agent 约为普通对话 4 倍 token，多 agent 约 15 倍（2025-06）。
  • 所以输入侧的缓存命中率往往是成本最大的杠杆。Manus 把 KV-cache 命中率称为生产 agent 最重要的单一指标，他们给出的例子里，缓存输入和未缓存输入的价差是 10 倍。

提示词缓存是怎么工作的

提供商会缓存请求的前缀：如果这次请求开头的一段 token 和最近某次请求完全相同，这段就按便宜得多的"缓存读"价格计费。几个关键事实（2026-11 核对官方文档）：

  • 缓存按前缀匹配：只要前面有一个 token 不同，后面全部失效。Anthropic 的缓存顺序是 tools → system → messages，改动前一层会让后面各层一起失效。
  • 缓存读通常是基础输入价的一小部分（常见为 0.1 倍，部分新模型更低）；缓存写反而更贵（常见为 1.25 倍起，长 TTL 更高）。
  • 有最小长度要求，不够长时静默不缓存；有 TTL（几分钟到一小时不等），每次命中会续期。
  • OpenAI 对足够长的提示自动缓存；也可以用缓存键（如 prompt_cache_key）帮助请求路由到同一缓存。
最常见的缓存杀手：把时间戳放在开头

"你是一个助手。当前时间：2026-11-25 14:03:27。"——这一行让每次请求的前缀都不同，缓存命中率直接归零，而且因为缓存写比普通输入还贵，你可能比不开缓存花得更多。Manus 的建议是：前缀保持稳定、上下文只追加不改写、序列化顺序确定（JSON 的键顺序也算）。会变的内容放到最后。

  1. D → A → B → C

6 · 控制成本的四个手段

6.1 模型分级与路由

常见做法是按任务难度用不同档次的模型：便宜的小模型做分诊（"这条消息值不值得深度分析"）、分类、抽取；贵的大模型只处理真正需要推理的部分。这就是第 1 章"路由"模式的成本用法。分诊挡掉的每一条，都省下了一整次深度分析。注意：换模型前后，要用同一套评测集比较（第 13 章），省钱不能以质量悄悄下滑为代价。

6.2 预算硬上限

agent 有一种独特的成本风险：失控。一个循环卡住、一次批量回填、一个被反复触发的定时任务，都可能在你睡觉时烧掉一个月的预算。必须有硬上限：

  • 按日、按月汇总估算费用（订阅登录的用量按公开价格估算），到上限就拒绝新的模型调用。
  • 超限时停止新的分析，但照常收录数据。消息、事件继续入库，恢复后由定时清扫补做——不丢数据，只是延后。
  • 超限要通知人，但同一范围每天只通知一次，别用告警淹没用户。
  • 预算检查发生在尝试任何模型之前，而不是调用之后才发现超了。

6.3 回退链：只对"换个模型能解决"的错误回退

配置一串模型 [主模型, 备用 1, 备用 2]，主模型不可用时切到下一个。关键是分清哪些错误值得回退：

错误类型回退？原因
认证失败、额度用完（401 / 403）是这个提供方暂时用不了，别的可以
限流、服务端错误（429 / 5xx）是（先按退避重试）偶发或局部故障
网络断开、超时、证书错误是连接问题，换一条路可能就通了
输出不符合 schema否这是提示词或任务的问题，换模型掩盖了它；应该在结构化输出层重试并回灌错误（第 3 章）
超出预算否换模型也是花钱，预算错误不是"可切换"的错误
已经执行过写操作的工具循环否换模型重来会重复执行写操作（第 10 章的幂等问题）

6.4 少调用

最便宜的调用是不调用：去抖成批（同一会话连发的三条消息合成一次分析）、分诊过滤、缓存上一次的分析结果、用确定性代码代替模型做能做的事（日期计算、格式校验、去重）。

7 · 延迟：用户等的是哪一段

手段效果注意
流式输出用户在首 token 就开始看到内容，体感延迟 ≈ TTFT结构化输出要等完整 JSON 才能校验，流式主要用于给人看的文本
并行工具调用互不依赖的工具同时执行，如图 14-1有写操作的工具并行要小心顺序和冲突
缓存命中除了省钱，长前缀命中缓存也能显著降低首 token 延迟同上一节，稳定前缀
小模型做前置步骤分诊、分类用快模型用评测确认质量
异步化不需要即时结果的工作（整理记忆、编译知识、生成简报）放到后台后台任务也要有预算和超时

还有一类延迟问题不在模型身上：连接被中途掐断却没有断开，请求就会无限期挂着。每次请求都要有超时——既有"等响应头 / 两次流事件之间的间隔"的超时，也有单次请求的总时长上限——并与调用方的取消信号合并。超时按失败处理，进入重试或回退。

夜里一个批量任务因为网络抖动失败了一次调用，回退到了备用模型，结果备用模型返回的 JSON 不符合 schema。下一步应该？

  1. 继续回退到第三个模型
  2. 直接放弃整个批量任务，回滚所有结果
  3. 换回主模型重试，直到成功
  4. 在结构化输出层把校验错误回灌给同一个模型重试；仍失败就把这一项标为失败、记入 trace，批量任务继续
schema 不合法不是"换个模型能解决"的错误，应在结构化输出层按"回灌错误、有限重试"处理（第 3 章）。批量任务不应因为一项失败整体回滚，失败项记录下来，事后通过 trace 分析原因。

8 · 运维：把 agent 当成一个长期服务

一个替你处理日常事务的 agent，价值在于它一直在。这意味着它要按服务的标准来运维：

8.1 进程与服务管理

  • 交给系统的服务管理器：macOS 用 launchd、Linux 用 systemd 的用户服务。登录即启动、异常退出自动拉起，不要靠用户开着一个终端窗口。
  • 单实例：同一份数据同一时刻只允许一个守护进程（用 pid 文件或文件锁），否则两个进程会各发一遍同一条回复。
  • 优雅退出：收到退出信号时，先停止接新工作，等进行中的动作（尤其是对外发送）结束，再关连接和数据库。启动时把残留的"执行中"状态改回"待处理"，由人决定是否重试，不自动重发（第 10 章）。
  • 长连接重连：断线按指数退避重连；凭证失效时停止收发并通知用户重新登录，而不是死循环重试。

8.2 日志、体检与配置

  • 日志按大小轮转：守护进程不重启，日志也不会撑满磁盘。日志用结构化格式（如 NDJSON），便于检索。
  • 体检命令（常叫 doctor）：一条命令检查配置能否解析、凭证是否有效、模型能否连通、外部连接是否在线、数据库能否打开、服务是否在运行，并给出修复建议。用户报问题时，第一句话就是"先跑一下 doctor"。
  • 配置与凭证分离：配置文件（可以提交、可以分享）和凭证文件（密钥、令牌）分开存放；凭证文件权限设为 0600，代码里不写死任何密钥。
  • 配置热更新：改设置（如某个会话的自动化级别）应该即时生效，同时更新配置文件和守护进程内存里的配置，不需要重启。

8.3 数据：备份、迁移、删除

  • 迁移随代码发布：数据库结构的每次变更都有编号的迁移脚本，启动时按顺序执行；破坏性迁移之前自动备份。
  • 备份范围要明确：只备份列出的文件和目录。含原文的调用记录是否进备份，是一个要有意识做出的隐私决定。
  • 能删干净：用户要求忘掉某个会话时，消息、分析、记忆、调用记录都要能删掉。设计数据布局时就要考虑这一点。

8.4 发布

面向个人用户的本地 agent，单文件可执行（例如 Bun 的 bun build --compile）能大幅降低安装门槛：下载一个文件就能跑。代价是要格外注意那些运行时才加载的东西——动态 import、运行时读取的文件、前端资源——它们是否真的被打进了包里。每次改了这类东西，都要用打包后的产物在一个干净目录里实跑一次体检和一次模型调用。

上线前检查为什么
每次模型调用都有超时、重试上限、预算检查防止挂死和失控
每次模型调用都写调用记录判错时能回看
对外动作都有幂等键重试、重启不会发重
服务管理器托管、单实例、优雅退出崩溃能自愈，不会双开
doctor 能检查全部外部依赖出问题能自助定位
凭证 0600、配置与凭证分离不泄露密钥
迁移带备份升级失败能回滚
真实项目复盘

本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

  • N16 · niuma 的 trace 没有批次和卡片的关联 id
  • N11 · niuma 的缓存和超时都是出了事才补
本章要点
  • agent 的问题大多"成功地做错了"，日志看不出来；要按一次运行记录 trace，并保留输入输出全文。
  • OTel GenAI 约定：invoke_agent 父 span 下挂 chat 与 execute_tool；仍是 Development 状态；消息内容是 Opt-In 敏感属性。
  • 本地 JSONL 调用记录是最低成本的起点：提示词版本、模型、耗时、用量、全文，按天存、过期压缩清理、只在本机。
  • agent 输入远多于输出，缓存命中率是成本最大的杠杆：稳定内容在前、只追加、会变的放最后。
  • 预算硬上限（超限停分析、照收数据），回退只针对认证 / 限流 / 网络类错误。
  • 按服务标准运维：服务管理器托管、单实例、优雅退出、日志轮转、doctor、凭证 0600、迁移带备份。
