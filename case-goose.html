goose：以 MCP 为骨架的扩展体系

大多数 agent 都会走到这一步：工具越接越多，内置的、第三方的、跑在别的进程里的混在一起，每一种都有自己的接入方式和权限规则。goose 的回答是"所有扩展都说 MCP 的数据模型"，再在统一的工具面上叠加命名、按需加载和逐层审批。它适合用来学习：一个通用 agent 怎样在工具越来越多的情况下保持可控。

5 · 关键设计逐个拆

5.1 三类扩展，一套数据模型

它怎么做：ExtensionConfig（agents/extension_config.rs#L55）只有三个变体：


#[serde(tag = "type")]
pub enum ExtensionConfig {
    /// Built-in extension that is part of the bundled goose MCP server
    #[serde(rename = "builtin")]
    Builtin { name: String, /* … */ available_tools: Vec<String> },
    /// Platform extensions that have direct access to the agent etc and run in the agent process
    #[serde(rename = "platform")]
    Platform { name: String, /* … */ available_tools: Vec<String> },
    /// Serialize the oi-kit config directly, preserving the existing tagged JSON.
    #[serde(untagged)]
    External(TransportConfig),
}
类别怎么运行源码
外部 External任意 MCP server，经 stdio 或 Streamable HTTP 连接（oi-kit 的 TransportConfig）extension_config.rs
内置 Builtingoose-mcp 里用 rmcp 写的真 MCP server（autovisualiser、computercontroller、memory、tutorial）。平时用两条 tokio::io::duplex 管道在进程内连接；放进 Docker 容器时改成执行 goose mcp <名字> 走 stdioextension_manager/builtin.rs#L38、goose-mcp/src/lib.rs#L89
平台 Platform进程内实现 PlatformExtension trait，能直接访问会话管理器、模型提供方等。接口的方法和返回类型（list_tools → Tool、call_tool → CallToolResult、get_info → InitializeResult）都是 MCP 的platform_extensions/client.rs#L8、mod.rs#L37

为什么这样设计：三类扩展的运行位置不同，但下游的一切——工具快照、命名、审批、执行结果处理、遥测——只认一种数据模型。新增一个能力时，团队只需要选"放在哪儿运行"，不需要为它设计新的接入协议。内置扩展更进一步：它本身就是一个标准 MCP server，只是省掉了进程开销，所以随时能搬进容器隔离运行。

"一切都是 MCP"要说准确

严格地说，只有外部和内置扩展走 MCP 协议；平台扩展是进程内的 Rust trait，只是数据模型和 MCP 一致。这样设计是有意的：developer（读写文件、shell）、扩展管理器、Code Mode 这些需要直接访问 agent 内部状态，走协议反而别扭。

对应课程：第 11 章（MCP 架构）、第 15 章（四层可替换的接口）。

5.2 工具命名：前缀、例外与纠错

它怎么做：工具名统一改写为 扩展名__工具名（oi-kit-agent/src/mcp/mod.rs#L313），不同扩展的同名工具就不会冲突。几个高频的平台扩展设了 unprefixed_tools: true，以原名暴露（注释写的是"为了作为一等工具直观使用"）。模型偶尔会把分隔符写错，于是有了 recover_mangled_tool_name：


let stripped = trimmed
    .strip_prefix("functions.")
    .or_else(|| trimmed.strip_prefix("functions:"))
    .unwrap_or(trimmed);
for (name, owner) in tools {
    // Prefixed tools: the model turns Goose's "__" separator into a dot
    // ("developer__shell" -> "developer.shell").
    let separator_mangled = name
        .split_once("__")
        .map(|(extension, tool)| format!("{extension}.{tool}"));
    // …
}

为什么这样设计：这是第 3 章"防呆设计"（poka-yoke）的典型。与其在提示词里反复强调"请使用双下划线"，不如在代码里接住模型的常见笔误。注意它只做确定性的映射：能唯一对上的才纠正，对不上的照常报错。

对应课程：第 3 章的工具设计原则（命名空间、防呆）。

5.3 工具面治理：不是所有工具都要每轮出现

工具一多，每一轮的上下文都被工具定义塞满，模型选错工具的概率也随之上升。goose 有四种互补的手段：

  1. 扩展管理器（platform_extensions/ext_manager.rs，默认启用）：给模型 search_available_extensions 和 manage_extensions 两个工具。模型发现缺能力时先搜索，再申请启用。权限检查器对 manage_extensions 特殊处理：在 Approve / SmartApprove 模式下，除非用户给它单独设过权限，否则一律要人批准（permission_inspector.rs#L177）。
  2. 工具延迟加载（ops_toolcalling.rs#L308 的 ToolDeferral）：配置 GOOSE_TOOL_DEFERRAL=lookup 后，MCP 工具只以清单形式列在提示里，模型调用 enable_tools、按工具名（参数 tool_names）启用后，下一轮才真正下发这些工具的定义；GOOSE_TOOL_DEFERRAL_ALWAYS_LOAD 列出始终加载的例外（services.rs#L161-170）。默认关闭。
  3. Code Mode（平台扩展 code_execution，默认关闭）：只给模型 list_functions、get_function_details、execute_javascript 三个工具，其他扩展的调用都写成代码执行。描述里写的就是"通过代码执行调用扩展，节省 token"——正是第 11 章提到的 Code execution with MCP 思路。
  4. Recipe 绑定扩展（recipe/mod.rs#L44）：一个 recipe 里写明 instructions、prompt、extensions、parameters、response（JSON Schema 约束的最终输出）、sub_recipes、retry。每类任务只启用它需要的扩展；扩展配置里的 available_tools 还能再筛到具体工具。

下面的组件用 goose 源码里的真实工具数，加上几个示意性的外部扩展，算一算不同策略下每轮进入上下文的工具定义有多大。

5.4 审批链：五个检查器，最严格者胜

它怎么做：agents/services.rs#L729-746 依次装配五个检查器：

检查器做什么默认行为
Security模式匹配与可选的分类模型，检测提示注入和恶意命令SECURITY_PROMPT_ENABLED 默认 false，即提示注入检测默认关闭（security/mod.rs#L46）
Egress从 shell 和 web 工具的参数里识别外发目标（域名、地址）只记日志、放行，不拦截
Adversary按用户写在 adversary.md 里的规则，让模型审查工具调用没有这个文件就不启用；只审 shell（可配置）；审查失败时放行（fail open）
Permission按模式与用户设置决定允许、拒绝或问人见下文
Repetition检测同一调用的重复次数上限默认不设（RepetitionInspector::new(None)）

合并规则在 apply_inspection_results_to_permissions（tool_inspection.rs）：任何一个检查器说"拒绝"，就从批准和待批里移出；说"需审批"，就从已批准移到待批；说"允许"则不推翻别人的结论。单个检查器执行出错时记日志、跳过它。

权限模式：GooseMode（oi-kit-provider-types/src/goose_mode.rs#L22）有三种，默认是 Auto：

  • Auto：权限检查器直接放行所有工具调用。
  • Approve：每次都问（旧名 chat 仍被识别为它）。
  • SmartApprove：只在敏感调用时问。判定顺序如下。

GooseMode::Approve | GooseMode::SmartApprove => {
    // 1. Check user-defined permission first
    if let Some(level) = permission_manager.get_user_permission(tool_name) { /* … */ }
    // 2. Check for a read-only annotation in SmartApprove mode
    else if goose_mode == GooseMode::SmartApprove
        && self.is_readonly_annotated_tool(tool_name) { InspectionAction::Allow }
    // 3. Special case for extension management
    else if tool_name == MANAGE_EXTENSIONS_TOOL_NAME_COMPLETE { /* RequireApproval */ }
    // 4. Defer to LLM detection (SmartApprove, uncached or legacy cached allow)
    else if goose_mode == GooseMode::SmartApprove && /* … */ { llm_detect_candidates.push(request); continue; }
    // 5. Default: require approval for unknown tools
    else { InspectionAction::RequireApproval(None) }
}

第 2 步用的是 MCP 工具注解里的 readOnlyHint；第 4 步让模型判断这次调用是否只读，而且只缓存否定结论（测试名就叫 smart_approve_only_caches_negative_name_wide_decisions）。原因是：同一个工具，换一组参数就可能从只读变成写操作，"它是只读的"不能按工具名推广，"它要审批"却可以。

为什么这样设计：权限被拆成了互相独立、可以单独开关的部件，每个部件只回答一个问题。最严格者胜的合并规则，让新增一个检查器只会让系统更保守，不会意外放宽权限。

默认值要自己判断

goose 是开发者在自己电脑上用的通用 agent，默认 Auto、提示注入检测默认关闭、Adversary 失败时放行，都是偏向"别打断我"的产品选择。如果你做的 agent 会代表你对外发消息，或者会读取不可信的输入，这些默认值都不能照抄：第 9 章的 lethal trifecta 在这里完全成立。值得照抄的是结构——可组合的检查器链和最严格者胜。

对应课程：第 8 章（按动作分级）、第 9 章（多层防御、fail open 与 fail closed 的取舍）。

5.5 上下文：压缩阈值和"把大结果放进文件"

  • 自动压缩阈值：默认在上下文窗口的 80% 触发（oi-kit-context-management/src/lib.rs#L34），但不超过 22.5 万 token（context_mgmt/mod.rs#L29）。源码注释说明了封顶值的来历：给 OpenAI 长上下文计价档位（输入超过 27.2 万 token）留出余量——压缩点是按成本而不只是按容量定的。两个值都能用 GOOSE_AUTO_COMPACT_THRESHOLD 和 GOOSE_AUTO_COMPACT_TOKEN_LIMIT 改。
  • 工具调用对的摘要：ToolPairCompactionOperation 把超出保留范围的旧"调用 + 结果"成对摘要，每批 10 对（TOOLCALL_SUMMARIZATION_BATCH_SIZE）。需用 GOOSE_TOOL_PAIR_SUMMARIZATION 开启，默认关闭。
  • 超大结果落盘：单段文本超过 20 万字符（GOOSE_MAX_TOOL_RESPONSE_SIZE 可改）就写进临时文件，模型只拿到路径和一句说明，需要时再用工具去读、去搜。这正是第 5 章 Manus 经验里的"把文件系统当上下文"。
  • Top Of Mind（平台扩展 tom，默认启用）：从环境变量 GOOSE_MOIM_MESSAGE_TEXT / GOOSE_MOIM_MESSAGE_FILE 读一段内容，每一轮都注入。

对应课程：第 5 章、第 14 章（成本）。

顺带一提：hooks 与 ACP

goose 的生命周期 hooks（hooks/mod.rs#L55）参照 Open Plugins 的 hooks 规范，事件包括 PreToolUse、PostToolUse、SessionStart、UserPromptSubmit、Stop 等，写在插件目录的 hooks/hooks.json 里。它还能通过 ACP 作为别的应用的 agent 后端（README "Build an app over ACP"、goose-acp-types crate）——"agent 本身通过协议暴露出来"，见第 7 节的对照。

6 · 值得借鉴 / 不宜照搬

值得借鉴不宜照搬
扩展只有三类、共用一套数据模型；新能力只需选"在哪运行"默认 Auto、提示注入检测默认关闭、Adversary 失败放行：只适合使用者就是唯一受影响者的本地开发场景

工具名前缀 + 确定性的名称纠错扩展管理器让模型自己"找工具、开工具"，在开放环境里等于让模型扩大自己的权限；goose 对它强制审批，你也必须如此
压缩阈值按成本封顶；超大结果落盘只回路径近 28 万行的通用 agent，不是你的单一用途 agent 的模板；借鉴机制，别借鉴规模

7 · 对照复盘

两个真实项目里的对应问题
  • N17 · niuma 的对话助手有 45 个工具，每轮全量下发，再用 18 条"用户说 X 就用 Y"的规则做路由。goose 的四种手段可以直接对照：扩展管理器（按需启用）、工具延迟加载（只列清单）、Code Mode（三个工具代替全部）、recipe 绑定扩展（按任务收窄工具面）。
  • D14 · devtask 的编码 agent 没有抽象，状态键和工具名都以某一个 agent 命名，加第二种时到处打补丁。goose 的做法相反：它把自己通过 ACP 暴露出去，任何支持 ACP 的宿主都能把它当后端；扩展这一侧也只认一种数据模型。
  • D8 · devtask 把编码 agent 的权限确认交给另一个模型代按。goose 也在 SmartApprove 里用模型判断"只读"，但做了两道保险：只缓存否定结论；模型没判定为只读的，一律问人。

8 · 读码练习

练习 1：为什么内置扩展要实现成真正的 MCP server，而不是像平台扩展那样直接写成 Rust trait？

看 extension_manager/builtin.rs#L10-43：同一个内置扩展，平时用 duplex 管道在进程内连接，放进 Docker 容器时改成执行 goose mcp <名字> 走 stdio。因为它本来就说 MCP，所以搬进隔离环境不需要改任何代码。平台扩展则需要直接访问 agent 内部，没法这样搬。

练习 2：SmartApprove 里，模型判断"这次调用是只读的"之后，为什么不缓存这个肯定结论？

只读与否取决于参数，而缓存是按工具名做的。shell 这次跑 ls 是只读，下次跑 rm 就不是。按名缓存"需审批"是安全的，按名缓存"只读"会放过后续的写操作。看 permission_inspector.rs 的 cache_non_readonly_decision 及相关测试。

练习 3：Egress 检查器发现 shell 命令要把数据发往一个陌生域名，会拦下吗？

不会。它只记录外发目标并放行（egress_inspector.rs#L308 起的 inspect，结论固定为 Allow）。拦截要靠 Adversary（配置 adversary.md）、Security 或权限模式。这也说明"可观测"和"可拦截"是两件事：先看见，才谈得上拦。

练习 4：自动压缩为什么同时有比例阈值和绝对封顶两个参数？

窗口很大的模型，80% 可能远超长上下文计价档位，费用会陡增；封顶值把触发点压在 22.5 万 token 以内（context_mgmt/mod.rs#L29 的注释）。capped_compaction_threshold 取两者中更早触发的那个。

goose 的五个检查器里，Permission 说"允许"、Adversary 说"需审批"、其余没有意见。最终这次调用会怎样？

  1. 直接执行，因为权限检查器的结论优先
  2. 直接执行，因为"允许"多于"需审批"
  3. 进入待审批，问人
  4. 被拒绝
合并规则是最严格者胜：Allow 不推翻别人的结论，RequireApproval 会把请求从已批准移到待批（tool_inspection.rs 的 apply_inspection_results_to_permissions）。这让新增检查器只会让系统更保守。

你在做一个会代表用户回复客户邮件的 agent，想参考 goose 的权限设计。下面哪种做法最合理？

  1. 沿用 goose 的默认 Auto 模式，靠提示词约束模型
  2. 借鉴检查器链与最严格者胜的结构，但把对外发送设为必须审批，检查器出错时拒绝而不是放行
  3. 全部改用 SmartApprove，让模型判断发邮件是不是只读
  4. 只保留 Egress 检查器，记录所有外发目标
goose 的默认值服务于"开发者本人在本机使用"，而你的场景存在不可信输入和对外动作（第 9 章）。结构可以照抄，默认值要按风险重新设定：对外发送是高风险动作，应该 fail closed。
本章要点
  • goose 只有三类扩展：外部（MCP 协议）、内置（进程内 duplex 管道上的真 MCP server）、平台（进程内 trait，数据模型与 MCP 一致）。
  • 工具名加 扩展名__工具名 前缀，并用确定性的规则纠正模型的常见笔误。
  • 工具面靠四种手段收窄：扩展管理器按需启用、延迟加载、Code Mode、recipe 绑定扩展。
  • 审批是五个独立检查器的组合，最严格者胜；SmartApprove 只缓存"需审批"这一种结论。
  • 默认 Auto、注入检测默认关闭、部分检查失败放行，是面向本地开发者的产品选择；对外发消息的 agent 要反过来设。
