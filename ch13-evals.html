评测：让 Agent 可度量地变好

没有评测的 agent 开发，就是在调一个看不见指针的仪表：改一句提示词，这个例子好了，另外三个悄悄坏了，你却要等用户投诉才知道。这一章讲怎么把"感觉不错"变成可以回归、可以进 CI 的数字。

约 45 分钟前置：第 3、4 章含 1 个分步动画、2 个交互、4 道小测
学完你能
  • 说清 task、trial、transcript、outcome、grader 这几个术语，并据此设计评测
  • 用错误分析（open coding → axial coding）从真实 trace 里找出失败模式
  • 写出二元判定的 LLM judge，并用 TPR / TNR 和人工标注对齐
  • 区分 pass@k 与 pass^k，知道面向用户的 agent 应该看哪个
  • 搭一个最小评测运行器，接进 CI，做能力评测和回归评测

1 · 为什么 agent 必须有评测

传统软件的测试建立在"同样的输入得到同样的输出"之上。agent 打破了这个前提，至少有三个原因：

  • 非确定性：同一个任务跑三次，可能走出三条不同的轨迹。一次通过说明不了什么。
  • 长尾：demo 里的十个例子都对，线上第一千条消息里总会冒出一种你没想到的写法——带附件的、半句话的、两件事混在一起的。
  • 改动的副作用不可见：提示词是一个整体，你为修 A 加的一句话，会改变模型在 B、C、D 上的行为。没有回归集，你根本看不到"按下葫芦浮起瓢"。

Hamel Husain 和 Shreya Shankar 在他们的 AI Evals FAQ（2026-09）里提到，他们大约把 60–80% 的开发时间花在评测相关的工作上。这不是夸张：对 agent 而言，"写功能"往往只是改几行提示词，真正的工程量在于知道这几行改得对不对。

反模式：靠"感觉"迭代

手动试五个例子、觉得"好像好一点了"就上线。这样迭代的系统通常会在几周后陷入一种状态：谁也不敢再改提示词，因为没人知道会坏掉什么。评测集是让你敢改的东西。

2 · 术语：先把名字叫对

Anthropic 在《Demystifying evals for AI agents》（2026-01-09）里给出了一套清晰的术语，本章沿用：

术语含义例子
task（任务）一个评测用例：输入、初始环境、成功标准"把下周三的周会挪到周四并通知参会人"，日历里有一个 6 人的周会
trial（试验）对同一个 task 的一次完整运行；因为非确定性，一个 task 要跑多次同一任务跑 5 次
transcript（记录）一次 trial 的完整轨迹：每轮的上下文、模型输出、工具调用和结果3 轮模型调用、3 次工具调用的完整日志
outcome（结果）trial 结束时环境的最终状态日历里周会在周四，6 位参会人各收到一封通知
grader（评分器）判断 outcome（或 transcript）是否合格的程序或人查日历 API 确认时间；检查发件记录覆盖全部参会人

三类 grader 的取舍

类型优点缺点适合判什么
代码 grader快、便宜、可复现脆弱：只能判能写成规则的东西，规则写死容易误杀合理的变体状态是否正确、格式是否合法、工具是否被调用、参数是否在范围内
模型 grader（LLM judge）灵活，能判语气、完整性、是否答非所问本身不确定，必须用人工标注校准后才可信回复是否礼貌得体、摘要是否遗漏要点、是否做了不该做的承诺
人工金标准贵、慢、难规模化建立标注集、校准 judge、抽检

原则是：能用代码判的就用代码判。LLM judge 是为那些"必须要人的判断"准备的，而且它只是人工判断的一个廉价近似——近似得好不好，要用数字证明（第 5 节）。

评结果，不评路径

Anthropic 的建议之一：优先判 outcome，而不是要求 agent 走某条固定路径。模型可能用一种你没想到的、同样正确的方式完成任务；按路径打分会把这些合理的变体判成失败，还会诱导你把系统调成"按你的想象做事"。路径只在它本身就是要求时才判（例如"发送前必须先征求审批"）。

3 · 第一步永远是错误分析

很多人做评测的第一步是"选一个指标"。Hamel 和 Shreya 的方法反过来：先看数据，再定指标。你不知道系统会怎么失败，就不知道该测什么；通用指标（如 ROUGE、"有用性 1–5 分"）测的往往不是你的系统真正的问题。

  1. 收集真实 trace：线上运行记录，或者在还没上线时用接近真实分布的输入跑一批。
  2. Open coding（开放编码）：逐条读，对每条有问题的 trace 写一句自由笔记，描述你看到的第一个出错点。不要预设分类，像写读书笔记一样写："把'周五前'理解成了本周五，其实对方说的是下周五"。
  3. Axial coding（轴向编码）：把笔记归类，合并同类，得到一个失败分类表，例如"时间理解错误""遗漏参会人""做了无权做的承诺""答非所问"，并统计每类的频次。
  4. 读到饱和：至少亲自看 30 条；持续看，直到新读的 trace 不再产生新的失败类别（理论饱和），通常建议 100 条以上。
  5. 按频次和严重程度排序，决定先修什么、先为哪几类失败建自动化 grader。
谁来定标准？

"这条回复算不算合格"往往有争议。Hamel 和 Shreya 的建议是指定一位"仁慈独裁者"（benevolent dictator）——最懂这个领域的人，由他最终裁定标准，而不是让一个委员会投票。标准不统一，后面所有的标注和 judge 都没有意义。

你刚做完一个会议纪要整理 agent，准备建评测。按本节的方法，第一件事应该是？

  1. 选定 ROUGE 作为主指标，和人写的纪要比对
  2. 写一个"纪要质量 1–5 分"的 LLM judge 先跑起来
  3. 拿 30 条以上真实运行结果逐条读，记下每条的第一个出错点，再归类
  4. 先找 1000 条数据，量大才有统计意义
不先做错误分析，你就不知道这个 agent 实际上怎么失败，指标和 judge 都可能测错东西。量也不是先决条件：读 30–100 条、读到不再出现新的失败类型，比盲目堆数据有用得多。

4 · 写出好的评测任务

有了失败分类，就可以把它们变成 task。Anthropic 的文章给了几条非常实用的经验：

  • 从小处起步：从真实失败里收集 20–50 个简单任务就够开始了。不必等凑齐几百个。
  • 无歧义：每个任务附参考解，标准是"两位领域专家看了会给出同样的判断"。专家都会争论的任务，不适合当自动化评测。
  • 正反例都要有：只测"该做的做了"，会把 agent 调成什么都做；还要测"不该做的没做"（不该回复的消息没回、无权承诺的没承诺）。
  • 每次 trial 从干净环境开始：上一次 trial 留下的日历事件、文件、记忆，会污染下一次的结果。
  • 一定要读 transcript：分数只告诉你"多少失败了"，transcript 才告诉你"为什么"。
  • 多次 trial 都接近 0%，先怀疑任务本身：通常是任务描述有歧义、环境没准备好、或者 grader 写错了，而不是 agent 无能。
案例：grader 的 bug 比模型的 bug 更隐蔽

Anthropic 在同一篇文章里举过一个例子：修掉评分程序里的 bug 之后，某个模型在 CORE-Bench 上的成绩从 42% 升到了 95%。评测本身也是代码，也会有 bug；分数异常低的时候，先读几条被判失败的 transcript，确认它们真的失败了。

5 · LLM judge：二元判定，并且要对齐

需要判语气、完整性、分寸这类东西时，就要用 LLM judge。三条纪律：

  1. 二元 pass/fail，不用 1–5 分。"3 分和 4 分的区别是什么"谁也说不清，打分会漂移；二元判定逼你把标准写清楚，结果也能直接算准确率。
  2. 一个失败模式一个 judge。不要写一个"整体质量"judge，而是"是否做了无权的承诺""是否遗漏了参会人"各一个。每个 judge 的提示词聚焦一件事，才判得准，也才知道该修哪里。
  3. 用人工标注校准。每个 judge 准备 100–200 条人工标注，切成 train / dev / test：train 里挑例子放进 judge 提示词，dev 上迭代 judge，最后在 test 上报告一次。衡量指标是 TPR（人工判通过的，judge 也判通过的比例）和 TNR（人工判失败的，judge 也判失败的比例）。

Anthropic 还建议给 judge 一个 "Unknown" 选项：信息不足以判断时，宁可说不知道，也不要被迫瞎猜。Unknown 的样本交给人看。

一个 judge 在 dev 集上和人工的总体一致率是 90%。但 dev 集里 90% 的样本人工判为通过，judge 把所有样本都判为通过。这个 judge 的问题是？

  1. 没问题，90% 已经很高
  2. TNR 为 0：它一条失败都抓不住，等于没有 judge
  3. TPR 太低，误杀了太多好回复
  4. 样本太少，无法判断
总体一致率会被类别比例掩盖。人工判失败的 10% 里，judge 一条都没判出来，TNR = 0。这正是要分别看 TPR 和 TNR 的原因：你建 judge 的目的恰恰是抓那 10% 的失败。

6 · pass@k 与 pass^k：用户体验到的是哪个？

因为非确定性，每个 task 要跑 k 次 trial。汇总时有两种完全不同的问法：

  • pass@k：k 次里至少一次成功的概率。k 越大越高。适合"可以多试几次、挑一个最好的"的场景，比如生成候选代码再跑测试筛选。
  • pass^k（读作 pass-hat-k）：k 次全部成功的概率。k 越大越低。它来自 Sierra 的 τ-bench，衡量的是一致性：用户每次来都要它做对。

面向用户的 agent 应该看 pass^k。如果单次成功率是 p，且各次独立，那么 pass@k = 1 − (1 − p)k，pass^k = pk。Anthropic 的文章给过一个直观数字：单次 75%，pass^3 只有约 42%。τ-bench 论文里，当时的强模型在零售场景单次成功率不到 50%，pass^8 低于 25%。

上面的公式假设每次 trial 独立。现实中失败往往是相关的：某个任务描述本身有歧义，模型就会稳定地做错。所以实际评测里直接数——k 次 trial 全部通过的任务占多少——而不是用单次成功率去推算。

你在做一个替用户安排日程的 agent，用户每天会用它十几次。评测报告里你最应该盯的数字是？

  1. pass^k：每次都要做对，一致性才是用户体验
  2. pass@k：只要多试几次有一次对就行
  3. 单次 trial 的最高分
  4. 平均 token 用量
用户不会帮你"多试几次挑最好的"。他每次使用都是一次独立的 trial，任何一次做错都会损害信任——这正是 pass^k 衡量的东西。

8 · 回放与盲测：改方法，不改答案

修一个失败时，最省事的做法是把这条用例的正确答案或特征写进提示词（"如果有人问月报导出，就回答……"）。这样这条用例马上就过了，但你修的是答案，不是方法：换一种问法、换一个场景，同样的错误照犯，提示词还越来越像一张补丁清单。

正确的流程是：

  1. 回放（replay）：拿 trace 里记录的完整输入重新跑一次，确认能复现。复现不了就先别改——可能是偶发，也可能是上下文里有你没注意到的东西。
  2. 找原因：读 transcript，问"模型为什么会这样判断"。是上下文缺了关键信息？工具描述有歧义？规则之间互相矛盾？还是任务本身超出了能力边界？
  3. 改方法：修正原因——补上缺失的上下文、澄清规则、改工具描述——而不是写死结论。
  4. 盲测：用没有参与修改的同类用例验证。只在你盯着修的那条用例上通过，说明你可能只是过拟合了它。这也是要留出 test 集、并且只在最后看一次的原因。

当用户确实给了一个"正确答案"（比如"这个群里的事归 A 组管"），它应该作为数据进入记忆或配置，和提示词里的方法分开存放。方法管"怎么判断"，数据管"这个具体事实是什么"。

agent 把"下周五前"理解成了本周五，导致承诺的时间错了。下面哪个修法最好？

  1. 在提示词里加一句"'下周五前'指的是下一个周五"
  2. 把这条消息和正确答案作为 few-shot 例子塞进提示词
  3. 换一个更强的模型
  4. 先回放确认复现，再检查上下文里有没有给出"今天是星期几"；补上当前日期与时区，用一批没见过的相对时间表达盲测
模型无法知道"今天"是哪天，除非你告诉它——这是方法层面的缺陷。选项 1、2 只修了这一种说法；选项 3 也无法凭空知道日期。补上缺失的上下文后，用一批没参与修改的表达（"月底前""下下周一"……）盲测，才能确认方法真的修好了。

9 · 一个最小评测运行器

下面是一个不依赖任何评测框架的运行器骨架：每个任务跑 k 次、每次干净环境、代码 grader 和 judge 组合、保存 transcript、汇总 pass@k 与 pass^k。真实项目里可以换成现成工具，但自己写一遍能让你清楚每个数字是怎么来的。跟练项目 P6 会把它扩展成完整的评测流水线。


type Verdict = 'pass' | 'fail' | 'unknown';

interface Outcome {
  finalText: string;
  toolCalls: { name: string; args: Record<string, unknown> }[];
  env: Env;                      // trial 结束时的环境，用于判结果而不是判路径
}

interface Grader {
  name: string;
  grade(task: Task, out: Outcome): Promise<{ verdict: Verdict; reason: string }>;
}

interface Task {
  id: string;
  input: string;
  setup: () => Promise<Env>;     // 每次 trial 构造一个干净环境
  graders: Grader[];
  suite: 'capability' | 'regression';
}

// 代码 grader：直接查最终状态
const allAttendeesNotified: Grader = {
  name: 'all-attendees-notified',
  async grade(_task, out) {
    const expected = new Set(out.env.calendar.event('weekly').attendees);
    const sent = new Set(out.env.mailbox.sent().flatMap((m) => m.to));
    const missing = [...expected].filter((a) => !sent.has(a));
    return missing.length === 0
      ? { verdict: 'pass', reason: '全部参会人已通知' }
      : { verdict: 'fail', reason: `漏通知：${missing.join('、')}` };
  },
};

// 模型 grader：只判一个失败模式，必须先和人工标注对齐过
function judge(name: string, prompt: string): Grader {
  return {
    name,
    async grade(task, out) {
      const r = await completeStructured(judgeModel, {
        schema: JudgeSchema,          // { reason: string; verdict: 'pass'|'fail'|'unknown' }
        system: prompt,
        user: `任务：${task.input}\n\n最终回复：${out.finalText}`,
      });
      return { verdict: r.value.verdict, reason: r.value.reason };
    },
  };
}

export async function runEval(tasks: Task[], agent: Agent, k = 3) {
  const rows = [];
  for (const task of tasks) {
    const trials: Verdict[] = [];
    for (let i = 0; i < k; i++) {
      const env = await task.setup();                 // 干净环境，避免 trial 之间互相污染
      const out = await agent.run(task.input, env);
      const results = await Promise.all(task.graders.map((g) => g.grade(task, out)));
      const verdict: Verdict = results.some((r) => r.verdict === 'fail')
        ? 'fail'
        : results.some((r) => r.verdict === 'unknown') ? 'unknown' : 'pass';
      trials.push(verdict);
      await Bun.write(`eval/runs/${task.id}.${i}.json`, JSON.stringify({ out, results }, null, 2));
    }
    rows.push({ id: task.id, suite: task.suite, trials });
  }
  const passAtK = rows.filter((r) => r.trials.includes('pass')).length / rows.length;
  const passHatK = rows.filter((r) => r.trials.every((t) => t === 'pass')).length / rows.length;
  const unknown = rows.filter((r) => r.trials.includes('unknown')).map((r) => r.id); // 交给人看
  return { rows, passAtK, passHatK, unknown };
}
把运行器接进 CI

回归集进 CI：每次改提示词、改工具、换模型都跑，pass^k 低于阈值就挂掉。能力集不进门禁（它本来就该偏低），但每次跑完把分数记下来画趋势。LLM 相关的单元测试用"假模型"（脚本化的固定回复）跑，不打真实接口；真实模型的评测作为单独的、可手动或定时触发的任务。

10 · 基准会过期，也会被污染

公开基准是比较模型的通用语言，但要清醒地看它们：

  • SWE-bench Verified 是 OpenAI 在 2024-08 从 1,699 条样本里人工筛出的 500 条编码任务，一度是编码 agent 的标杆。2026-02-23，OpenAI 宣布不再报告这项成绩：他们审计了 138 道难题，59.4% 存在测试或描述缺陷，而且前沿模型都能复述参考解——题目已经进了训练数据。OpenAI 转而推荐 SWE-bench Pro。
  • τ²-bench（2025-06）引入了"双控"环境：用户也会用工具改变共享状态。agent 从单方操作切换到和用户共同操作时，表现明显下降——这更接近真实的办公协作。它的仓库现在建议改用 τ³-bench，且不同版本之间的分数不可比。

结论：公开基准用来选模型，自己的评测集用来做产品。你的用户、你的工具、你的失败模式，任何公开基准都覆盖不到。

11 · 评测集的工程化

问题做法
评测集会变和代码放在同一个仓库、同样走评审；每个任务记录来源（哪条 trace、哪次失败）和加入日期
分数不可比报告里写清评测集版本、模型、提示词版本、k 值；改了 grader 要重跑基线
含真实数据来自线上的输入可能含个人信息，脱敏或只在本地保存，不要原样提交到公开仓库
跑得太慢太贵回归集保持精简（每类失败几条代表性任务）；大集合定时跑，不进每次提交的门禁
judge 自己会漂换 judge 模型或改 judge 提示词后，在 test 集上重新报告 TPR / TNR
真实项目复盘

本章的知识点在两个真实项目里缺位时发生了什么，以及"有这块知识"时会怎么设计：

  • N4 · niuma 87 个改提示词的提交里只有 17 个附了回放数据，一天内四次修同一个判断
  • N5 · niuma 的结清判断一致率没达标就上线
  • D13 · devtask 482 个单测里没有一条测 agent 的决策
本章要点
  • agent 的非确定性和长尾让评测成为必需品；没有回归集，就没人敢改提示词。
  • 先做错误分析（open coding → axial coding，读到饱和），再决定测什么。
  • 能用代码判就用代码判；LLM judge 用二元判定、一个失败模式一个，并用 TPR / TNR 和人工标注对齐。
  • 面向用户的 agent 看 pass^k（一致性），不是 pass@k；单次 75% 时 pass^3 约 42%。
  • 评测数据来自线上真实失败与用户信号，形成飞轮；修失败要改方法，并用盲测验证。
  • 公开基准会失效和被污染：用来选模型，不用来代替你自己的评测集。
